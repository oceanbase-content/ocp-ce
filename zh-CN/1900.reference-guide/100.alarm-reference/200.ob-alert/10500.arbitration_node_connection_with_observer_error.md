# arbitration_node_connection_with_observer_error Arbitration 节点无法连接 observer

## 告警描述

该告警表示仲裁服务节点无法连接对应的 observer。

## 对系统的影响

仲裁副本和 Follower 网络隔离，可能导致 Leader 宕机时无法选举，影响 2F1A/4F1A 的高可用能力。故障发生时，将直接影响系统服务。

## 可能原因

* 硬件故障。
* 防火墙、iptable 等配置故障。
* 路由器、网关配置不通。

## 处理方法

1. 确认故障对象和失败目标。根据告警详情中的 `address`、`host`、`error_code` 和日志中的 `dst="ip:port"`，确认故障的具体仲裁服务实例及无法连接的 observer 节点。若日志中出现 `in_blacklist=true`，表示该 observer 已被仲裁侧标记为 “新建连接失败” 的目标，需要重点排查该目标节点和链路。
  
   ```bash
   grep -n "arb active keepalive probe_connectivity" /home/admin/oceanbase/log/observer.log*
   ```

2. 检查目标 observer 进程和监听端口。登录告警中的目标 observer 节点，确认 observer 进程正常运行，且日志中的目标端口处于监听状态。若 observer 已退出、卡死或端口未监听，应先恢复 observer 服务。

   ```bash
   ps -ef | grep observer
   ss -lntp | grep <告警日志中的目标端口>
   ```

3. 验证仲裁节点到 observer 节点的网络连通性。在仲裁节点上对日志中的 `dst` 地址和端口进行连通性测试，确认连通失败原因，如整机不可达、端口不可达，或链路抖动。若 `ping` 正常但 TCP 建连失败，则通常代表防火墙、安全组、端口监听或路由策略存在问题。

   ```bash
   ping <observer_ip>
   nc -vz <observer_ip> <observer_port>
   traceroute <observer_ip>
   ```

4. 检查主机和网络配置。需重点核查仲裁节点与 observer 节点之间的防火墙、iptables/nftables、交换机 ACL、安全组、路由和网关配置，确认仲裁节点访问 observer RPC 端口时是否存在拦截；同时检查目标 observer 节点的绑定地址、RPC 端口配置是否发生变更，避免出现服务已启动但未监听告警中目标地址或端口的情况。

5. 恢复后验证告警是否消除。修复后，在仲裁节点再次执行 TCP 连通性测试，并持续观察仲裁服务日志，确认日志中不再出现 “arb active keepalive probe_connectivity failed” 或 “blacklisted for new connections” 关键字。如果日志级别允许，告警恢复后可看到 probe connect ok 之类的成功日志。

   若 1 到 2 分钟后仍持续报错，应继续收集双方节点的 `observer.log`、网络策略配置和链路探测结果进一步分析。

   ```bash
   grep -E "probe connect ok|probe_connectivity" /home/admin/oceanbase/log/observer.log*
   ```

6. 必要时寻求更多帮助。如果 observer 服务正常、端口监听正常、仲裁节点到 observer 节点的 TCP 探测仍失败，建议收集故障时刻两端的 `observer.log`、系统日志、网络策略和链路探测结果，联系网络或系统管理员进一步定位硬件故障、交换机/网关异常、跨网段策略拦截等问题。
