# tenant_compaction_status_is_suspend 租户合并暂停

## 告警描述

该告警监测 OceanBase 集群中各租户的合并（Major Compaction）是否处于暂停状态。当 OCP 检测到某个租户的合并被暂停时，立即上报告警。

合并（Major Compaction）是 OceanBase 数据库的核心后台操作，负责将增量数据与基线数据进行合并，以释放存储空间、优化查询性能。该功能从 OceanBase V4.0 版本开始支持租户级别的合并管理。

## 告警原理

下表列出了该告警监控逻辑中涉及的关键参数。

| 参数 | 值 |
| -------- | --------- |
| 监控指标 | tenant_compaction_status |
| 监控表达式 | `max(tenant_compaction_status{@LABELS}) by (@GBLABELS)` |
| 采集指标 | tenant_compaction_status |
| 指标来源 | OCP 定时任务 CheckSuspendTenantCompactionTask 实时查询 OceanBase 集群系统视图 `CDB_OB_MAJOR_COMPACTION`，获取 `is_suspended` 字段判断租户合并是否被暂停。 |
| 采集周期 | 60 秒 |

OCP 通过定时任务 `TenantSchedules.checkSuspendTenantCompactionStatus()` 每 60 秒执行一次采集，具体流程如下：

1. 筛选出 OceanBase V4.0 及以上版本、处于运行状态且非黑屏注册的集群。

2. 对每个集群，通过 `CompactionOperator.listObTenantCompaction()` 执行以下 SQL 实时查询 OceanBase 集群：

   ```sql
   SELECT tenant_id, global_broadcast_scn AS broadcast_scn, is_error AS error, status,
          frozen_scn, last_scn, is_suspended AS suspend, info, start_time, last_finish_time
   FROM CDB_OB_MAJOR_COMPACTION
   ```

3. 对每个租户，根据查询结果中的 `is_suspended` 字段判断合并状态：

   * `is_suspended` 为 `YES`（suspend = true），发布指标值为 1；

   * `is_suspended` 为 `NO`（suspend = false），发布指标值为 0。

监控指标 tenant_compaction_status 的值为 1 时，表示该租户的合并处于暂停状态，触发告警。

## 规则信息

| 监控指标 | 默认阈值 | 持续时间 | 检测周期 | 消除周期 |
| -------- | -------- | ------- | -------- | -------- |
| tenant_compaction_status | 1 | N/A | 60 秒 | 5 分钟 |

其中持续时间为 N/A 表示一旦检测到指标值等于 1，立即触发告警，无需持续等待。

## 告警模板

* **告警概述**
  * 模板：${alarm_target} ${alarm_name}
  * 样例：ob_cluster=obcluster-1:tenant_name=mytenant 租户合并暂停

* **告警详情**
  * 模板：OceanBase 集群 ${ob_cluster_name} 租户 ${tenant_name} 的合并状态为暂停，建议继续合并
  * 样例：OceanBase 集群 obcluster-1 租户 mytenant 的合并状态为暂停，建议继续合并

* **告警恢复**
  * 模板：告警：${alarm_name}，租户合并状态是否是暂停：${value_shown}
  * 样例：告警：租户合并暂停，租户合并状态是否是暂停：0

其中，${alarm_target} 表示产生告警的对象，格式为 `ob_cluster=xxxxxxx:tenant_name=xxxxxxx`。

## 对系统的影响

租户合并长时间暂停可能导致以下问题：

* 存储空间持续增长：增量数据无法与基线数据合并，MemTable 和 SSTable 的冗余数据不断累积，导致磁盘使用量持续上升，严重时可能触发磁盘空间不足告警。

* 查询性能下降：未合并的增量数据层级增多，读取操作需要扫描更多的数据层级，导致查询延迟增大。

* 转储压力增大：合并暂停后，冻结的 MemTable 数量持续增加，可能触发 tenant_active_memstore_percent_over_threshold（MemTable 内存使用率过高告警），严重时可能导致写入被限流。

* 影响后续合并：长时间不合并可能导致后续合并耗时增长，合并期间对系统性能的影响更大。

## 可能原因

常见于以下几种情况：

* 人工主动暂停：管理员通过 OCP 界面或 SQL 命令（`ALTER SYSTEM SUSPEND MERGE`）手动暂停了租户的合并操作，通常是为了在特定窗口期（如大促、数据迁移）避免合并对业务性能的影响。

* 合并出错后被暂停：租户合并过程中发生错误，系统或管理员将合并暂停以防止错误扩大。此场景下通常会同时触发 ob_tenant_compaction_error（租户合并出错）告警。

* 运维操作后未恢复：在集群升级、节点替换、数据迁移等运维操作期间暂停了合并，操作完成后忘记恢复。

* 第三方工具或脚本操作：自动化运维脚本或第三方管理工具在执行特定操作时暂停了合并，但未在操作完成后自动恢复。

## 处理方法

1. 确认告警涉及的租户信息。在 OCP 告警详情中获取集群名（ob_cluster_name）和租户名（tenant_name），定位到具体的租户。

2. 确认合并暂停是否为预期操作。联系集群管理员确认是否人工主动暂停了合并。若为计划内操作（如大促期间主动暂停），可暂时忽略告警，但需确保在操作结束后及时恢复合并。

3. 检查是否存在合并出错。查看是否同时存在 ob_tenant_compaction_error（租户合并出错） 告警。若合并出错导致暂停，需先排查并解决合并错误。可在 OceanBase 集群的 sys 租户下执行以下 SQL 查看合并详情：

   ```sql
   SELECT tenant_id, status, is_error, is_suspended, info
   FROM CDB_OB_MAJOR_COMPACTION;
   ```

   若 `is_error` 为 YES，info 字段会包含具体的错误信息。可通过以下 SQL 清除错误状态：

   ```sql
   ALTER SYSTEM CLEAR MERGE ERROR TENANT = '<tenant_name>';
   ```

4. 恢复租户合并。确认可以安全恢复后，通过 OCP 界面操作或执行以下 SQL 恢复合并：

   ```sql
   ALTER SYSTEM RESUME MERGE TENANT = '<tenant_name>';
   ```

   也可以通过 OCP 的租户合并管理页面单击 **恢复合并** 按钮。

5. 验证合并是否已恢复。恢复后，再次查询确认合并状态：

   ```sql
   SELECT tenant_id, status, is_suspended FROM CDB_OB_MAJOR_COMPACTION
   WHERE tenant_id = <tenant_id>;
   ```

   确认 `is_suspended` 为 NO 后，OCP 将在下一个采集周期（60 秒）更新指标值为 0，告警将在最多 5 分钟（resolve_timeout_seconds: 300）内自动消除。

6. 若以上方法均无法解决，联系 OCP 技术支持人员排查。
