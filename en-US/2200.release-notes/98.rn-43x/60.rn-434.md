# OCP V4.3.4

OCP 4.3.4 is now available. This release primarily enhances the organizational role permission model to improve the overall security of the system.

## Version information

* **Version:** V4.3.4

* **Earlier version:** V4.3.3 BP1

* **Release date:** January 14, 2025

* **Supported upgrade paths:**

  * Currently, you can directly upgrade from OCP V3.2.4 and later to this version.

  * For OCP versions from V2.3.x to V3.2.4, upgrade to OCP V3.3.4 first.

  * For OCP versions earlier than V2.3.0, upgrade to OCP V2.3.x first, and then upgrade to OCP V3.3.4.

## New features

* **Optimized user and permission management model**

    The system administrator manages users at the system level, the organization administrator manages users at the organization level, and the user manages his or her own permissions. This forms a three-tier user management system of system administrator > organization administrator > user. In addition, the system supports permission control over resources and menus. This flexible permission management mechanism allows for resource sharing between organizations, enabling tenant sales in private cloud scenarios, resource isolation between different organizations/departments, and permission isolation between users within the same organization. These enhancements help users effectively manage system permissions and improve overall system security.

* **Support for managing multiple Docker instances on a single host**

    Supports managing multiple Docker instances on a single host in host mode, allowing you to fully leverage the hardware resources of large-scale servers and maximize hardware resource utilization. (The new system parameter `ocp.agent.use.specific.http.ip` is introduced to control whether OCP Agent uses the IP address allocated to Docker. The default value is `false`.)

* **Enhanced basic binlog service**

    Provides comprehensive support for binlog upgrades to ensure efficient and stable service performance.

## Key feature highlights

### Optimized organization role-based permission model

OCP builds a three-tier user management system and a two-dimensional permission control system. The three tiers are system administrator > organization administrator > user. The two dimensions are resources and menus.

A system administrator has full permissions on all resources and menus in the entire system. An organization administrator has full permissions on all resources and menus in the organization. A user can perform limited operations based on the assigned permissions. In the current system, permissions are primarily granted on resources and menus. Resources are clusters, tenants, OBProxy clusters, hosts, and binlog services. Menus are set at the sub-menu level, such as clusters or Cluster > Overview. A system administrator or organization administrator can create roles that have specific combinations of resource and menu permissions and precisely assign the roles to users, thereby granting the users the permissions to access the corresponding resources and menus. If a role has permissions on only resources or menus, users who have the role cannot use the system features normally. For example, a role may have permissions on a specific cluster but not on the cluster menu. In this case, the users who have the role cannot view the cluster page in the system interface. Similarly, if a user has permissions on the cluster menu but not on the cluster itself, the user cannot operate the cluster. OCP also supports a flexible resource sharing mechanism between organizations. The administrator of the organization that has the shared resources can grant the resources to specific roles and users in the organization.

The optimized permission model enables OCP to support the following key business scenarios:

* Tenant sales scenario. OCP allows you to set fine-grained permissions to ensure the compliance and security of the tenant sales process.
* Multi-organization permission isolation scenario. OCP allows you to grant permissions to organization administrators and ordinary users in different organizations, ensuring the independence and autonomy of each organization in resource usage and management, and effectively avoiding permission conflicts and interference.
* Database administrator (DBA), development, and audit personnel. OCP allows you to grant permissions and isolate business scenarios for different roles, clearly defining the permission boundaries of different role groups. This provides rigorous and efficient permission management for database O&M, development, and auditing.

**Notice**

* A host has the same permissions as the tenant it belongs to.
* By default, a user with tenant permissions has read-only access to the clusters in the tenant.

**Limitations**

* Do not grant the Task Center, Alert Center, parameter template, or tag feature to an organization administrator or an ordinary user.
* Make sure that each name in the system, such as username, role name, cluster name, tag name, monitoring dashboard name, or alert template name, is unique.
* This version reconstructs the permission model. Custom roles created based on the previous permission model cannot be automatically compatible. Please configure the permissions of custom roles following [User management](../../1600.system-management-features/200.manage-users/50.user-management-overview.md).

# Version limitations

## Hardware requirements

OCP-Server can be installed on a physical server or in a Docker container. OCP-Server supports the deployment of multiple nodes in high availability mode.

The following table describes the minimum hardware requirements for an OCP-Server node.

| Hardware | Required               |
|-------|------------------------------------|
| CPU  | <li>X86_64, 8 cores</li><li>ARM aarch 64, 8 cores</li> |
| Memory | 16 GiB of available memory |
| Network card | 10 Gigabit network card |

OCP-Agent occupies few resources and has no special requirements for the hardware resources of the installation node.
