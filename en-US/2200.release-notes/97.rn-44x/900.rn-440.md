### Key features

#### Real-time monitoring

To address the complexity of end-to-end performance monitoring and fault localization in distributed database environments, OCP introduces an end-to-end real-time monitoring solution. This solution constructs a five-level monitoring system covering OBProxy > OceanBase cluster > tenant > host > unit. The three core capabilities of this solution enhance the O&M experience:

* **3D topology visualization for a comprehensive view of the architecture**: A dynamic 3D visualization engine is used to present the logical relationships and physical deployment between OBProxy and clusters, clusters and hosts, and tenants and OBServer nodes. The topology view supports drilling down from the global architecture to individual units, providing an intuitive display of resource distribution and dependencies. This makes the "black box" operation state of distributed architectures transparent.

* **Comprehensive metric monitoring for rapid anomaly detection**: Real-time aggregation of over 10 core performance metrics, including QPS, TPS, RT, connection count, and CPU/memory usage rate, enables precise identification of performance turning points through trend analysis. The solution supports viewing associated alert counts directly on the topology view and jumping to the alert center, enabling one-click tracing from metric anomalies to the root cause of faults, significantly improving fault localization efficiency.

* **Dual-mode data presentation for diverse O&M scenarios**: Structured table data views are provided, complementing graphical and digital information to meet the needs of both managers for global situational awareness and technicians for in-depth analysis. This effectively reduces the cognitive and management barriers of distributed systems.

With the end-to-end real-time monitoring solution, users can better manage and optimize system performance for daily O&M, fault troubleshooting, and large-screen displays, enhancing system stability and reliability.

#### KMS TDE encryption

The TDE feature in OceanBase Database is a powerful data protection measure designed to ensure the security of data stored on disk. Through an invisible encryption mechanism, TDE automatically encrypts data as it is written to storage devices and automatically decrypts data when it is read. This process is completely transparent to users, effectively preventing hackers and malicious users from accessing sensitive data in data files, database backups, or on disk.

OceanBase Database's TDE feature uses a two-tier key system for encryption and decryption. The smallest encryption granularity is a table in a database, but the table must be located in an encrypted tablespace. A tablespace can be understood as a collection of tables, a concept designed by OceanBase Database to ensure compatibility with Oracle databases. Each encrypted tablespace is associated with a specific encryption algorithm and a corresponding data key, used to encrypt the data within that tablespace. Additionally, each tenant has a master key, which is used to encrypt the data keys of the tablespaces. To prevent unauthorized decryption, the master key is typically stored in a dedicated keystore.

KMS supports a series of key management functions, including generation, storage, backup, recovery, and destruction. Through KMS, users can conveniently manage access permissions to their digital assets, ensuring that only authorized users can access specific data resources. Furthermore, KMS helps users avoid security risks associated with key loss or forgetting.

To provide a unified key management solution, OCP acts as an agent for the KMS service, offering a unified key management service and interface. This shields OceanBase Database from the differences between KMS services of different cloud providers. Users only need to provide the access domain name, AccessKey (AK), SecretKey (SK), and master key ID of Alibaba Cloud or Tencent Cloud to easily enable the KMS TDE encryption feature for tenants.

### New features

#### Basic maintenance

1. **Cluster Management**: When you upgrade a cluster, the upgrade process automatically displays a prompt that the Dynamic Partition feature is enabled. This prevents the DDL operations from being disabled during the upgrade from affecting the business operations or interrupting the business operations. The supported OceanBase Database version range is [V4.2.5 BP2, +∞).
2. **Cluster Management**: During the installation, deployment, or upgrade of OceanBase Database, if the host is found to not support the AVX instruction set, the relevant operations will be automatically stopped to avoid potential compatibility issues. Supported OceanBase Database versions include [V4.2.5, V4.2.5 BP2) and [4.3.5, 4.3.5 BP4).
3. **Cluster Management**: Displays information related to tenant-level primary/standby, major compactions, and data backups to help users quickly understand the current status of the cluster.
4. **Tenant management**: When you create a MySQL tenant, you can set the variable `ob_compatibility_control`. This feature applies to OceanBase Database versions [V4.2.3, V4.3.0) and [V4.3.2, V4.3.5 BP3).
5. **Tenant Management**: Supports custom tenant connection strings, making it convenient for users to access databases using different domains.
6. **Tenant management**: supports granting the `Create routine` privilege to a user in a MySQL tenant. This feature is available in OceanBase Database V4.2.2, V4.3.0, V4.3.1, and later.

#### Monitoring and alerts

1. Supports alerts for the synchronization status (SYNCHRONIZATION_STATUS) of primary and standby clusters of OceanBase Database V2.x/V3.x.
2. Added the following 8 metrics for tenant monitoring: Read Lock Application Success Rate of MemStore, Write Lock Application Success Rate of MemStore, RPC Request Success Rate, GTS Request Count, Transaction Rollback Ratio, Fuse Row Cache Hit Rate, Schema Cache Hit Rate, and Temporary Page Cache Hit Rate.
3. Added two cluster-level monitoring metrics: RPC network delay and delivery failures within the sampling period.
4. It supports displaying the maximum value, average value, and current value of a monitored metric in an observation time period of the OBProxy cluster.

#### Disaster recovery management

1. In a disaster recovery scenario of one primary tenant and multiple standby tenants or cascading tenants, you can freely switch between the primary and standby tenants for synchronization source and perform site switch drills.
2. For the standby tenant created in the archive-based manner, the restore point of the tenant is specified by the parameter `ocp.standby.tenant.restore.advance.seconds` (the default value is the current time minus 60 seconds).
3. You can use the Overview page of a tenant to view the primary/standby relationship between tenants.

#### Management of response plans

1. If two tenants exist, and primary and standby tenants have the same service name, read traffic in the standby tenant is automatically switched to the primary tenant when service of the standby tenant fails.
2. If the OBManager (OBM) crashes, it automatically restarts the binlog process, which takes effect for only once every 30 minutes.

#### Manage binlogs

When you create a Binlog instance, you can specify the position of a Clog file in the instance to set the starting point for Clog file parsing. This feature allows downstream systems to subscribe to Clog files as needed.

#### Restore

1. You can enable or disable the dynamic partition feature during a full data restore based on your business requirements to avoid data loss caused by this feature. This feature is supported in OceanBase Database versions [V4.3.5 BP2, +∞).
2. Rapid tenant recovery: After a tenant is recovered, the tenant is read-only. This means that the tenant cannot be merged or backed up. Supported OceanBase Database versions: V4.3.3 and later.
3. Backups at the cluster level are skipped if the backup strategy specifies to skip locked tenants by default.
4. Support the advanced options for object storage compatible with the S3 protocol:
   * delete_mode=delete (default)/tagging, supported in OceanBase Database V4.2.3.0 to V4.2.5.0 and in V4.3.0 and later.
   * checksum_type: Specifies the checksum type. Valid values: md5 and crc32. The default value is md5. This parameter is supported in OceanBase Database V4.2.1.6 to V4.2.2.0 and V4.2.3.0 and later.
   * addressing_model=virtual_hosted_style (default) or path_style. This parameter is supported in OceanBase Database V4.2.1.9, V4.2.2.0, V4.2.5.1, V4.3.0.0, V4.3.5.0, and later.

### Optimize Products

#### Managing a cluster

1. The Resources tab now includes real-time visual displays of remaining CPU, memory, log disk, and data disk space. This helps users quickly monitor resource usage and improve operations and maintenance efficiency.
2. You cannot reinstall the OBServer node if the zone contains only one OBServer node and a replica exists on it.

Tenant specifications can be searched by specification name, addressing query efficiency when there are many tenant specification names.

#### Host Management

Operations in the Hosts column support displaying the host standardization report.

#### Backup and recovery

1. sys tenants are system management tenants that do not support backup and restore. Therefore, their backup and restore page has been removed to avoid user confusion and errors. This applies to OceanBase Database of [V4.0, +∞).
2. When you restore a tenant, support the users to select an operation path: to view the task progress in the Task Center, or stay on the restore initiation page to continue the operation.

#### Others

1. **AI Assistant** Provides general conversation capabilities for business scenarios that do not have configured large-scale models, to achieve document search capabilities.
2. Remove the limit on the number of characters displayed in tags on the details page of a cluster, tenant, OBProxy, or host.
3. **Audit of operations** supports the display of the IP addresses of the clients that access the database.

### Product Behavior Updates

1. Because the behavior of the Tencent Cloud COS product may change and cause exceptions in database log backup, we recommend that you use the S3 protocol instead of the COS protocol. Supported OceanBase Database versions are [V4.2.1.9, V4.2.2), [V4.2.5.0, V4.3.0), and [V4.3.3.0, V4.4.0). OceanBase Database V4.4.0 and later no longer support the COS protocol.
2. Removes the exclusive-host constraint for the Binlog service, enabling multiple products to share the same host (only recommended for testing environments), thereby reducing deployment and O&M costs.

The following table lists the minimum hardware requirements for OCP-Server nodes.
