# References about OpenSearch

## Background

To support the full-link tracing feature in OceanBase Database V4.x, OCP V3.3.0 introduces the Data Intelligence feature, which includes full-link tracing and log search features. These features rely on an OpenSearch cluster for data storage and query. In a private cloud scenario, you can also deploy an OpenSearch cluster alongside the OCP cluster. This approach can reduce the deployment learning curve for support personnel.

## Prerequisites

You have planned the resources for the OpenSearch cluster based on the **Cluster specifications assessment** section.

## Deploy an OpenSearch cluster

1. Obtain the OpenSearch Docker image on the OCP host. You can run the following command to obtain the required image. If you need to download the image, contact the delivery service personnel.

   <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>The latest version of the image is V3.3.2. </p>
   </main>

    ```shell
    docker pull oceanbase/opensearch:3.3.2
    ```

2. Deploy OpenSearch using Docker.

    1. Generate a root certificate.

        ```shell
        cd ${pem-path}
        openssl genrsa -out ./root-ca-key.pem 2048
        openssl req -new -x509 -sha256 -key ./root-ca-key.pem -subj "/C=CA/ST=ONTARIO/L=TORONTO/O=ORG/OU=UNIT/CN=ROOT" -out ./root-ca.pem
        ```

    2. Start the container.

        ```shell
        docker run -d --net host -v ${pem-path}/root-ca-key.pem:/opt/opensearch/config/root-ca-key.pem -v ${pem-path}/root-ca.pem:/opt/opensearch/config/root-ca.pem --env  OPENSEARCH_USERNAME=xxx --env OPENSEARCH_PASSWORD=xxx --env OPENSEARCH_NODE_URLS=ip1,ip2,ip3 --env HOST_IP=xxx.xxx.xxx.xxx --env OPENSEARCH_JVM_HEAP=4g --name ocp-opensearch reg.docker.alibaba-inc.com/oceanbase-platform/ocp-opensearch:3.3.2-x64
        ```

        <main id="notice" type='notice'>
          <h4>Notice</h4>
          <ul>
          <li>The Docker image of OpenSearch must be started in the host network mode.</li>
          <li>The ${pem-path} in the command specifies the directory where the root certificate is stored. </li>
          <li>If you want to mount a host directory to the OpenSearch directory, first set the permissions of the mount directory on the host to admin. The uid and gid of the admin user in the container are both 500. If the host admin user ID is different from the container admin user ID, the mounting will fail. In this case, after the container starts, you can execute the <code>chown admin:admin /data/1/opensearch</code> command in the container and then restart the container. </li>
          <li>If you want to deploy OpenSearch in a multi-node mode, copy the root certificate to each node and then start the container on each node. </li>
          </ul>
        </main>

    When you start the image, the following environment variables are provided:

    | Environment variable | Required | Description |
    |---------|--------|-------|
    | OPENSEARCH_USERNAME | Yes | The username for logging in to OpenSearch, which is also the username for logging in to cerebro. |
    | OPENSEARCH_PASSWORD | Yes | The password for logging in to OpenSearch, which is also the password for logging in to cerebro. |
    | OPENSEARCH_NODE_URLS | Yes | The list of OpenSearch nodes. |
    | HOST_IP | No | The IP address of the host. Please specify the actual IP address. If you do not specify it, the system will execute the `hostname -i` command to obtain it. Make sure that `/etc/hosts` is correctly configured. |
    | OPENSEARCH_JVM_HEAP | No | The size of JVM memory for OpenSearch. We recommend that you set it to half of the node memory (max 32 GB). The default value is 4 GB. |
    | OPENSEARCH_HTTP_PORT | No | The port for external communication for OpenSearch. The default value is 9200. |
    | OPENSEARCH_TCP_PORT | No | The port for communication between OpenSearch nodes. The default value is 9300. |
    | CEREBRO_PORT | No | The port of cerebro. The default value is 9100. |
    | ELASTICSEARCH_EXPORTER_PORT | No | The port of elasticsearch_exporter. The default value is 9114. |

3. Connect to the OpenSearch cluster from OCP.

    After OCP starts, manually add the address and account password in **System Parameters**. For more information, see [Configure link query parameters](../1300.log-service/300.configuration-trace-paremeters.md).

    | Parameter | Description |
    |----|----
    |ocp.analyze.es.client.addresses| The IP addresses of the OpenSearch cluster. If multiple client addresses are configured, separate them with commas.   |
    |ocp.analyze.es.client.username| The username for logging in to the OpenSearch cluster.   |
    |ocp.analyze.es.client.password| The password for logging in to the OpenSearch cluster.     |

## Description of OpenSearch Service

The docker image of OCP-OpenSearch contains three services: opensearch, elasticsearch_exporter, and cerebro.

### OpenSearch

OpenSearch is a distributed search and analytics engine that is community-driven and built on Apache Lucene. It originated from ES 7.10.2 and uses the Apache License 2.0.
After you add data to OpenSearch, you can perform full-text searches on the data: search by field, across multiple indexes, boost fields, rank results by score, sort results by field, and aggregate results.

### elasticsearch_exporter

elasticsearch_exporter is an exporter that uses the Prometheus format to export various metrics of OpenSearch. It has been integrated into ocp_prometheus. The open-source license is Apache License 2.0.
You can use elasticsearch_exporter to obtain monitoring data of OpenSearch, including index performance, JVM memory usage and garbage collection, cluster health and node availability, system and network metrics.

### cerebro

cerebro is an OpenSearch management tool. You can perform O&M operations on OpenSearch through a web interface. It supports operations such as index creation and deletion, and cluster configuration parameter modification. The software is open source and uses the MIT License 2.0.

### Log location

The log directory is: `/home/admin/logs`.

## Estimate the specifications of an OpenSearch cluster

### Disk space

The disk space required for an OpenSearch cluster depends on the following factors:

* The number of replicas.
* The overhead of indexes: typically 10% larger than the source data.
* The operating system: 5% of the space is reserved by default.
* The overhead of OpenSearch: 20% of the space is reserved for internal operations such as segment merging and logging.
* The security threshold: at least 20% of the space is reserved.

The minimum disk size = source data size × (1 + number of replicas) × 1.7. You can use this formula to control the disk space.

### CPU and memory

OpenSearch consumes minimal CPU resources for computations. It requires a sufficient amount of memory for indexing and querying. We recommend that you allocate 16 GB, 32 GB, or 64 GB of memory to OpenSearch. The memory allocated to OpenSearch should not exceed half of the total system memory or 32 GB.

### Shard assessment

The size and number of shards are important factors affecting the stability and performance of an OpenSearch cluster.

We recommend that you allocate shards to an OpenSearch cluster in the following ways:

* Before allocating shards, test the OpenSearch cluster with sample data. When a large amount of data is written, reduce the size of written data to alleviate the pressure on the OpenSearch cluster. We recommend that you use more than one primary shard and one replica shard in this case. When a small amount of data is written and the write volume is low, you can use one primary shard and multiple replica shards.
* We recommend that you allocate no more than 30 GB of storage space to a single shard (optimal) or at most 50 GB of storage space to a shard in special cases. The shard size should not be too large or too small. If the shard size is too large, the recovery speed of Elasticsearch after a failure becomes slow. If the shard size is too small, a large number of shards will be generated. In this case, each shard will use a certain amount of CPU and memory resources. This will lead to poor read/write performance and memory insufficiency.
* We recommend that you allocate the same number of shards (including replica shards) as data nodes or a number that is an integer multiple of the number of data nodes to ensure uniform distribution of shards across nodes and facilitate load balancing.

### Disk space required for an OB OpenSearch cluster

A node of the OB OpenSearch cluster generates about 6 to 8 GB of logs per day. The trace feature is under development and can be temporarily counted as 8 GB. By default, data is retained in OpenSearch for one week. Therefore, if a node has one replica shard and the data is retained for seven days, 380 GB of disk space is required for OpenSearch on this node. The following table shows the configuration specifications of the OpenSearch cluster based on this requirement:

| Number of observers | Size of the OpenSearch cluster | CPU cores per node | Memory per node | Disk space |

| 20 | 4 | 8 | 32 GB | 2 TB |
| 50 | 10 | 8 | 32 GB | 2 TB |
| 200 | 20 | 16 | 64 GB | 4 TB |
| 400 | 40 | 16 | 64 GB | 4 TB |
