# External Integration Overview

You can configure external account services of the OAuth2 or OIDC type to enable single sign-on to the OCP homepage.

## Background Information

Single Sign-On (SSO) is an authentication method that allows users to securely authenticate with OCP using a single credential.

## Concepts

* OAuth (Open Authorization) is an open standard authorization protocol that allows users to grant third-party applications access to information stored on their resource servers without providing the username and password to the third-party application, thereby decoupling authentication from authorization. As an international standard, OAuth is widely adopted and continuously evolving. OAuth 2.0 is the successor version of the OAuth protocol, more secure and easier to implement, but not compatible with OAuth 1.0, which has been completely deprecated. OAuth defines a secure, open, and simple standard for authorizing user resources, allowing third parties to obtain user authorization information without knowing the user's account and password.

  * OAuth 2.0 is a delegated authorization framework for REST APIs.
  * OAuth 2.0 is token-based authorization, enabling applications to obtain limited access to user data without exposing the user's password.
  * OAuth 2.0 decouples authentication from authorization.

* OpenID Connect (OIDC) is a security authentication mechanism where third-party applications connect to an Identify Provider to obtain user information and return this information to the third-party application in a reliable manner. OIDC extends the OAuth 2.0 protocol by adding extended ID Token fields to provide basic user identity information. The ID Token is encapsulated in JSON Web Token (JWT) format, providing self-containedness and tamper-proof mechanisms, making it safe to pass to third-party applications and easy to verify.

## Principles

### OAuth2

OCP adapts to the standard OAuth2 authentication center and currently only supports the authorization-code mode, where the application uses an authorization code to request an access token or refresh token from the authorization server.

![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/432/OAuth2.png)

As shown in the figure, the authorization process can be described in the following steps:

1. The user logs in to the application system, requesting a redirect to the authentication server, and is returned to the login authentication page via a 302 response.
2. The user enters authentication information for verification. If passed, the authentication server returns a code to the application system.
3. The application system exchanges the code with the authentication server for an access token. The authentication server verifies information such as the Client ID and code, and sends the access token to the application system.
4. The application system uses the access token to query the user's login information. The authentication server returns the user information, such as the username.
5. The application system verifies the username, creates a session, and redirects to the redirect URL.

### OIDC

![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/432/oidc.png)

1. The client sends an authentication request to the authentication service.
2. The user confirms authorization on the authentication page.
3. The authentication service verifies the authentication request and returns a code to the client.
4. The client requests a callback interface from the business service, including the code.
5. The business service requests the authentication service to issue a token, including the code, Client ID, and Client Secret.
6. The authentication service verifies the legitimacy and returns an ID token.
7. Authentication succeeds, and the business service returns the ID token to the client.
8. The client makes a request to the business, including the ID token.
9. The business service verifies whether the ID token is legitimate and then returns the business response.

## Login scenarios

* When SSO mode is enabled and local login mode is enabled, users can log in with their account credentials or through third-party login.
* When SSO mode is enabled but local login mode is not enabled, users can directly log in to the OCP system with their third-party account credentials (the first login requires redirecting to the third-party authorization login page; after authorization, subsequent visits allow direct login).
* When SSO mode is not enabled, only local account credential login is supported.
