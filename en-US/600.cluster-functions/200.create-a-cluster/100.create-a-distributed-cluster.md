# Create a distributed cluster

A distributed cluster is an enterprise-level native distributed database architecture of OceanBase. It features financial-grade high availability and smooth scaling, and is highly compatible with Oracle/MySQL modes. It is suitable for core business systems with high data security requirements.

You can create a distributed primary cluster to be managed based on your business needs.

<main id="notice" type='notice'>
<h4>Applicability</h4>
<p>OCP Community Edition only supports creating primary clusters.</p>
</main>

## Background information

* When the cluster **<UI-TERM key="ocp-v2.Cluster.Component.ClusterList.DeploymentMode">Deployment Mode</UI-TERM>** is set to Single Zone Multi-host, only the computing capability of the OceanBase service is scaled out. This configuration does not provide high availability through multiple replicas and is suitable for development and test environments.
* When the cluster **<UI-TERM key="ocp-v2.Cluster.Component.ClusterList.DeploymentMode">Deployment Mode</UI-TERM>** has an even number of zones, it cannot meet high availability requirements and poses data security risks. We recommend that you adjust the configuration to maintain an odd number of zones or enable the arbitration service for the cluster or tenant.

## Prerequisites

* The current user logged in to OCP has the **ADMIN** or **ORG_ADMIN** role.

* (Optional) If you are creating a multi-replica OceanBase cluster, an available OBProxy cluster must already exist in the current OCP. You can refer to the following links to add an OBProxy cluster.

  * [Create an OBProxy cluster](../../800.obproxy-functions/200.create-an-obproxy-cluster.md)

  * [Take over OBProxy](../../800.obproxy-functions/400.manage-a-obproxy-server/200.take-over-an-obproxy.md)

## Procedure

1. After logging in to OCP, click **<UI-TERM key="ocp-v2.component.alarm.Search.Cluster">Cluster</UI-TERM>** in the left navigation bar to go to the **<UI-TERM key="ocp-v2.Cluster.Import.Cluster">Cluster</UI-TERM>** overview page.    1. If you have no manageable clusters, the system will prompt you to create a new cluster on the **<UI-TERM key="ocp-v2.Cluster.Component.ClusterList.ClusterList">Clusters</UI-TERM>** tab. Click **<UI-TERM key="ocp-v2.page.Cluster.CreateANewCluster">Create Cluster</UI-TERM>** directly in the prompt.

   2. If you already have manageable clusters, click **<UI-TERM key="ocp-v2.page.Cluster.CreateANewCluster">Create Cluster</UI-TERM>** in the upper-right corner of the **<UI-TERM key="ocp-v2.Cluster.Component.ClusterList.ClusterList">Clusters</UI-TERM>** tab.

### Step 4: Configure Cgroup

Cgroup is mainly used for CPU resource isolation between tenants and within tenants in an OceanBase cluster. You can choose whether to enable Cgroup for the cluster based on your actual business type to achieve stronger CPU/IOPS isolation. When you create an OceanBase cluster of version V4.0 or later, Cgroup is enabled by default.

* Enabling Cgroup will result in a performance drop of about 7%. If your business scenario involves single tenants, small specifications (<14C), and requires higher database performance, it is recommended to disable Cgroup.
* If the host's operating system kernel version is lower than 5.1.0, it is recommended to disable Cgroup for the cluster, as this may cause system performance degradation or instability.
* If the host's operating system kernel version is lower than 4.1.9, the cluster will not be able to create tenants. In this case, Cgroup is disabled by default and the Cgroup switch is not displayed.

### Step 5: Configure CPU overprovisioning

When loads from different business scenarios overlap, an OceanBase cluster may experience overload during operation, leading to thread competition for CPU resources among different tenants and consequently slowing down the actual business scenarios. To ensure that the loads of different tenants in the system can run in an orderly manner, you can configure CPU overprovisioning when configuring CPU resources to improve resource utilization.

<main id="notice" type='explain'>
<h4>Note</h4>
<p><ul><li>Only OceanBase V4.0 and later support CPU overprovisioning. With proper configuration, you can fully utilize hardware resources.</li><li>The CPU overprovisioning feature depends on Cgroup. Before configuring the CPU overprovisioning ratio, please enable Cgroup for the cluster.</li></ul>
</p></main>

In the **<UI-TERM key="ocp-v2.Cluster.New.CpuOversoldSettings">CPU Oversubscription Settings</UI-TERM>** section, you can configure the overprovisioning ratio using the slider or the input box. The default value is 120%, with a range of 101% to 200%.

### Step 6: Configure the JVM environment dependency service

Enable **JVM Environment Dependency Service** so that OBServer can interface with external tables, Java UDFs, ODPS remote access, and other features through the JNI (Java Native Interface) framework.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p><ul><li>Only OceanBase Database V4.3.5.1 and later support configuring the JVM environment dependency service.</li><li>Refer to <a href='https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000003976539'>Deploy the OceanBase Database Java SDK environment</a>. Use the <a href='../../1500.manage-software-packages/100.upload-a-software-package.md'>Upload a software package</a> feature to upload the JAR package library required by the service dependency in advance, ensuring that OBServer can load and use it properly.</li><li>This service depends on the Java environment. If any machines in the cluster have not yet been configured with a Java environment, configure it yourself:<ul><li>If the host is an x86_64 architecture, ensure OpenJDK is version 15 or later.</li><li>If the host is of another architecture, ensure OpenJDK is version 11 or later.</li></ul>
</p></main>

1. Configure the service type.

   OCP supports five service types: ODPS external table, HDFS external table, Java UDF, ODPS Catalog, and MySQL external table plugin. Different services have different requirements for the OceanBase cluster version. For details, see the following table.

   | Service type | OceanBase version requirement |
   |-----------------|-----------------|
   | ODPS external table | [V4.3.5.1, +∞)  |
   | HDFS external table | [V4.3.5.1, +∞)  |
   | Java UDF | [V4.3.5.1, +∞)  |
   | ODPS Catalog | [V4.4.0, +∞)    |
   | MySQL external table plugin | [V4.4.1, +∞)   |

   <main id="notice" type='explain'>
   <h4>Note</h4>
   <p>When configuring the service type, the first four service types—ODPS external table, HDFS external table, Java UDF, and ODPS Catalog—are enabled by default and cannot be disabled.</p></main>

2. Configure JVM memory.

   Proper JVM memory configuration directly affects the stability and performance of Java applications. By setting the JVM memory, you can ensure the basic operational needs of Java applications in the OceanBase cluster. The following table provides predefined JVM memory configuration options based on the different memory specifications of OBServer nodes:

   | OBServer memory node | -Xmx/-Xms | -Dio.netty.maxDirectMemory | Total JVM memory |
   |--------------------|----------------------|-----------------------------|--------------|
   | 16 GiB             | 512 MiB              | 512 MiB                     | 1 GiB        |
   | 32 GiB             | 1 GiB                | 1 GiB                       | 2 GiB        |
   | 70 GiB             | 3 GiB                | 3 GiB                       | 6 GiB        |

3. Configure the JAVA_HOME path.

   After enabling the JVM environment dependency service, you need to manually specify the JAVA_HOME path. Ensure that the JAVA_HOME paths for all OBServer nodes in the cluster are identical.

### Step 8: Configure users, paths, and ports

In the **<UI-TERM key="ocp-v2.Cluster.New.CustomSettings">Custom Settings</UI-TERM>** module, you can perform cluster-level user configuration (such as the operating system owner user), path configuration (such as software installation paths, data disk paths, and log disk paths), and port configuration (such as SQL ports and RPC ports).

1. Configure the operating system owner user:

   This user is the operating system user used for installing and running OBServer and cannot be edited. You can modify this user by adjusting the default configuration of the `ocp.operation.default.os.user` parameter. This parameter modification only affects the creation of distributed clusters, [standalone clusters](200.create-a-standalone-centralized-cluster.md), [OBProxy clusters](../../800.obproxy-functions/200.create-an-obproxy-cluster.md), and [arbitration service clusters](../1350.manage-arbitration-services/200.create-arbitration-services.md). It does not affect other configurations of existing clusters.

2. Configure related paths:

   | Configuration | Description |
   |-----|-------|
   | **<UI-TERM key="ocp-v2.Information.Detail.CollectDetails.SoftwareInstallationPath">Software Path</UI-TERM>** | <ul><li>When the **Operating System Owner User** is admin, the **<UI-TERM key="ocp-v2.Cluster.New.SoftwareInstallationPath">Software Path</UI-TERM>** defaults to `/home/admin/oceanbase` and supports customization.</li><li>When the **Operating System Owner User** is non-admin, the **<UI-TERM key="ocp-v2.Detail.Overview.SoftwareInstallationPath">Software Path</UI-TERM>** defaults to `/opt/oceanbase/oceanbase` and supports customization.</li></ul> |
   | **<UI-TERM key="ocp-v2.Information.Detail.CollectDetails.DataDiskPath">Data Disk Path</UI-TERM>** | Defaults to `/data/1` and supports customization. |
   | **<UI-TERM key="ocp-v2.Cluster.New.LogDiskPath">Log Disk Path</UI-TERM>** | Defaults to `/data/log1` and supports custom paths. In a production environment, it is recommended that the log disk space be at least three times the host's memory space. Additionally, to avoid disk usage collection issues, it is recommended to mount the data directory, installation directory, and log directory on different disks.<main id="notice" type='explain'><h4>Note</h4>Starting from OCP 4.3.0 BP1, when creating an OceanBase cluster of the following versions, the slog directory will be placed on the log disk and will no longer be bound to the data disk. If the size of the disk where slog and clog reside is less than 40 GiB, the reserved space for slog will be less than 4 GiB, which may affect slog writing.<ul><li>V4.2.4.0 ≤ OceanBase < V4.3.0.0</li><li>OceanBase ≥ V4.3.1.0</li></ul>For more information about slog, see <a href="https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000000819002">OBServer Node Installation Directory Structure</a>.</main> |

3. Configure ports:

   | Configuration | Description |
   |-----|-------|
   | **<UI-TERM key="ocp-v2.Cluster.New.SqlPort">SQL Port</UI-TERM>** | Defaults to 2881 and supports customization. |
   | **<UI-TERM key="ocp-v2.Detail.Component.OBProxyList.RpcPort">RPC Port</UI-TERM>** | Defaults to 2882 and supports customization. |

4. After configuration, click **<UI-TERM key="ocp-v2.Cluster.New.Test">Test</UI-TERM>** to verify that the specified path and port are available.

      * If the test passes, click **<UI-TERM key="ocp-v2.Cluster.Component.ConfirmClusterDrawer.New">Create</UI-TERM>**.
      * If the test fails, troubleshoot the issue as prompted.

### Step 9: Confirm the configuration information

1. In the right-side panel, confirm that the configured cluster information is correct, and click **<UI-TERM key="ocp-v2.src.hook.usePreCheckSteps.NextStep">Next</UI-TERM>**.

2. Perform a pre-check before creation. The system verifies whether your environment meets the minimum requirements for creating a distributed primary cluster. If a check item fails, you can perform the following operations as prompted:

    * **<UI-TERM key="ocp-v2.Detail.Component.UpgradeModal.Upload">Upload</UI-TERM>**: Displayed only when a specific check item fails. Follow the prompts and click **<UI-TERM key="ocp-v2.component.UploadPackageDrawer.Upload">Upload</UI-TERM>** to manually upload the required software package.
    * **<UI-TERM key="ocp-v2.Component.AddBackupStrategy.Skip">Skip</UI-TERM>**: This operation skips the current check item (designed for special scenarios). Ensure the related check item meets product specification requirements; otherwise, subsequent process execution may fail. After skipping, the status of that check item changes to **<UI-TERM key="ocp-v2.component.PreCheck.CheckResult.Warning">Warning</UI-TERM>**.
    * **<UI-TERM key="ocp-v2.Alarm.Event.Detail.Retry">Retry</UI-TERM>**: Troubleshoot and fix the issue based on the failure cause and optimization suggestions. After fixing it, click **<UI-TERM key="ocp-v2.src.constant.task.TryAgain">Retry</UI-TERM>** to rerun the failed check item.
    * **<UI-TERM key="ocp-v2.component.PreCheck.CheckResult.RetryAll">Retry All</UI-TERM>**: After all issues are troubleshooted and fixed, click **<UI-TERM key="ocp-v2.component.PreCheck.CheckResult.RetryAll">Retry All</UI-TERM>** to rerun all failed check items.

3. Once there are no failed check items, click **<UI-TERM key="ocp-v2.Component.AddSamplingInspectStrategy.New">Create</UI-TERM>**.

   After submitting the new cluster task, you can view its execution progress in **<UI-TERM key="ocp-v2.src.hook.useMenuOptions.TaskCenter">Task Center</UI-TERM>**.
