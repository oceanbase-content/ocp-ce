# 外部連携の概要

ユーザーはOAuth2またはOIDCタイプの外部アカウントサービスを設定することで、OCPのホームページへのシングルサインオンを実現できます。

## 背景

シングルサインオン（SSO）とは、ユーザーがその資格情報を用いてOCPに安全に認証できる認証方式です。

## 概念

* OAuth（Open Authorization、オープン認可）は、オープンな標準の認可プロトコルです。ユーザーは、リソースサービス上に保存された自身の保護された情報にアクセスするために第三者アプリケーションに権限を付与できますが、その際にユーザー名やパスワードを第三者アプリケーションに提供する必要はありません。これにより、認証と認可が分離されます。OAuthは国際標準として広く普及し、継続的に採用されています。OAuth2.0はOAuthプロトコルの継続版であり、より安全で実装も容易ですが、OAuth1.0とは互換性がなく、OAuth1.0は完全に廃止されました。OAuth（Open Authorization、オープン認可）は、ユーザーリソースの認可に関する安全でオープンかつ簡単な標準を定義しており、第三者はユーザーのアカウントやパスワードを知ることなく、ユーザーの認可情報を取得できます。

  * OAuth2は、REST/APIsのための委譲認可フレームワーク（delegated authorization framework）です。
  * OAuth2はトークン（Token）に基づく認可方式であり、ユーザーのパスワードを露出させることなく、アプリケーションに対してユーザーデータへの制限付きアクセス権限を付与します。
  * OAuth2は認証と認可を分離します。

* OIDC（OpenID Connect）は、セキュリティ認証メカニズムです。第三者アプリケーションは、アイデンティティプロバイダー（Identify Provider）に接続してユーザー情報を取得し、それらの情報を信頼性のある方法で第三者アプリケーションに返します。OIDCはOAuth2.0プロトコルを拡張し、拡張されたIDトークン（ID Token）フィールドを通じてユーザーの基本的身元情報を提供します。IDトークンはJWT（JSON Web Token）形式で封入され、自己完結性と改ざん防止メカニズムを備えており、第三者アプリケーションへ安全に渡され、容易に検証できます。

## 原理

### OAuth2

OCPは標準のOAuth2認証センターに対応しており、現在は認可コード（authorization-code）モードのみをサポートしています。つまり、アプリケーションは認可コードを使用して認可サーバーからアクセストークン/リフレッシュトークンを申請します。

![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/432/OAuth2.png)

図に示すように、認可プロセスのシナリオは以下の手順で説明できます：

1. ユーザーがアプリケーションシステムにログインし、認証サーバーへのジャンプをリクエストします。そして、302でログイン認証ページに返します。
2. ユーザーが認証情報を入力して認証を行い、認証サーバーが認証に成功すると、codeをアプリケーションシステムに返します。
3. アプリケーションシステムはcodeを持って認証サーバーにアクセストークンと引き換えます。認証サーバーはClient ID、codeなどの情報を確認し、アクセストークンをアプリケーションシステムに送信します。
4. アプリケーションシステムはアクセストークンを持ってユーザーのログイン情報を照会し、認証サーバーはユーザー情報（例：ユーザー名）を返します。
5. アプリケーションシステムがユーザー名を確認し、正しいことを確認した後、セッションを作成し、redirect urlにジャンプします。

### OIDC

![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/432/oidc.png)

1. クライアントは認証サービスに認証リクエストを送信します。
2. ユーザーは認証ページで権限確認を行います。
3. 認証サービスは認証リクエストを検証し、codeをクライアントに返します。
4. クライアントはcodeを含むコールバックインターフェースをビジネスサービスにリクエストします。
5. ビジネスサービスはcode、Client ID、Client Secretを含むリクエストを認証サービスに送信し、Tokenの発行を依頼します。
6. 認証サービスは合法性を検証し、ID Tokenを返します。
7. 認証が成功すると、ビジネスサービスはID Tokenをクライアントに返します。
8. クライアントはID Tokenを含むビジネスリクエストを送信します。
9. ビジネスサービスはID Tokenの合法性を検証し、ビジネス応答を返します。

## ログインシナリオ

* ユーザーがSSOモードを有効にし、ローカルログインモードも有効にした場合、ユーザーのアカウント情報によるログインと第三者ログインがサポートされます。
* ユーザーがSSOモードを有効にし、ローカルログインモードを無効にした場合、第三者のアカウント情報を使用して直接OCPシステムにログインできます（初回ログイン時は第三者の認証ログイン画面にジャンプし、第三者による認証後は、その後のアクセスでは直接ログインできます）。
* ユーザーがSSOモードを有効にしていない場合、ローカルのアカウント情報によるログインのみがサポートされます。

## SSOリストの表示

現在OCPにログインしているユーザーが**ADMIN**ロールまたは**ADMIN_VIEWER**ロールの場合、**SSOリスト**でOCP内のSSO統合の詳細な設定情報を確認できます。これには、設定名、タイプ、作成日時、最終変更日時、作成者、およびローカルログインモードが有効かどうかが含まれます。一般的な運用保守操作もサポートされています。詳細については、[新規SSO統合の作成](200.create-sso-integration.md)、[SSO統合設定の有効化/無効化](300.enable-and-disenable-sso-integration.md)、[SSO統合の編集](400.edit-sso-integration.md)、[SSO統合の削除](500.delete-sso-integration.md)を参照してください。
