# SSO統合の新規作成

OCPにはアカウントシステムが組み込まれています。このページを参照して、OCPで外部統合サービスを設定し、SSOを使用してOCPのホームページにログインすることができます。

## 前提条件

* [外部連携の概要](100.external-integration-overview.md)を参照し、SSOの概念と認可プロセスを理解していること。
* 現在OCPにログインしているユーザーが**ADMIN**ロールであることを確認してください。
* ユーザーが認可サービスをデプロイ済みであること。

## 注意事項

* OAUTH/OIDC連携は、認可コードモードのみをサポートします。
* OAUTH/OIDCでログアウトすると、OCPアプリケーションのログイン状態のみがクリアされ、SSOシステムのログイン状態はクリアされません。

## 設定の説明

### Client Authentication Method

Client Authentication Method（クライアント認証方式）とは、OAuth2、OIDC、またはその他のAPIセキュリティプロトコルにおいて、クライアントアプリケーションが認可サーバーに自己の身元を証明する方法を指します。クライアントのタイプとセキュリティ要件に応じて、適切な認証方式を選択できます。

#### client_secret_basic

* 方法：HTTP Basic認証を使用します。
* 実装：client-idとclient-secretをBase64エンコードし、HTTPリクエストヘッダーのAuthorization: Basic ...に含めます。

#### client_secret_post

* 方法：資格情報をPOSTリクエストボディのパラメータとして送信します。
* 実装：リクエストボディにclient_idとclient_secretパラメータを含めます。

#### client_secret_jwt

* 方法：対称鍵（Client Secret）に基づいて署名されたJWTを使用します。
* 実装：クライアントは、クレームを含むJWTを生成し、client_secretを使用して署名して認証資格情報とします。

#### private_key_jwt

* 方法：非対称鍵（秘密鍵）に基づいて署名されたJWTを使用します。
* 実装：クライアントは自身の秘密鍵を使用してJWTに署名し、認可サーバーは事前に設定された公開鍵を使用して署名を検証します。

#### none

* 方法：クライアント認証を行いません。
* 適用シナリオ：通常、公開クライアント（Public Client、モバイルアプリやSPAアプリなど）で使用されます。これらのアプリケーションはSecretを安全に保存できないため、PKCEプロセスと組み合わせて使用されることが多いです。

### User Info Authentication Method

OAuth2におけるUser Info Authentication Methodとは、クライアントがユーザー情報（User Info）エンドポイントを要求する際に、サーバーに対して自己の身元を証明する方法を指します。一般的な3つの方法は以下の通りです：

#### Query

クライアントの資格情報（例：client_idとclient_secret）をクエリパラメータとしてURLに追加して渡します。

例：

```GET /user_info?access_token=xxx&client_id=abc&client_secret=def```

この方法は推奨されません。URLがログに記録されたりキャッシュされたりする可能性があり、漏洩リスクがあるためです。

#### Header

HTTP Authorizationヘッダーを使用して認証を行います。通常、Base64エンコードされたclient_id:client_secretをBasic Auth情報として使用します。

例：

```Authorization: Basic base64encode(client_id:client_secret)```

この方式は比較的安全ですが、通信プロセスの暗号化（例：HTTPS）を確保する必要があります。

#### Form

リクエストボディ内でフォーム形式でクライアント認証情報を送信します。

例：

```http
POST /user_info
Content-Type: application/x-www-form-urlencoded
client_id=abc&client_secret=def
```

この方式は client_credentials 認可タイプで一般的であり、Content-Type ヘッダーと併用する必要があります。

### ユーザー情報データ構造タイプ

#### FALT

FALT 方式はフラットな構造を示し、ユーザーフィールドが username である場合、以下の返却形式がフラットな構造となります：

```json
{
"username":"xxx"
}
```

#### NESTED

NESTED 方式は入れ子構造を示し、username が userInfo 構造の中に埋め込まれていることを意味します。ユーザー情報データ構造タイプを NESTED に設定した場合、ネストされたユーザーデータを取得する際には userInfo を記入し、その後にユーザー名フィールドを設定する必要があります：

```json
{
    "userInfo":{
        "username":"xxx"
    }
}
```
