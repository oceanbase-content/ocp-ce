* 一部のLinuxディストリビューションにおいて、コンテナ環境情報の取得が不正確であるためにOCPプロセスが頻繁に再起動する問題を修正しました。

## V4.3.1

OCP V4.3.1は、OceanBase V4.3.1バージョンを正式にサポートしています。このバージョンでは、Binlogサービスのインストール・デプロイ、基本的な運用保守、監視・アラートなどの機能を提供し、ユーザーがMySQLの下流エコシステムとシームレスに連携することを支援します。また、Service Nameをサポートすることで、プライマリ/スタンバイテナント間のセッション自動ルーティング切り替え機能を実現し、OceanBase V4.xの高可用性ソリューションをさらに完善しました。さらに、このバージョンはS3プロトコルをサポートするバックアップストレージメディアをサポートしており、ネイティブのAWS S3に加え、Huawei Cloud OBSやGoogle GCSなどのS3プロトコル互換オブジェクトストレージもサポートしています。これにより、国内外の主要なクラウドベンダーのストレージメディアをほぼ網羅し、顧客のマルチクラウドやプライベートクラウド環境におけるバックアップストレージニーズを満たします。

### 新機能

#### OceanBase V4.x対応

* Service Name機能をサポートし、OceanBaseクラスタとテナントの概念を抽象化することで、マルチテナント環境において業務側がデータベース接続文字列を変更することなく、業務の管理とメンテナンスを容易に行えるようにします。また、プライマリ・スタンバイテナント間のセッションを自動ルーティング切り替える機能を実現し、Switchover/Failover時の業務切り替え時間を大幅に短縮できます。

* データバックアップ・リストアがS3プロトコルをサポートし、ネイティブのAWS S3や、S3プロトコルに互換性のあるオブジェクトストレージ（Huawei Cloud OBS、Google GCS、China Mobile Cloud EOSなど）をサポートしています。これにより、国内外の主要なクラウドベンダーのオブジェクトストレージタイプ（Azure Blobを除く）をほぼ網羅しており、ユーザーはより便利にデータのバックアップとリストアを行えるようになり、データの安全性と信頼性が向上します。

### 最適化

**クラスタ管理**：クラスタのローテーションアップグレードシナリオにおいて技術アーキテクチャチェックを追加し、クラスタのデプロイメントスキームが2F1Rの場合、ユーザーにRレプリカをFレプリカに変換するよう促します。

### 主要機能の解説

#### Binlogサービス

Binlogは、MySQLとCanalやFlinkなどの下流エコシステムを接続するための重要なコンポーネントです。OceanBaseはMySQLエコシステムとの統合を図るため、Binlogサービスを提供し、ネイティブのClogをMySQL Binlog形式に変換することで、ユーザーがOceanBaseデータベースにシームレスに接続できるようにします。これにより、既存のデータフローシステムを維持し、既存のインフラを再利用できるため、ユーザーのデータベース移行コストを最大限に削減できます。OCPはBinlogクラスタのデプロイメントやBinlogインスタンスの管理、監視・アラート、パラメータ管理などの機能を提供し、ユーザーのBinlogサービスの管理・メンテナンスコストを大幅に削減し、労働生産性を向上させることができます。

Binlogサービスの制限事項は以下の通りです：

* OBServerバージョンはV4.1.0.1以上が必要です。
* OBProxyバージョンはV4.2.1以上が必要です。V4.3.1.0-402024062810またはV4.2.1.0-20240604114727の使用を推奨します。
* Binlog ServiceバージョンはV4.0.0以上が必要です。
* MetaDBバージョンは2.2.77 (Built Feb 14 2022 18:11:59)以上が必要です。
* MySQLモードのテナントのみをサポートします。

#### サービス名

サービス名は、OceanBaseが提供する新しいデータベースアクセス方式であり、クラスタとテナントのエイリアスと見なすことができます。これにより、アプリケーションは `mysql -hxxx.xxx.xxx.xxx -P2883 -uroot@<Service Name>` の接続文字列を使用してデータベースにアクセスできるようになります。

OceanBase V4.1 の高可用性ソリューションは、テナントレベルのプライマリ/スタンバイデータベースへと変更されました。クラスタレベルではプライマリ/スタンバイの概念がなくなり、クラスタ名は単に一つのクラスタを一意に識別するために使用されます。プライマリ/スタンバイの役割はテナントレベルに移譲され、プライマリテナントとスタンバイテナントが属するクラスタは異なる場合があり、プライマリテナント名とスタンバイテナント名も異なる場合があります。

OCPは、プライマリテナントとスタンバイテナントのサービス名の作成、編集、削除、検証、およびプライマリテナントとスタンバイテナントが属するクラスタへの同一OBProxyクラスタのバインド機能をサポートしています。ユーザーは、プライマリテナントとスタンバイテナントを同一のサービス名に設定することで、プライマリテナントとスタンバイテナントの切り替え時のセッションの自動切り替えを実現できます。同時に、ユーザーはビジネスの具体的なシナリオに応じて、例えば非プライマリ/スタンバイテナントシナリオでサービス名をクラスタ名/テナント名の接続方式に代わって使用する方法や、プライマリ/スタンバイテナントシナリオでプライマリテナントとスタンバイテナントが異なるサービス名を使用する方法を提供するなど、サービス名機能をより便利に利用できるよう支援します。

サービス名の制限事項は以下のとおりです：

* OceanBaseのバージョン要件はV4.2.4.0以上、V4.3.0.0未満です。
* OBProxyのバージョン要件はV4.3.1以上です。
* サービス名は単一のOCPクラスタ（マルチクラスタモードを含む）内で一意である必要があります。

### 修正された問題

OCP V4.3.1バージョンでは、主に以下の問題が修正されました：

* マルチクラスタモードの災害復旧切り替えに関するいくつかの問題が修正されました。
* 非英字・数字の文字を含むテナントパラメータを変更する際に失敗する問題が修正されました。
* `db.table` スタイルのSQLでインデックス情報が表示されない問題が修正されました。
* SQL診断のOceanBase V1.4.79への互換性が最適化されました。

OCP-Serverは物理マシンにインストールできるほか、Dockerコンテナでの稼働もサポートしています。OCP-Serverはマルチノードの高可用性デプロイメントモードをサポートしています。

OCP-Serverノードの最低ハードウェア要件は以下の表のとおりです。

| ハードウェア | 要件                 |
|-------|------------------------------------|
| CPU  | <li>X86_64、8コア</li><li>ARM AArch64アーキテクチャ、8コア</li> |
| メモリ | 利用可能メモリ16 GiB             |
| NIC | 10ギガビットNIC                |
