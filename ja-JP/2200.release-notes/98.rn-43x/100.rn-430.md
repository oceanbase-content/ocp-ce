# OCP V4.3.0

## V4.3.0 BP2

### バージョン情報

* **バージョン番号：** V4.3.0 BP2

* **前回のバージョン：** V4.3.0 BP1

* **リリース日：** 2024年7月12日

### 主な変更点

* 大規模クラスタシナリオ（1,000台以上のホスト）におけるOCPのパフォーマンスを最適化しました。

* OBProxyの一部のバージョン間でアップグレードが失敗する問題に対して、互換性処理を施し、アップグレードの成功を確保しました。ただし、現在も残存するリスクがあるため、ユーザーはOBProxyをアップグレードする前に、テクニカルサポートスタッフとバージョン間の互換性を確認する必要があります。

### バグ修正

* OBProxyアップグレード後の熱再起動失敗問題を修正しました。

* マルチクラスタモードにおけるアラート問題を修正しました。

* 大規模シナリオにおけるOCPのパフォーマンスを最適化しました。

## V4.3.0 BP1

### バージョン情報

* **バージョン番号：** V4.3.0 BP1

* **前回のバージョン：** V4.3.0

* **リリース日：** 2024年6月14日

### 製品の最適化

* **クラスタ管理**

  シングルサイトシナリオにおけるメッセージを最適化しました：シングルマシン（集中型アーキテクチャ）にはデータレプリカが1つしかなく、ストレージまたはハードウェア障害が発生した場合、データ損失のリスクが存在します。重要な業務システムについては、定期的なバックアップの実施や高可用性ソリューションの構成（テナントのプライマリ/スタンバイデータベース、複数レプリカによる災害復旧など）を推奨し、単一障害点のリスクを回避してください。

* **クラスタ管理**

  OceanBaseのバージョンがV4.2.1.7以降（V4.2.2、V4.2.3、V4.3.0は除く）の場合、SLOGログとログディスクは同じストレージ領域を共有します（SLOG用に4GiBのストレージ容量を確保することを推奨します）。

* **<UI-TERM key="ocp-v2.src.hook.useMenu.AlarmCenter">アラートセンター</UI-TERM>**

  テナントのログディスク使用率アラートのしきい値を85%に調整しました（元の値：95%）。

### 不具合の修正

* OCP V4.3.0でログバックアップが有効なV3.x系クラスタに対して即時バックアップを実行する際に、バックアップが失敗する問題を修正しました。

* OceanBase V1.4.79をMetaDBとして使用すると、OCPのアップグレードが失敗する問題を修正しました。

* V3.1.x以前のバージョンのOCPをV4.xにアップグレードした後、自己回復アラートがトリガーされない可能性がある問題を修正しました。

## V4.3.0

OCP V4.3.0は、OceanBase V4.3.0を正式にサポートしています。このバージョンでは、**<UI-TERM key="ocp-v2.Information.Detail.CollectDetails.InformationCollection">情報収集</UI-TERM>**と**<UI-TERM key="ocp-v2.src.hook.useMenu.PlanManagement">緊急対応プラン管理</UI-TERM>**という2つの重要な機能が提供されており、ユーザーが異常シナリオにおける情報収集と自動化処理を支援し、障害診断の効率を向上させるとともに、業務の継続性と安定性を高めます。

さらに、このバージョンではCPUオーバーコミット機能をサポートしており、ユーザーは業務特性に応じてCPUを適切に割り当てることで、リソース利用率を最大限に引き上げることができます。また、3A Timemodelに基づくより細かい待機イベントタイプのモニタリング指標を提供し、システム問題の分析と解決をより効率的に支援します。同時に、OCP V4.3.0は、基本的な運用保守、監視・アラート、バックアップ・リカバリ、サードパーティ統合などの面で20項目以上の最適化と強化を行い、製品の使いやすさ、安定性、開放性を重点的に向上させ、完全なライフサイクルデータベース管理プラットフォームを構築し、ユーザーがより簡単かつ効率的にOceanBaseデータベースを管理できるよう支援します。

### 新機能

#### OceanBase V4.x機能対応

* OCPマルチクラスタモードでテナントレベルのプライマリ/スタンバイデータベースをサポートし、OceanBaseの災害復旧ソリューションを強化しました。
* クラスタレベルおよびテナントレベルのパラメータテンプレート`Complex_OLTP`、`Express_OLTP`、`OLAP`、`HTAP`、`OBKV`に対応し、ビジネスモデルの観点からクラスタおよびテナントのパラメータ設定を簡素化し、データベースを「箱から出してすぐ使える」状態にし、ユーザーの構成コストを削減します。
* OBProxyセッションID方式に対応し、分散環境において特定のセッションを特定できない問題を解決し、外部アプリケーションによるセッション終了をサポートする機能を実装しました。

#### CPUオーバーコミット

通常、クラスタ内の異なるテナント間で業務特性によるピーク時とオフピーク時の差異が生じる場合、例えば`業務A`が午前9時から11時にかけて混雑し、`業務B`の負荷がこの時間帯に低い場合や、`業務A`が午後1時から3時にかけて負荷が低く、`業務B`がこの時間帯に業務が忙しい場合などがあります。そのため、ユーザーはテナントの業務タイプやピーク・オフピーク時間を整理し、クラスタとテナントの仕様を適切に設定することで、業務の安定した運用を保証しつつクラスタのリソース利用率を向上させ、コスト削減と効率向上を実現できます。

### 主要機能の解説

#### CPUオーバーコミット

CPUオーバーコミットとは、OceanBaseクラスタがテナントに割り当て可能な総リソース量が、実際に利用可能な物理リソースを上回ることを許可する仕組みです。クラスタ作成時に、ユーザーはクラスタのCPUオーバーコミット率（最大値：200%）を指定でき、Unit作成時にCPUの最大値と最小値を指定します。また、OCPはユーザーがオンラインでオーバーコミットを無効にしたり、オーバーコミット率を調整したりする機能をサポートしており、ユーザーが実際のビジネス状況に応じてクラスタを管理できるよう支援します。

CPUオーバーコミットの典型的な適用シナリオは以下の通りです：

1. ビジネスの統合：ユーザーは、ピークとデマンドがあるビジネスを同一クラスタに配置できます。例えば、昼間は取引型のビジネスを、夜間はバッチ処理や分析を行うビジネスを混合してデプロイすることができ、ビジネスの混合配置によりクラスタ全体のリソースを最大限活用できます。

2. 突発的なトラフィックへの対応：特定のビジネスで突発的なトラフィックが発生し、そのビジネスが組織にとって重要な場合、当該テナントはオーバーコミットメカニズムを利用して他のテナントのリソースを秒単位で占有し、ビジネスの安定した運用を保証できます。

<main id="notice" type='explain'>
<h4>説明</h4>
CPUオーバーコミット機能は、OceanBaseバージョン4.0以上で、かつクラスタでcgroupが有効になっている場合にのみ使用できます。
</main>

#### プラン管理

プラン管理とは、OceanBaseデータベースで発生する可能性のある緊急事態や危機に対して、一連の緊急対応プランを策定し実施するプロセスを指します。プラン管理は、事前に障害対応計画を構築することを目的としており、ユーザーは緊急事態や危機により適切に対処し、損失を軽減してデータベースの安定稼働を確保することで、潜在的なリスクがユーザーの業務に与える影響を低減し、OceanBaseデータベース全体の緊急対応能力を向上させることができます。

現在のプラン管理モジュールには、2つのモジュールが含まれています：

1. プラン：このモジュールでは、OBServerの自動起動、テナントCPU/メモリの拡張、単一SQLのPlanCacheのリフレッシュなど、11種類のプランを提供しています。ユーザーは、ビジネスシナリオやテナントのリソース使用状況などの実際の状況に合わせて、テンプレートをカスタマイズすることができます。例えば、拡張計画やプランの自動実行の有無などです。

2. プラン実行：このモジュールでは、プランの実行情報、ロールバック計画、対応するSQLの詳細などを提供しています。また、自動起動が有効なテンプレートを無効にした場合、ユーザーが手動で実行することもサポートしています。プラン管理は、ユーザーがOceanBaseデータベースの緊急管理メカニズムと運用規範を確立するのに役立ち、ビジネス継続性と安定性をよりインテリジェントに保証します。

* Agentのメモリリーク問題を修正しました。この問題はagentのメモリ使用量が想定を超える原因となっていました。

## バージョンの使用制限

### ハードウェア要件

OCP-Serverは物理マシンにインストールできるほか、Dockerコンテナ内での稼働もサポートしています。OCP-Serverは、複数ノードによる高可用性デプロイメントモードをサポートしています。

OCP-Serverノードの最低ハードウェア要件は以下の表のとおりです。

| ハードウェア | 要件                 |
|-------|------------------------------------|
| CPU  | <li>x86_64、8コア</li><li>ARM AArch64アーキテクチャ、8コア</li> |
| メモリ | 利用可能メモリ16GiB             |
| NIC | 10ギガビットNIC                |

OCP-Agent自体が消費するリソースは非常に少なく、インストールノードのハードウェアリソースに特別な要件はありません。

### オペレーティングシステム要件

OCPサーバー側（OCP-Agentを含む）のインストールに適したオペレーティングシステムの要件は以下の表のとおりです。

| サーバータイプ    | オペレーティングシステム    | 対応バージョン   |
|-------------|------------|-----------|
| x86_64   | RHEL    | 7.2以降のバージョン |
| x86_64   | CentOS   | 7.2以降のバージョン |
| x86_64   | AliOS   | 7.2以降のバージョン |
| x86_64   | openSUSE  | 12 SP3以降 |
| ARM AArch64 | AliOS   | 7.2以降のバージョン |
| ARM AArch64 | NeoKylin    | 7.6    |
| ARM AArch64 | Huawei EulerOS | 2.0 SP8  |
| x86_64 | Debian    |  Debian GNU/Linux 11 (bullseye)  |
| x86_64 | Ubuntu | Ubuntu 18.04.6 LTS |

### クライアント要件

一般的にユーザーはWebブラウザを通じてOCPサービスにアクセスします。そのため、クライアントに関する要件は以下のとおりです。

| ブラウザ   | 最小バージョン |
|---------|------|
| Chrome | 88  |
| Firefox | 78  |
| Safari | 14  |
| Edge  | 88  |

iOSオペレーティングシステムを搭載したデバイスからOCPにアクセスする場合、バージョン要件は以下の表のとおりです。

| オペレーティングシステム | 最小バージョン |
|------|------|
| iOS | 10  |
