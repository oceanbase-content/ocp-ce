# メジャーコンパクション時刻の収集

## 収集の概要

クラスタのメジャーコンパクション時刻を照会し、現在時刻と比較します。単位はマイクロ秒です。

## 収集の仕組み

OceanBase V4.0.0 より前のバージョン：

```sql
select zone, name, value, time_to_usec(now()) from __all_zone where name = 'merge_start_time';
```

OceanBase V4.0.0 以降のバージョン：

```sql
select tenant_id, time_to_usec(start_time) as start_time, time_to_usec(now()) as now from CDB_OB_MAJOR_COMPACTION;
```

## 対処方法

現在、OCPにはOceanBaseクラスタが長時間メジャーコンパクションをトリガーしていないかどうかを監視するアラートがあります。前回のメジャーコンパクションからの経過時間がしきい値（デフォルトで108000秒）を超えるとアラートが発報されます。同時に、OceanBaseクラスタのRoot Serviceは定期的にフリーズを開始します。長時間フリーズやメジャーコンパクションが発生しない場合、ディスク使用量の増加やディスク満杯などの問題が発生し、業務上の書き込みに影響を与える可能性があります。

1. 日次メジャーコンパクションが有効になっているか確認します。

   パス：クラスタ **<UI-TERM key="ocp-v2.src.hook.useMenu.Overview">概要</UI-TERM>** > **<UI-TERM key="ocp-v2.Detail.Compaction.MergeManagement">メジャーコンパクション管理</UI-TERM>** > **<UI-TERM key="ocp-v2.Detail.Compaction.MergeConfiguration">メジャーコンパクション構成</UI-TERM>** の **<UI-TERM key="ocp-v2.Compaction.Settings.MergePolicy">メジャーコンパクション戦略</UI-TERM>** で **<UI-TERM key="ocp-v2.Compaction.Settings.DailyMergeTime">毎日メジャーコンパクション時間</UI-TERM>** が設定されているか確認します。

   * 設定されていない場合、自動的にフリーズがトリガーされません。手動で有効にする必要があります。
   * 設定されている場合、他の原因が考えられます。次の手順に進んでください。

2. プロセス異常がRoot Serviceサービスの異常を引き起こしていないか確認します。

   observerプロセスに異常がある場合、**ob_cluster_exists_inactive_server OBクラスタに非稼働OBServerノードが存在します** アラートが報告されます。[ob_cluster_exists_inactive_server OBクラスタに非稼働OBServerノードが存在します](../../100.alarm-reference/200.ob-alert/400.ob_cluster_exists_inactive_server.md) を参照して対処してください。処理後、観察が必要です。5分後もアラートが報告され続ける場合、次の手順に進んでください。

3. Root Serviceがリーダー不在の状態になっていないか確認します。

    `sys`テナントで以下のステートメントを実行して `__all_virtual_core_meta_table` を照会し、Root Serviceがリーダー不在の状態になっていないか判断します。

    ```sql
    SELECT svr_ip, zone, role, member_list FROM __all_virtual_core_meta_table;
    ```

    * 接続は正常だが、クエリが失敗した場合、Root Serviceはリーダー不在の状態にあることを意味します。Root Serviceが配置されているOBServerノードを再起動するか、rootservice_list内のすべてのOBServerノードを再起動して復旧できます。

       1. 以下の方法で対応するOBServerノードのIPを見つけます。

          ```sql
          -- sysテナントに接続してクエリを実行します。

          -- Root Serviceが配置されているOBServerノードを照会します。
          SELECT zone, svr_ip, svr_port
          FROM __all_server WHERE with_rootserver=1;

          -- rootservice listを照会する
          -- rootservice_listの形式は';'区切りの文字列で、各部分が1台のOBServerノードを表す
          SELECT DISTINCT `value` AS rootservice_list
          FROM __all_virtual_sys_parameter_stat
          WHERE `name` = 'rootservice_list';
          ```

       2. クラスタの**<UI-TERM key="ocp-v2.Detail.Monitor.Monitor.Overview">総覧</UI-TERM>**ページの**<UI-TERM key="ocp-v2.Component.OBServerList.ObserverList">OBServerリスト</UI-TERM>**にある対応するOBServerノードの**<UI-TERM key="ocp-v2.Instance.Overview.Restart">再起動</UI-TERM>**ボタンをクリックします。

          <main id="notice" type='explain'>
          <h4>説明</h4>
          強制再起動はプロセスを直接終了する方法で再起動します。過半数を維持できない場合、この方法で再起動する必要があります。過半数を維持できない状態でOBServerノードを再起動すると、一部のレプリカでリーダーが不在になる可能性があります。再起動後、システムテナントが正常に接続できるようになるまでに15分ほど待機する必要がある場合があります。ビジネステナントでも同様の状況が発生する可能性があります。
          </main>

          再起動後、または強制再起動後15分経っても回復しない場合は、手順**3**を繰り返してください。

    * リーダーが存在する場合は、他の原因が考えられます。次の手順を実行してください。

4. OBServerノード上のログ情報を収集し、OCPテクニカルサポートに連絡して支援を依頼してください。
