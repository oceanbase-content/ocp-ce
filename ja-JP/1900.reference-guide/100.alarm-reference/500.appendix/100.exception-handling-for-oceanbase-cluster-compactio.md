# OceanBaseクラスタのメジャーコンパクション異常処理

## 異常現象

一般的にOceanBaseクラスタのメジャーコンパクションで異常が発生すると、OCPではOCPコンパクションタイムアウトまたはコンパクションエラーのアラートがトリガーされます。アラート情報は以下の図のようになります：

![Image 404.png](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/p199580.png)

同時に、OceanBaseのログ監視にもコンパクション関連のエラーが表示されます。アラート情報は以下の図のようになります：

![image.png](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/p199581.png)

コンパクション異常アラートを受信した後、管理者は該当するアラート対象のOceanBaseクラスタのsysテナントにログインし、具体的な原因を特定することができます。

### コンパクション異常サーバーの特定

sysテナントにログインした後、`__all_zone` テーブルをクエリしてコンパクション状態を確認し、具体的なコンパクション失敗ゾーンを特定できます。サンプルステートメントは以下のとおりです：

```sql
SELECT * FROM __all_zone WHERE name IN ('merge_status','all_merged_version');
```

クラスタが正常なコンパクション状態にある場合、クエリ結果は以下のようになります：

```sql
mysql> SELECT * FROM __all_zone WHERE name IN ('merge_status','all_merged_version');
+----------------------------+----------------------------+---------+--------------------+-------+---------+
| gmt_create                 | gmt_modified               | zone    | name               | value | info    |
+----------------------------+----------------------------+---------+--------------------+-------+---------+
| 2019-06-24 11:19:00.559234 | 2020-02-18 14:02:28.997661 |         | merge_status       |     1 | MERGING |
| 2019-08-28 13:34:31.182559 | 2020-02-18 08:48:28.447141 | ET15_10 | all_merged_version |   773 |         |
| 2019-08-28 13:34:31.182986 | 2020-02-18 14:02:31.640651 | ET15_10 | merge_status       |     1 | MERGING |
| 2019-08-28 14:37:25.685870 | 2020-02-18 08:40:52.009764 | ET15_11 | all_merged_version |   773 |         |
| 2019-08-28 14:37:25.686322 | 2020-02-18 14:02:31.643109 | ET15_11 | merge_status       |     1 | MERGING |
| 2019-08-28 13:33:17.273600 | 2020-02-18 08:30:00.087549 | ET15_9  | all_merged_version |   773 |         |
| 2019-08-28 13:33:17.273964 | 2020-02-18 14:02:31.645466 | ET15_9  | merge_status       |     1 | MERGING |
+----------------------------+----------------------------+---------+--------------------+-------+---------+
```

クラスタ内のあるゾーンでコンパクション異常が発生した場合、該当ゾーンの `info` 列の値は `TIMEOUT` となります。同時に、現在のコンパクションバージョンが `all_merged_version`（`name` 列の値が `all_merged_version`）であるゾーンの `value` 列の値が773であれば、現在バージョン番号773でコンパクションが進行中であることを示します。

バージョン番号773を以下のSQLステートメントの `WHERE` 条件 `major_version` に代入することで、コンパクション異常サーバーのIPアドレスを特定できます。このクエリ結果の `svr_ip` の値がコンパクション異常サーバーのIPアドレスです。サンプルステートメントは以下のとおりです：

```sql
SELECT zone, svr_ip, major_version, macro_block_count, use_old_macro_block_count
        , merge_start_time, merge_finish_time, merge_process, merge_finish_time - merge_start_time AS cost_time
        , macro_block_count - use_old_macro_block_count AS merge_macro_block_count
        , (macro_block_count - use_old_macro_block_count) / (merge_finish_time - merge_start_time) AS avg_per_sec
FROM __all_virtual_partition_sstable_image_info
WHERE major_version = 773
        AND merge_process <> 100
ORDER BY zone, svr_ip, major_version;
```

## 異常原因の特定

### サーバー異常原因の特定

コンパクション異常サーバーのIPを特定した後、まずSSHでサーバーにログインし、問題がホストのハードウェアまたはソフトウェアによる異常によるものかどうかを調査する必要があります。通常は以下の原因を順に調査することができます：

1. I/O性能が低い。コンパクションI/O待機がタイムアウトした場合、コマンド `iostat -x -k 1` を実行して確認できます。I/O使用率が100%の場合、コンパクションに影響します。

2. ディスクが満杯です。この場合、新しいデータを書き込むことができません。データは /home/admin/oceanbase/log、Clogディレクトリ、コンテナ化されたDockerディレクトリなどに書き込むことができません。コマンド `df -lh` を実行してディスク容量を確認できます。

3. ハードウェア障害。以下のステートメントを実行してハードウェア障害を確認します。戻り値がある場合、ハードウェア異常が存在します：

   ```shell
   dmesg|grep -E "Failed status, reset controller|Controller encountered a fatal error and was reset|Controller encountered a fatal error and was reset"
   ```

   RAIDカードを搭載したマシンの場合、以下のコマンドでチェックすることもできます。戻り値がある場合、RAIDカードに異常があります：

   ```shell
   tbraid log | grep -E "Read Medium ERR|Error"
   tbraid log | grep -E 'host IOs were blocked|I2C 4 cannot find idle bus'
   ```

4. カーネルの問題です。以下のステートメントを実行してカーネルを確認します。`task xxx blocked for more than 120 seconds` のような情報が返された場合は、カーネルのバグが原因でI/O異常が発生していることを示します：

   ```shell
   dmesg |grep blocked
   ```

5. ネットワーク要因です。NICに異常がある場合は、Messageログを確認するか `TSAR` コマンドを実行します。以下に示すような異常が発生した場合は、ネットワーク要因です：

   ```shell
   May 26 04:34:23 db142151114.na62 lldpd[67883]: iface_eth_recv: error while receiving frame on eno1: Network is down
   May 26 04:34:23 db142151114.na62 lldpd[67883]: iface_eth_recv: error while receiving frame on eno2: Network is down
   May 26 04:34:23 db142151114.na62 lldpd[67883]: iface_eth_recv: error while receiving frame on enp7s0f0: Network is down
   May 26 04:34:23 db142151114.na62 lldpd[67883]: iface_eth_recv: error while receiving frame on enp7s0f1: Network is down
   ```

   上記のいずれか一つまたは複数の原因が存在する場合は、当社の運用保守担当者までご連絡いただき、異常の解決をお手伝いします。サーバーの交換が必要な場合は、OBServerノードの交換が必要です。詳細な操作手順については、このマニュアルの **OBServerノード管理** セクションを参照してください。

### 内部異常の原因特定

上記のサーバー自体による異常以外にも、OceanBaseクラスタは稼働中にネットワークジッター、I/Oタイムアウト、パラメータ設定などの原因で内部処理に異常が発生し、それによってマージ異常が引き起こされることがあります。以下の原因を順に調査することができます：

1. 内部マクロブロックの異常。内部マクロブロックの異常は、具体的な異常を起こしているPartitionを特定するためにクエリを実行する必要があります。方法は、特定したマージバージョン番号（この例では前のセクションで特定したバージョン番号773）を以下のSQLに代入することです。ここでは、OceanBaseのバージョンに応じて区別する必要があります：

   ```shell
   (1.x) select * from __all_meta_table where data_version != 773;

   (2.x) select * from __all_virtual_meta_table where data_version != 773;
   ```

   実行結果は、現在マージ異常が発生しているPartitionの情報であり、そのサーバーのIPアドレスやZoneなどの情報が含まれます。

2. パラメータ設定の異常。OceanBaseクラスタには、クラスタのマージを制御するパラメータもあります。設定が異常な場合も、マージの失敗を引き起こす可能性があります。以下のステートメントを実行して、手動マージパラメータが有効になっていないか確認します。有効になっていると、手動マージコマンドを使用してのみマージが可能になります。戻り値が `false` の場合は正常です：

   ```shell
   show parameters like '%enable_manual_merge%';
   ```

   以下のステートメントを実行して、アップグレードパラメータが有効になっていないか確認します。有効になっていると、すべてのマージがブロックされます。戻り値が `false` の場合は正常です：

   ```shell
   show parameters like '%enable_upgrade%';
   ```

## 解決策

上記の二つの異常原因には、それぞれ異なる解決策があります。

### サーバー異常の解決策

* サーバーの間欠的な異常については、この種の異常は一般的に瞬時的なものです。異常が再発しないことを確認した後、まず異常なサーバーに対して

  `STOP SERVER`

  操作を行い、その後OBServerノードを再起動します。詳細な操作手順については、《OBServerノード管理者マニュアル》の **OBServerノード管理** セクションを参照してください。

* サーバーの持続的な異常については、この種の異常は一般的に発生すると継続します。運用保守担当者が障害サーバーをオフラインで修理する必要があります。オフラインにする前に、ユーザーはまず異常なサーバーに対して

  `STOP SERVER`

  操作を行い、その後OBServerノードの交換操作を行います。詳細な操作手順については、《OBServerノード管理者マニュアル》の **OBServerノード管理** セクションを参照してください。

### 内部異常

* 内部マクロブロックの異常については、この種の異常処理方法はサーバーの間欠的な異常と類似しています。まず、異常なサーバーに対して `STOP SERVER` 操作を実行し、その後OBServerノードを再起動する必要があります。詳細な操作手順については、『OBServerノード管理者マニュアル』の **OBServerノード管理** セクションを参照してください。

* パラメータ設定の異常については、この種の異常は通常、`ALTER` 操作を使用して異常なパラメータ設定を正常に修正することで、即座に回復できます。以下に例文を示します：

  ```shell
  ALTER system SET `parameter_name`= 'True';
  ```
