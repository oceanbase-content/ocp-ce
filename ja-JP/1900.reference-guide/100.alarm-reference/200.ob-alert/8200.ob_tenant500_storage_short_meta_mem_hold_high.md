# ob_tenant500_storage_short_meta_mem_hold_high OceanBase テナント500のSTORAGE_SHORT_TERMモジュールのメモリ使用率が高すぎる

## アラートの説明

OceanBase 500テナントでリソース割り当てができない潜在的な問題が存在します。STORAGE_SHORT_TERM_META_CTX_IDモジュールがsystem_memoryの50%に達し、メモリリソースの割り当てを停止します。
sstableは固定長ではないため、個数で計算した結果は正確ではありません。そのため、all_virtual_memory_infoをクエリして監視し、500テナントのメモリの30%を超えた場合にアラートを発報します。

## システムへの影響

TableStoreは固定長配列であるため、テーブル数がハイウォータマーク(56個)を超えると、新しいSSTableを配列に追加できなくなり、それによりMini Mergeが実行できなくなる可能性があります。

## 考えられる原因

* シングルマシンのパーティション数が多すぎます。

  ```sql
  select count(*) from __all_virtual_table_mgr where svr_ip=? and table_type !=0;
  ```

* パーティションレプリカの SSTable が多すぎる可能性があります。原因は以下の通りです：

  * undo_retention の設定時間が長すぎて、単一ノードに過剰な SSTable が保持されています。

  * インデックスが作成されていません。`index_status !=2` はインデックステーブルが作成中であることを示します。インデックスが重要でない場合は、削除してみることができます。

    ```sql
    select * from __all_virtual_table where data_table_id =? and index_status != 2
    ```

    インデックス関連のアラートのトラブルシューティングについては、[OceanBaseクラスタにインデックス失敗のテーブルが存在する場合](500.ob_cluster_exists_index_fail_table.md)を参照してください。

  * インデックス作成によりマルチバージョンを保持する必要があります。

    ```sql
    select * from __all_acquired_snapshot;
    ```

  * undo_retention の値が0ではない場合、つまり保存されているマルチバージョンデータの量が多い場合、SSTableがタイムリーに回収できない可能性があります。

    指定したテナントで実行し、テナントが保存する必要があるマルチバージョンの時間（秒）を確認します：`show variables like 'undo_retention'`。

  * major freeze の頻度が高すぎます。

    major freeze はダンプをトリガーし、`major_freeze_ts` のデータをダンプします。そのため、major freeze が発生するたびに少なくとも1つの mini SSTable が生成されます。`__all_zone` テーブルの `frozen_version` と `last_merged_version` を確認し、数値の差が大きい場合、major freeze によって生成されるバージョンが多すぎることを意味します。毎回の major merge では強制フリーズが行われ、mini SSTableが生成されます。未完了の major バージョンが多すぎ、対応する mini SSTable の数も多い場合、`table_store` がパンクする可能性があります。

  * 書き込み負荷が高すぎて、ダンプが頻繁に発生し、配列がパンクします。

    `__all_virtual_table_mgr` を確認し、`table_store` 内の SSTable の種類を確認します。mini SSTable のデータが多く、かつ `table_size` が0ではない場合があります。

    内部テーブルで MINOR の DAG に積み上がりがないか確認します：`select * from __all_virtual_dag_scheduler where svr_ip =?`

    `observer.log` のキーワード検索でログを調べ、当時の MINOR DAG の数を確認します："dump_dag_status"。

    MINOR DAG の数が多い場合、MINOR スレッド数を増やすことでこの状況を改善できます。

    * [V4.x] `compaction_mid_thread_score`、デフォルト値は0で、バックグラウンドスレッド6個に対応します。
    * [V2.x/V3.x] `minor_merge_concurrency`、デフォルト値は0で、バックグラウンドスレッド10個に対応します。

  * `gc_snapshot_version` が上がらず、テーブルが回収できません。

    ログで "too old"、"update info commit" を検索します。gc_snapshot が上がらない場合、`multi_version_start` が正常に上がらず、SSTable が回収できません。

  * `minor_compact_trigger` の設定が大きすぎて、mini minor がタイムリーに実行されません。

    ```sql
    show parameters like "minor_compact%";
    ```

    `minor_compact_trigger` とは、最新の `freeze_info` 区間内の mini SSTable の数がこの値を超えた場合、自動的に mini minor merge をトリガーし、複数の mini SSTable を1つに統合することを指します。`minor_compact_trigger` の設定が大きすぎると、mini minor のトリガーが遅延する原因となります。

    Mini SSTableを削減する方法：

    1. Mini Minor Merge：最新の`freeze_info`区間にある複数のMini SSTableを1つに統合します(OceanBase V3.1以降では、History Mini Minorがサポートされており、過去の`freeze_info`区間にある複数のMini SSTableを1つに統合できます)。
    2. Major MergeによるMini SSTableの回収。

    Major Mergeの前に、不要なマルチバージョンデータを回収するために、一度`remove_old_table`の回収操作がトリガーされます。

  * 実行中のMinor mergeがあるかどうかを確認します。

    ```SQL
    select * from __all_virtual_sys_task_status;
    ```

    対応するパーティションでMINOR MERGEのtraceが実行されている場合、開始時間を確認し、実行時間が長すぎないかどうかを確認します。また、そのマシンでTraceに基づいて実行状況を確認し、フリーズしていないかどうかを確認します。

    何個のminiが1回のminor mergeをトリガーするかは、デフォルトで2です。この値を大きく設定しすぎると、minor mergeのトリガー時期が遅くなり、さらにデータが大量にインポートされると、SSTableの数がタイムリーに減少しなくなります：

    ```SQL
    show parameters like "minor_compact_trigger";
    ```

## 対処方法

1. V3.2.0以降のバージョンでは、診断用の仮想テーブル`__all_virtual_compaction_diagnose_info`を直接クエリします。

2. Major SSTableの保存個数は構成パラメータ`max_kept_major_version_number`によって決定され、デフォルトは2個です。undo_retentionによる保持やインデックス作成のためのマルチバージョン保持を設定していない場合、デフォルトで2個のMajor SSTableのみが保存されます。クエリステートメント：

   ```SQL
   show parameters like "max_kept_major_version_number";
   ```
