# obproxyd_process_dead OBProxy デーモンが存在しない

## 警報の概要

AgentがOBProxyデーモン(`obproxyd.sh`)の存在を判定し、OCPは1秒ごとにプロセスの存在状態を取得します。プロセスが存在しない場合、この警報がトリガーされます。

## 警報の仕組み

次の表は、この警報の監視ロジックに関連する主要なパラメータを示しています。

| パラメータ | 値 |
|-------|-----------|
| 監視指標 | obproxyd_process_exists。この指標は、obproxyのデーモン`obproxyd.sh`が存在するかどうかを示します。指標値が`1`の場合は存在し、`0`の場合は存在せず、警報がトリガーされます。 |
| 監視式 | ```process_exists{name="obproxyd.sh",obproxy_work_mode!="obSharding",@LABELS}```      |
| 取得指標 | obproxyd_process_exists      |
| 指標ソース | この警報の指標ソースは特殊で、OCP-Agentが以下のLinuxコマンドを実行してOBProxyデーモンの存在を判定します：<br>```ps -ef\|grep -w obproxyd.sh\|grep -v grep\|wc -l``` |
| 取得サイクル | 5秒 |

## ルール情報

|          監視指標           |    デフォルトしきい値    | 持続時間 | 検出サイクル | 解消サイクル |
|-------------------------|------------|------|------|------|
| obproxyd_process_exists | 0   | 30秒  | 10秒 | 5分 |

## 警報情報

|   警報トリガー方式   | 警報レベル | 対象範囲  |
|------------|------|-----|
| 監視指標の式に基づく | 極めて重要   | ホスト |

## 警報テンプレート

* **警報概要**

  * テンプレート：\${alarm_target} ${alarm_name}
  * 例：alarm_template_id=0:obproxy_cluster=obproxy_02-1:host=xxx.xxx.xxx.xxx OBProxy デーモンが存在しない

* **警報詳細**

  * テンプレート：OBProxyクラスタ：\${obproxy_cluster}、ホスト：\${host}、警報：\${alarm_name}。
  * 例：OBProxyクラスタ：obproxy_02、ホスト：xxx.xxx.xxx.xxx、警報：OBProxy デーモンが存在しない。

* **警報回復**

  * テンプレート：警報：${alarm_name}、OBProxy デーモンの生存状態：\${recover_value}
  * サンプル：アラート：OBProxy デーモンが存在しません、OBProxy デーモンの生存状態：1

ここで、${alarm_target} はアラートが発生した対象を表します。形式は obproxy_cluster_id=xx:obproxy_cluster=xx:svr_ip=xx です。obproxy_cluster_id はアラートが発生した OBProxy クラスタの ID、obproxy_cluster はアラートが発生した OBProxy クラスタの名前、svr_ip はアラートが発生した OBProxy マシンの IP です。

## システムへの影響

`obproxyd.sh` プロセスは OBProxy プロセスの状態を監視しており、OBProxy が異常終了した場合、`obproxyd.sh` プロセスは OBProxy プロセスの再起動を試みます。`obproxyd.sh` プロセスに異常が発生した場合、その時点で OBProxy プロセスにも異常が発生していると、OBProxy プロセスが終了した後に再起動される保証はありません。

## 考えられる原因

一般的に以下の三つのシナリオが考えられます：

* ネットワーク通信障害。

* `obproxyd.sh` プロセスが異常停止した場合。

* `obproxyd.sh` プロセスは生存しているが応答なく、ハートビートが報告されない場合。

## **対処方法**

1. OBProxy マシンに障害がないか確認します。

   OBProxy マシンが起動可能かどうか確認します。

   * はいの場合、手順2を実行します。

   * いいえの場合、プロセスが存在しないのは OBProxy マシンの障害が原因です。該当する OBProxy の交換を推奨します。

     方法：該当する OBProxy クラスタに新しい OBProxy を追加し、その後現在障害のある OBProxy を削除します。

2. ssh コマンドを使用して OBProxy マシンにログインし、正常にログインできるか確認します。

   * はいの場合、他の未知の問題が原因である可能性があります。手順3を実行してください。

   * いいえの場合、OBProxy マシンが忙しいため、OBProxy の再起動を推奨します。

     1. **OCP \> OBProxy** を選択し、クラスタリストで障害のある OBProxy が属するクラスタを見つけてクリックします。

     2. OBProxy リストで障害のある OBProxy ホストを見つけ、対応する **<UI-TERM key="ocp-v2.component.TraceTimelineDrawer.Operation">操作</UI-TERM>** 列の **<UI-TERM key="ocp-v2.Detail.Component.RestartObproxyModal.Restart">再起動</UI-TERM>** をクリックします。

     3. 再起動後も接続できない場合、手順3を実行してください。

3. この OBProxy の負荷が高すぎるか、ネットワークが切断されているなどの理由でハートビートが報告されないか確認します。

   プロセスの状態とリソース使用状況を確認するために、以下のコマンドを参照してください。

   ```shell
   # プロセスが生存しているか確認します。生存していない場合、再起動してください。
   ps aux | grep obproxyd

   # CPUやメモリなどのリソース使用量が高すぎると、OBProxyが正常に動作しない可能性があります。
   # OBServerノードのCPUおよびメモリ使用率を確認します。
   top -n 1 -p $(pgrep obproxyd)

   # ディスク（データディスク、ログディスク）の空き容量を確認します。
   df | grep /data

   # OBServerノードのネットワーク接続数を確認します。接続数が0の場合、ネットワーク障害が発生している可能性があります。
   netstat -anp | grep 2883 | wc -l
   ```

   上記の問題がなければ、次の手順に進みます。

4. 他の未知の問題が原因である可能性があります。以下の方法でログ情報を収集し、テクニカルサポートにお問い合わせください。

   1. OBProxyログの収集

      一般的に、OBProxyが生成するERRORログは、OCPでアラート情報として表示されます。まず、OCPのアラートイベントページでOBProxyログアラートが存在するか確認してください。

   2. OSログの収集。`/var/log/messages` ログファイルで `error` キーワードを検索し、システムが返す情報を確認します。
