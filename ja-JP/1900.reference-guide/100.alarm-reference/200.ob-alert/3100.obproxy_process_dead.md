# obproxy_process_dead OBProxyプロセスが存在しない

## アラートの概要

このアラートは、OBProxyホスト上のobproxyプロセスが存在するかどうかを監視し、存在しない場合にアラートを報告します。

## アラートの仕組み

以下の表は、このアラートの監視ロジックに関連する主要なパラメータを示しています。

| パラメータ | 値 |
|-------|-------|
| 監視指標 | obproxy_process_exists。この指標はobproxyプロセスが存在するかどうかを示します。指標値が `1` の場合は存在し、`0` の場合は存在せず、アラートがトリガーされます。   |
| 監視式 | ```process_exists{name="obproxy",@LABELS}```     |
| 取得指標 | obproxy_process_exists   |
| 指標ソース | このアラートの指標ソースはやや特殊で、OCP-Agentが以下のLinuxコマンドを実行してobproxyプロセスが存在するかどうかをチェックします。<br>```ps -ef\|grep -w obproxy\|grep -v grep\|wc -l```  |
| 取得サイクル | 5秒     |

## ルール情報

|      監視指標          | デフォルトしきい値 | 持続時間 | 検出サイクル | 解消サイクル |
|------------------------|------|------|------|------|
| obproxy_process_exists | 0   | 30秒  | 10秒 | 5分 |

## アラート情報

|   アラートトリガー方法   | アラートレベル | 対象範囲  |
|------------|------|-----|
| 監視指標の式に基づく | サービス停止   | ホスト |

## アラートテンプレート

* **アラート概要**

  * テンプレート：\${alarm_target} ${alarm_name}
  * 例：alarm_template_id=0:obproxy_cluster=obproxy_02-1:host=xxx.xxx.xxx.xxx OBProxyプロセスが存在しない

* **アラート詳細**

  * テンプレート：OBProxyクラスタ：\${obproxy_cluster}、ホスト：\${host}、アラート：${alarm_name}。
  * 例：OBProxyクラスタ：obproxy_02、ホスト：xxx.xxx.xxx.xxx、アラート：OBProxyプロセスが存在しない。

* **アラート回復**

  * テンプレート：アラート：${alarm_name}、OBProxyプロセスの生存状態：\${recover_value}
  * サンプル：アラート：OBProxy プロセスが存在しません、OBProxy プロセスの生存状態：1

ここで、${alarm_target} はアラートが発生した対象を表します。形式は obproxy_cluster_id=xx:obproxy_cluster=xx:svr_ip=xx です。obproxy_cluster_id はアラートが発生した OBProxy クラスタの ID、ob_cluster はアラートが発生した OBProxy クラスタの名前、svr_ip はアラートが発生した OBProxy マシンの IP です。

## システムへの影響

OBProxy は OceanBase クラスタのプロキシ層として機能し、OBServer ノードへのアクセスを提供します。OBProxy プロセスが存在しない場合、アプリケーションはデータベースに接続できなくなります。

## 考えられる原因

一般的な原因は以下のとおりです：

* ネットワーク通信障害。

* OBProxy プロセスが異常終了した場合。

* OBProxy プロセスは生存しているものの応答せず、ハートビート信号を送信できない場合。

  ハートビート信号が送信できないのは、通常、メモリ不足、ディスク容量不足、ネットワーク障害、または OBProxy の負荷が高すぎるためです。

## **対処方法**

1. OBProxy マシンに障害が発生していないか確認します。

   OBProxy マシンが起動可能かどうか確認します。

   * はいの場合、手順2に進みます。

   * いいえの場合、プロセスが存在しないのは OBProxy マシンの障害が原因です。その OBProxy を交換することを推奨します。

     方法：その OBProxy クラスタに新しい OBProxy を追加し、次に現在障害が発生している OBProxy を削除します。

2. ssh コマンドを使用して OBProxy マシンにログインし、正常にログインできるか確認します。

   * はいの場合、他の未知の問題が原因である可能性があります。手順3に進みます。

   * いいえの場合、OBProxy マシンが忙しくて応答していない可能性があります。OBProxy を再起動することを推奨します。

     1. **OCP \> OBProxy** を選択し、クラスタリストで障害が発生した OBProxy が属するクラスタを見つけてクリックします。

     2. OBProxy リストで障害が発生した OBProxy ホストを見つけ、対応する **<UI-TERM key="ocp-v2.Component.ZoneList.Restart">再起動</UI-TERM>** をクリックします。

     3. 再起動後も接続できない場合、手順3に進みます。

3. その OBProxy の負荷が高すぎるか、ネットワークが切断されていないか確認します。

   プロセスの状態とリソース使用状況を確認するには、以下のコマンドを参照してください。

   ```shell
   # プロセスが生存しているかどうかを確認します。生存していない場合は、再起動してください。
   ps aux | grep obproxy

   # CPUやメモリなどのリソース使用量が高すぎると、OBProxyが正常に動作しない可能性があります。
   # OBServerノードのCPUおよびメモリ使用率を確認します。
   top -n 1 -p $(pgrep obproxy)

   # ディスク（データディスク、ログディスク）の空き容量を確認します。
   df | grep /data

   # OBServerノードのネットワーク接続数を確認します。接続数が0の場合、ネットワーク障害が発生している可能性があります。
   netstat -anp | grep 2883 | wc -l
   ```

   上記の問題がない場合は、次の手順に進みます。

4. その他の未知の問題が原因である可能性があります。以下の方法でログ情報を収集し、テクニカルサポートにお問い合わせください。

   1. OBProxyログの収集

      一般的に、OBProxyが生成するERRORログは、OCPでアラート情報として表示されます。まず、OCPのアラートイベントページでOBProxyログアラートが存在するか確認してください。

   2. OSログの収集。`/var/log/messages` ログファイルで `error` キーワードを検索し、システムが返す情報を確認します。
