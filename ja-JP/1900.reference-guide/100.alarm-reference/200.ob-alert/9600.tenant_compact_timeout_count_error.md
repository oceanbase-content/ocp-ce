# tenant_compact_timeout_count_error OceanBaseテナントの長期未ダンプパーティション(sstable)数

## アラートの概要

このアラートは、OceanBaseテナントで長期間ダンプされていないパーティション(sstable)の数を検出します。長時間凍結されたまま解放されていないFrozen Memtableが存在する場合、Memtableが正常にダンプまたは解放できないことを示しています。

## アラートの仕組み

Memtableが凍結されると、Frozen Memtableに`END_SCN`が設定されます。この時間は当時のシステム時刻に近い値です。このFrozen Memtableがダンプ完了し、メモリの解放が完了すると、`GV$OB_SSTABLES`ビューでは観察できなくなります。

以下の表は、このアラートの監視ロジックに関連する主要なパラメータを示しています。

| パラメータ | 値 |
|--------------|----------|
| 監視指標 | ob_tenant_compact_timeout_count。この指標はテナントの長期未ダンプパーティション(sstable)数を表し、数がしきい値を超えた場合にアラートがトリガーされます。 |
| 監視式 | `sum(ob_tenant_sstable_compact_timeout_count{@LABELS}) by (@GBLABELS)` |
| 収集指標 | ob_tenant_sstable_compact_timeout_count |
| データソース | SQL収集：```select /*+ MONITOR_AGENT NO_REWRITE READ_CONSISTENCY(WEAK) QUERY_TIMEOUT(20000000) */ a.tenant_id,b.svr_ip,b.svr_port,count(*) as cnt from DBA_OB_TENANTS a join ( select * from GV$OB_SSTABLES where table_type = 'MEMTABLE' and is_active='NO' ) as b on a.tenant_id = b.tenant_id and (TIMESTAMP_TO_SCN(now()) - end_log_scn) > 1800 * 1000 * 1000 * 1000 group by b.tenant_id,b.svr_ip,b.svr_port```<br>このSQLは各クラスタのsysテナントで実行され、単一のsstableのダンプが1800秒を超えた場合に集計されます。 |
| 収集サイクル | 5秒 |

## ルール情報

| 監視指標 | デフォルトしきい値（単位：個） | 持続時間 | 検出サイクル | 解消サイクル |
|------------|-----------------------|------------|-----------|--------------|
| ob_tenant_compact_timeout_count | 0 | 0秒 | 60秒 | 5分 |

## システムへの影響

メモリ上限を超えたり、クローグが正常に回収できずディスク容量が枯渇したりする可能性があります。

## 考えられる原因

* ダンプタスクが積み上がり、ダンプタスクの消費速度が追加速度に追いつかない。
* ダンプタスクの実行に失敗した。
* ダンプは成功したものの、Memtableが解放されない。これは内部ロジックに関連しています。
* パーティションがダンプの条件を満たしていない。例：ダンプ可能なsstableの数が上限に達し、新しいsstableを追加できない。

## 対処方法

* ダンプタスクが積み上がっている場合、以下のコマンドを参照してダンプキュースレッドを追加できます：

    ```sql
    alter system set compaction_high_thread_score = xxx tenant xxx;
    ```

* `V$OB_COMPACTION_DIAGNOSE_INFO`ビューまたは`GV$OB_COMPACTION_DIAGNOSE_INFO`ビューを使用して、テナントにダンプ失敗のレコードが存在するかどうかを確認できます。コマンドは以下のとおりです：

  ```sql
  select * from oceanbase.GV$OB_COMPACTION_DIAGNOSE_INFO where tenant_id = xxx;
  ```
