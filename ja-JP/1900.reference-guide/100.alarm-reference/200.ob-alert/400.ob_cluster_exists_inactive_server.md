# ob_cluster_exists_inactive_server OceanBaseクラスタに非稼働OBServerノードが存在する

## アラートの概要

このアラートは、OceanBaseクラスタ内に非稼働状態のOBServerノードが存在するかどうかを監視し、存在する場合にアラートを報告します。

## アラートの仕組み

次の表は、このアラートの監視ロジックに関連する主要なパラメータを示しています。

| パラメータ | 値 |
|---------|------------|
| 監視指標 | inactive_server_count。この指標は、OceanBaseクラスタ内に非稼働状態のOBServerノードが存在するかどうかを示し、指標値がしきい値を超えた場合にアラートがトリガーされます。 |
| 監視指標式 | ```max(ob_server_num{status="inactive",@LABELS}) by (@GBLABELS)```     |
| 取得指標 | ob_server_num |
| データソース | 内部ビューから取得。取得SQL：<li>OceanBase V4.0未満のバージョン：```select /*+ MONITOR_AGENT READ_CONSISTENCY(WEAK) */ group_concat(svr_ip SEPARATOR ',') as servers, status, count(1) as cnt from __all_server group by status```</li><li>OceanBase V4.0以降のバージョン：```select /* MONITOR_AGENT */ group_concat(svr_ip SEPARATOR ',') as servers, status, count(1) as cnt from DBA_OB_SERVERS group by status```</li> |
| 取得間隔 | 5秒 |

OceanBase内部には、各OBServerノードの状態を判断するハートビートメカニズムがあり、その状態をリアルタイムで`__all_server`テーブルに更新します。すべてのOBServerノードはこのテーブルの情報を取得できます。

## ルール情報

| 監視指標 | デフォルトしきい値 | 持続時間 | 検出サイクル | 解消サイクル |
|-----------------------|------|------|------|------|
| inactive_server_count | 0    | 30秒  | 10秒 | 5分 |

## アラート情報

| アラートトリガー方法 | アラートレベル | 対象範囲 |
|-----------|-------|-------|
| 監視指標式に基づく | サービス停止 | クラスタ |

## アラートテンプレート

* **アラート概要**

  * テンプレート：\${alarm_target} \${alarm_name}
  * サンプル：alarm_template_id=0:ob_cluster=obcluster-1 OceanBaseクラスタに非稼働OBServerノードが存在する

* **アラート詳細**

  * テンプレート：クラスタ：\${ob_cluster_name}、アラート：\${alarm_name}。非稼働OBServerノード数は\${value}個、非稼働OBServerノードのIPアドレスは${server_ips}です。
  * サンプル：クラスタ：obcluster-1、アラート：OceanBaseクラスタに非稼働OBServerノードが存在する。非稼働OBServerノード数は2個、非稼働OBServerノードのIPアドレスは xxx.xxx.xxx.1,xxx.xxx.xxx.2 です。

* **アラート回復**

  * テンプレート：アラート：\${alarm_name}、OceanBaseクラスタの非稼働OBServer数：\${value}
  * サンプル：アラート：OceanBaseクラスタに非稼働OBServerノードが存在します、OceanBaseクラスタの非稼働OBServer数：0

ここで、${alarm_target} はアラートが発生した対象を表します。形式は ob_cluster=xxxxxxx です。ob_cluster はアラートが発生したクラスタ名です。

## システムへの影響

利用可能なOBServerノード数が減少し、クラスタの可用性が低下します。

例えば、3ノードのクラスタで1ノードが異常停止すると、3レプリカが2レプリカになります。その後、さらに1ノードが異常停止すると、そのクラスタは利用不能になります。

## 考えられる原因

一般的に以下の3つの状況が考えられます：

* ネットワーク通信障害。

* OBServerノードの障害またはプロセスの異常停止。

* observerプロセスは生存しているが応答せず、ハートビートを報告できない。

## 解決策

1. そのOBServerノードをまだ使用する必要があるか確認します。

   * 使用する必要がある場合は、次の手順に進み、そのOBServerノードが非稼働になった原因を調査します。

   * 使用しない場合は、そのOBServerノードを直接削除できます。

2. ネットワーク通信障害がないか確認します。

   以下のコマンドを参考に、OBServerノードとリーダーOBServerノード間でネットワーク障害がないか確認します。

   ```shell
   # OBServerノードからリーダーOBServerノードにpingを送信します。xxx.xxx.xxx.1はバックアップストレージホストの例IPです。
   ping xxx.xxx.xxx.1

   # リーダーOBServerノードからOBServerノードにpingを送信します。xxx.xxx.xxx.2はOCPホストの例IPです。
   ping xxx.xxx.xxx.2
   ```

    <main id="notice" type='explain'>
    <h4>説明</h4>
    <p>リーダーOBServerノードのIPは、そのOceanBaseクラスタのsysテナントで以下のステートメントを実行して取得できます。
    <code>select svr_ip,with_rootserver from oceanbase.__all_server;</code></p>
    </main>

   * 連続したデータ送信情報が返された場合、ネットワークは正常であり、他の原因がアラートを引き起こしている可能性があります。

   * 継続的なデータ送信メッセージが返されない場合、ネットワーク障害です。ネットワーク管理者に連絡し、具体的なネットワーク問題を調査してもらってください。ネットワーク管理者がいない場合は、[ネットワーク障害のトラブルシューティング](../500.appendix/300.network-troubleshooting.md) を参照して調査および修復を行ってください。

3. OBServerノードが障害またはプロセス異常で停止していないか確認します。

   [ob_cannot_connected OBサーバー接続不可](../200.ob-alert/100.ob_cannot_connected.md) アラートが報告されていないか確認します。

   * はいの場合、OBServerノードが障害またはプロセス異常です。[ob_cannot_connected OBサーバー接続不可](../200.ob-alert/100.ob_cannot_connected.md) を参照して解決してください。

   * いいえの場合、他の原因が考えられます。次の手順に進んで調査を続けます。

4. observerプロセスは正常だが、ハートビートが報告されていないか確認します。

   OCPの **<UI-TERM key="ocp-v2.Information.Detail.CollectDetails.HostList">ホスト一覧</UI-TERM>** から該当するOBServerノードに移動し、**OCP Agent** タブのプロセスが正常か確認します。

   プロセスは正常だが、そのOBServerノードに依然として接続できない場合、ハートビートが報告されていない可能性があります。ディスクまたはメモリが十分であるか確認することを推奨します。

   ```shell
   #メモリ残量の確認
   free -m

   #OBServerノードディレクトリ（デフォルトは /home/admin）のディスク残量
   df -h
   ```

   * ディスクまたはメモリ不足により、OBServerノードのハートビートが報告されない可能性があります。

     * ディスク不足の場合、ディスクの拡張、不要なログのクリーンアップ、または業務状況に応じたデータ保持日数の削減を行います。

     * メモリ不足の場合、メモリの拡張、または業務負荷に応じたテナント仕様の削減を行います。

   * ディスクとメモリが十分な場合、次の手順に進みます。

5. OCPテクニカルサポートに連絡し、問題の特定を依頼します。
