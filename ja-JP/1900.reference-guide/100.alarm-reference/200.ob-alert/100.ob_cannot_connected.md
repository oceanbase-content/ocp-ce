# ob_cannot_connected OceanBaseサーバーへの接続ができません

## アラートの概要

現在、OCPが管理するOceanBaseクラスタ内に接続できないOBServerノードが存在するかどうかを監視します。

## アラートの仕組み

次の表は、このアラートの監視ロジックに関連する主要なパラメータを示しています。

| パラメータ | 値 |
|-----------|---------------------------------------------|
| 監視指標 | ob_connectable。この指標はOceanBaseサーバーが接続可能かどうかを示します。指標値が`1`の場合、OBServerノードは接続可能です。指標値が`0`の場合、そのOBServerノードは接続できず、アラートがトリガーされます。 |
| 監視式 | ```min(oceanbase_connectivity{@LABELS}) by (@GBLABELS)``` |
| 取得指標 | oceanbase_connectivity |
| 指標ソース | このアラートの指標ソースは特殊で、データベース接続プールを使用してローカルのOBServerノードに接続し、SQLステートメント`select 1;`を実行してOBServerノードが接続可能かどうかを検出し、その結果を取得指標に渡します。 |
| 取得周期 | 5秒 |

## ルール情報

| 監視指標 | デフォルトしきい値 | 持続時間 | 検出周期 | 解消周期 |
|----------------|---------|----------|---------------|--------|
| ob_connectable | 0 | 30秒 | 10秒 | 5分 |

## アラート情報

| アラートのトリガー方法 | アラートレベル | 対象範囲 |
|------------|------|-----|
| 監視指標の式に基づく | サービス停止 | サーバー |

## アラートテンプレート

* **アラートの概要**

  * テンプレート：\${alarm_target} ${alarm_name}
  * 例：alarm_template_id=0:ob_cluster=obcluster-1:host=xxx.xxx.xxx.xxx OceanBaseサーバーへの接続ができません

* **アラートの詳細**

  * テンプレート：クラスタ：\${ob_cluster_name}、ホスト：\${host}、アラート：\${alarm_name}。
  * 例：クラスタ：obcluster-1、ホスト：xxx.xxx.xxx.xxx、アラート：OceanBaseサーバーへの接続ができません。

* **アラートの回復**

  * テンプレート：アラート：${alarm_name}、OBServer接続状態：\${recover_value}
  * サンプル：アラート：OceanBaseサーバーに接続できません、OBServer接続状態：1

ここで、${alarm_target} の形式は `ob_cluster=xxxxxxx:svr_ip=xxxxxx` です。ob_cluster はアラートが発生したクラスタ名です。svr_ip はアラートが発生したクラスタ内の対応するOBServerノードのIPアドレスです。

## システムへの影響

一部ホストのOBServerノードが利用不可となり、一部データレプリカの可用性が低下します。

## 考えられる原因

* observerプロセスが異常終了したり、負荷が高すぎてリクエストに応答できない場合。

* OBServerノードマシンの障害により、OBServerノードがアクセス不能になった場合。

## 解決策

1. OBServerノードマシンに障害がないか確認します。

   OBServerノードマシンが起動できるかどうかを確認します。

   * はいの場合、手順2を実行します。

   * いいえの場合、OBServerノードマシンの障害が原因でOBServerノードがアクセス不能となっています。OBServerノードの交換を推奨します。

2. sshコマンドを使用してOBServerノードマシンにログインし、正常にログインできるか確認します。

   * はいの場合、他の未知の問題が原因である可能性があります。手順3を実行してください。

   * いいえの場合、OBServerノードマシンの負荷が高いため、以下のコマンドを参照してOBServerノードを再起動することを推奨します。

     ```shell
     # adminユーザーでOBServerノードが配置されているマシンにログインします。

     # killを試みます。
     pgrep observer | kill

     # プロセスが終了しない場合、強制的にkillします。
     pgrep observer | kill -9

     # OBServerノードを再起動します。
     cd /home/admin/oceanbase && bin/observer
     ```

     OCPクラスタの **<UI-TERM key="ocp-v2.Detail.Monitor.Monitor.Overview">総覧</UI-TERM>** ページの **<UI-TERM key="ocp-v2.Component.OBServerList.ObserverList">OBServerリスト</UI-TERM>** から再起動タスクを開始することもできます。

     再起動後も接続できない場合、手順3を実行します。

3. そのOBServerノードの負荷が高すぎるか、ネットワークが切断されていないか確認します。

   以下のコマンドを参照して、プロセスの状態とリソース使用状況を確認します。

   ```shell
   # プロセスが生存しているかどうかを確認します。生存していない場合は再起動してください。
   ps aux | grep observer

   # CPU、メモリなどのリソース使用量が高すぎると、OBServerノードが正常に動作できない可能性があります。
   # OBServerノードのCPUおよびメモリ使用率を確認します。
   top -n 1 -p $(pgrep observer)

   # ディスク（データディスク、ログディスク）の空き容量を確認します。
   df | grep /data

   # OBServerノードのネットワーク接続数を確認します。接続数が0の場合、ネットワーク障害が発生している可能性があります。
   netstat -anp | grep 2881 | wc -l
   ```

   上記の問題がなければ、次の手順に進みます。

4. 他の未知の問題が原因である可能性があります。以下の方法でログ情報を収集し、テクニカルサポートにお問い合わせください。

   1. OBServerノードのログを確認する

      一般的に、OBServerノードで生成されたERRORログは、OCPでアラート情報として表示されます。まず、OCPのアラートイベントページでOBログのアラートが存在するかどうかを確認してください。OBServerノードのログは `/home/admin/oceanbase/log` に配置されています。まず、拡張子が `.wf` のファイルを確認してください。この種のファイルにはWARNおよびERRORレベルのログが記録されています。

   2. OSログを確認する。`/var/log/messages` ログファイルで `error` キーワードを検索し、システムが返す情報を確認します。
