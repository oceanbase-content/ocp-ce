# ob_cluster_no_frozen OceanBaseクラスタが長時間凍結されていない

## アラートの概要

このアラートは、OCP内のOceanBaseクラスタが長時間凍結をトリガーしておらず、前回の凍結時刻から閾値（デフォルトで90000秒）を超えた場合に発報します。

## アラートの仕組み

以下の表は、このアラートの監視ロジックに関連する主要なパラメータを示しています。

| パラメータ | 値 |
|-------------|-------------|
| 監視指標 | no_frozen_time。この指標は、クラスタで凍結が実行されていない時間を示し、指標値が閾値を超えるとアラートが発報されます。 |
| 監視式 | ```(max(ob_zone_current_timestamp{name="frozen_time",@LABELS}) by (@GBLABELS) - max(ob_zone_stat{name="frozen_time",@LABELS}) by (@GBLABELS)) / 1000000```      |
| 取得指標 | ob_zone_current_timestamp、ob_zone_stat |
| 指標ソース | 内部ビューから取得。取得SQL：```select /*+ MONITOR_AGENT READ_CONSISTENCY(WEAK) */ zone, name, value, time_to_usec(now()) as current from __all_zone``` |
| 取得サイクル | 5秒 |

## ルール情報

|         監視指標             | デフォルト閾値（単位：秒） | 持続時間 | 検出サイクル | 解消サイクル |
|------------------------------|------------|-------|------|------|
| no_frozen_time               | 90000      | 0秒  | 10秒 | 5分 |

## アラート情報

|   アラートトリガー方式   | アラートレベル | 対象範囲 |
|------------|------|-------|
| 監視指標の式に基づく | 極めて重要   | クラスタ |

## アラートテンプレート

* **アラート概要**

  * テンプレート：\${alarm_target} \${alarm_name}
  * 例：alarm_template_id=0:ob_cluster=obcluster-1 OceanBaseクラスタが長時間凍結されていない

* **アラート詳細**

  * テンプレート：クラスタ：\${ob_cluster_name}、アラート：\${alarm_name}。前回の凍結時刻から \${value_shown} 秒が経過し、${alarm_threshold} 秒を超えています。
  * 例：クラスタ：obcluster-1、アラート：OceanBaseクラスタが長時間凍結されていない。前回の凍結時刻から1時間17分49.496秒が経過し、40秒を超えています。

* **アラート復旧**

  * テンプレート：アラート：${alarm_name}、OceanBaseクラスタの前回の凍結からの間隔：\${value_shown}秒
  * サンプル：アラート：OceanBaseクラスタが長時間凍結されていません、OceanBaseクラスタの前回の凍結からの間隔：70000.0秒

## システムへの影響

長期間凍結またはメジャーコンパクションを実行しない場合、ディスク使用量が増加し、ディスク満杯になってビジネスの書き込みに影響を与えます。

## 考えられる原因

* 日次メジャーコンパクションが無効になっているか、アップグレードモードパラメータが有効になっています。

* Root Serviceサービスが異常に一時停止しています。例えば、リーダーがいない場合や、プロセスが異常に一時停止した場合です。

## 解決策

1. 日次メジャーコンパクションが有効になっているか確認します。OCPの**クラスタ概要 \> コンパクション管理 \> コンパクション設定**ページの**<UI-TERM key="ocp-v2.Compaction.Settings.MergePolicy">メジャーコンパクション戦略</UI-TERM>**で、**<UI-TERM key="ocp-v2.Compaction.Settings.DailyMergeTime">毎日メジャーコンパクション時間</UI-TERM>**が設定されているかどうか確認します。

   * 設定されていない場合、自動凍結はトリガーされません。手動で有効にする必要があります。

   * 設定されている場合、他の原因が考えられます。次の手順に進んでください。

2. プロセスの異常がRoot Serviceサービスの異常を引き起こしていないか確認します。

   observerプロセスが異常な場合、[ob_cluster_exists_inactive_server OBクラスタに非稼働OBServerノードが存在します](../200.ob-alert/400.ob_cluster_exists_inactive_server.md)と同時に報告されます。ドキュメントを参照して処理した後、5分後にアラートがまだ報告されるか観察してください。

3. Root Serviceがリーダーを持たない状態になっていないか確認します。

   以下のステートメントを実行して`__all_virtual_core_meta_table`をクエリし、Root Serviceがリーダーを持たない状態になっていないか判断します。

   ```sql
   -- sysテナントに接続してクエリ
   SELECT svr_ip, zone, role, member_list FROM __all_virtual_core_meta_table;
   ```

   * 接続は正常ですが、クエリが失敗した場合、Root Serviceはリーダーを持たない状態にあることを意味します。

     Root Serviceが配置されているOBServerノードを再起動するか、rootservice_list内のすべてのOBServerノードを再起動して回復を試みることができます。

     1. 以下の方法で対応するOBServerノードのIPを見つけます。

        ```sql
        -- sysテナントに接続してクエリ

        -- Root Serviceが配置されているOBServerノードをクエリ
        SELECT zone, svr_ip, svr_port
        FROM __all_server WHERE with_rootserver=1;

        -- rootservce listをクエリ
        -- rootservice_listの形式は';'区切りの文字列で、各部分が1台のOBServerノードを表します
        SELECT DISTINCT `value` AS rootservice_list
        FROM __all_virtual_sys_parameter_stat
        WHERE `name` = 'rootservice_list';
        ```

     2. クラスタの **<UI-TERM key="ocp-v2.Detail.Monitor.Monitor.Overview">総覧</UI-TERM>** ページの **<UI-TERM key="ocp-v2.Component.OBServerList.ObserverList">OBServerリスト</UI-TERM>** で、該当するOBServerノードの **<UI-TERM key="ocp-v2.src.constant.compute.Restart">再起動</UI-TERM>** ボタンをクリックします。

    <main id="notice" type='explain'>
    <h4>説明</h4>
    <p>強制再起動を選択すると、プロセスを直接終了する方法で再起動します。過半数が揃わない場合には、この方法で再起動する必要があります。過半数が揃わない状態でOBServerノードを再起動すると、一部のレプリカでリーダーが不在になる可能性があります。再起動後は、sysテナントへの接続に15分ほど待機する必要がある場合があり、ビジネステナントでも同様の状況が発生することがあります。</p>
    </main>

     3. 再起動後、または強制再起動後15分経っても回復しない場合は、手順3を実行してください。

   * リーダーが存在する場合は、他の原因が考えられます。手順4を実行してください。

4. OBServerノード上のログ情報を収集し、テクニカルサポートに連絡して分析および解決を依頼してください。
