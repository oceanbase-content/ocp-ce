# tenant_cpu_percent_over_threshold OceanBaseテナントスレッド使用率がしきい値を超えた場合

## アラートの概要

OceanBaseテナントのスレッド使用率がしきい値を超えた場合にこのアラートがトリガーされます。

OceanBaseテナントのスレッド使用率 = テナントが実際に使用しているスレッド数 / 当該テナントが現在のメインゾーン内で所有するユニットのスレッド上限の合計。

## アラートの仕組み

以下の表は、このアラートのモニタリングロジックに関連する主要なパラメータを示しています。

| パラメータ  | 値                     |
|-------|------------------------|
| モニタリング指標   | ob_tenant_thread_percent。この指標はクラスタ内のテナントのスレッド使用率を示し、使用率がしきい値を超えるとアラートがトリガーされます。       |
| モニタリング式 | ```100 * sum(ob_sysstat{stat_id="140006",@LABELS}) by (@GBLABELS) / sum(ob_sysstat{stat_id="140005",@LABELS}) by (@GBLABELS)```<ul><li>統計イベントID 140005：テナントが最大で使用できるスレッド数を集計します。</li><li>統計イベントID 140006：テナントが使用しているスレッド数を集計します。</li></ul>モニタリング式は、「stat_id=140006 の value の合計」と「stat_id=140005 の value の合計」の比率をテナントのスレッド使用率のモニタリング指標値として表します。 |
| 収集指標  | ob_sysstat    |
| 指標ソース  | 内部ビューから収集。収集SQL：<li>OceanBase V4.0未満のバージョン：```select /*+ MONITOR_AGENT READ_CONSISTENCY(WEAK) */ con_id tenant_id, stat_id, value from v$sysstat where stat_id IN (140005, 140006) and (con_id > 1000 or con_id = 1)```</li><li>OceanBase V4.0以降のバージョン：```select /* MONITOR_AGENT */ con_id tenant_id, stat_id, value from v$sysstat where stat_id IN (140005, 140006) and (con_id > 1000 or con_id = 1) and con_id in (select tenant_id from DBA_OB_TENANTS WHERE tenant_type<>'META')```</li>    |
| 収集サイクル  | 5秒     |

## ルール情報

|       モニタリング指標           | デフォルトしきい値（単位：%） | 持続時間 | 検出サイクル | 解消サイクル |
|--------------------------|------------|------|------|------|
| ob_tenant_thread_percent | 80         | 120秒  | 10秒 | 5分 |

|   アラートトリガー方式   | アラートレベル | 対象範囲 |
|------------|------|---------|
| モニタリング指標の式に基づく | 警告   | テナント |

* **アラート概要**

  * テンプレート：\${alarm_target} \${alarm_name}
  * サンプル：alarm_template_id=0:obcluster-1:tenant_name=tenant-1:host=xxx.xxx.xxx.xxx OceanBaseテナントスレッド使用率がしきい値を超えた場合

* **アラート詳細**

  * テンプレート：クラスタ：\${ob_cluster_name}、テナント：\${tenant_name}、アラート：\${alarm_name}。テナントのスレッド使用率 \${value_shown} が \${alarm_threshold} % を超えました。
  * サンプル：クラスタ：obcluster-1、テナント：m****、アラート：OceanBaseテナントスレッド使用率がしきい値を超えた場合。テナントのスレッド使用率 96.0 % が 95.0 % を超えました。

## **システムへの影響**

影響ありません。

## **考えられる原因**

* ビジネスにおいて、大規模なクエリやホットデータが発生しています。

* テナントのリソース計画が実際よりも小さく設定されていたり、ビジネス上予期せぬホットスポットが発生している可能性があります。

## 解決策

1. アプリケーションの負荷が正常かどうか確認します。

   OCPで該当するアラートテナントの**<UI-TERM key="ocp-v2.page.Monitor.PerformanceMonitoring">パフォーマンス監視</UI-TERM>**画面に移動し、**パフォーマンスとSQL**タブの**<UI-TERM key="ocp-v2.src.constant.monitor.TenantThreadUsage">テナントスレッド使用率</UI-TERM>**の折れ線グラフを確認します。グラフ上でアラートが発生した時点のテナントスレッド使用率が、過去の長期間（1～7日間）に比べて急激に増加していないか確認します。

   * 増加している場合は、異常な負荷です。

   * 増加していない場合は、正常な負荷です。

     正常なトラフィックによって負荷が高すぎる場合は、[Unit仕様の管理](../../../700.tenant-functions/1630.manage-unit-specification.md)を参照し、テナントの仕様を引き上げて、より多くのテナントスレッドリソースを割り当ててください。

2. 大規模なクエリやホットトラフィックによって負荷が高すぎる可能性があります。

   以下の異なるシナリオに基づいて、適切な処理を行います。

   * SQL実行において大規模なクエリが存在する

     OCP **<UI-TERM key="ocp-v2.page.Overview.SqlDiagnosis">SQL 診断</UI-TERM>**ページの**TopSQL**タブで、CPU使用率が高すぎるSQLがないか確認します。

     * ある場合は、そのSQLを最適化してください。

     * ない場合は、この原因ではありません。

   * SlowSQLによって負荷が高すぎる。

     OCP **<UI-TERM key="ocp-v2.page.Overview.SqlDiagnosis">SQL 診断</UI-TERM>**ページの**SlowSQL**タブで具体的な診断結果を確認し、テナントのスレッド負荷が高くなる可能性があるか分析します。

     その可能性がある場合は、そのSQLを最適化してください。

   * ホット行によって発生したホットデータが原因で、テナントの特定ノードのCPUが高すぎる場合は、[OceanBaseクラスタのトラフィック制限](../500.appendix/200.limit-the-inbound-traffic-of-the-oceanbase-cluster.md)を参照して、そのテナントのビジネスに対してトラフィックを制限してください。
