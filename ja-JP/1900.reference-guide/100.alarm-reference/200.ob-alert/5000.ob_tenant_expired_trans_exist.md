# ob_tenant_expired_trans_exist OceanBaseテナントにハングしたトランザクションが存在する

## アラートの概要

テナント内にコミット段階で1200秒以上停止しているトランザクションが存在する場合、このアラートがトリガーされます。

## アラートの仕組み

以下の表は、このアラートの監視ロジックに関連する主要なパラメータを示しています。

| パラメータ | 値 |
|-------|------|
| 監視指標 | pending_trans_max_duration_seconds。この指標は、OceanBaseテナント内のトランザクションがコミット段階で停止している時間を示します。その値がしきい値を超えた場合にアラートがトリガーされます。 |
| 監視式 | ```max((collect_time - ctx_create_time)/1000000)```  |
| 収集指標 | collect_time、ctx_create_time |
| データソース | 内部ビューから収集。<ul><li>収集SQL：<ul><li>OceanBaseバージョンがV2.2.7未満の場合：```select /*+ MONITOR_AGENT READ_CONSISTENCY(WEAK) QUERY_TIMEOUT(%d)*/ tenant_id, trans_id, `partition`, floor(unix_timestamp(ctx_create_time) *1000000) as ctx_create_time, session_id, participants, trans_type, part_trans_action, sql_no from __all_virtual_trans_stat where svr_ip = ? and svr_port = ? and is_exiting != 1```</li><li>OceanBaseバージョンがV2.2.7以上、V3.2未満の場合：```select /*+ MONITOR_AGENT READ_CONSISTENCY(WEAK) QUERY_TIMEOUT(%d)*/ a.tenant_id, b.tenant_id as tenant_id_xa, a.trans_id, `partition`, floor(ctx_create_time) as ctx_create_time, session_id, participants, trans_type, part_trans_action, sql_no from (select tenant_id, svr_ip, trans_id, `partition`, unix_timestamp(ctx_create_time) *1000000 as ctx_create_time, session_id, participants, trans_type, part_trans_action, sql_no from __all_virtual_trans_stat where svr_ip = ? and svr_port = ? and is_exiting != 1) a left join __all_virtual_global_transaction b on a.tenant_id = b.tenant_id and a.trans_id = b.trans_id```</li><li>OceanBaseバージョンがV3.2以上の場合：```select /*+ MONITOR_AGENT READ_CONSISTENCY(WEAK) QUERY_TIMEOUT(%d)*/ a.tenant_id, b.tenant_id as tenant_id_xa, a.trans_id, `partition`, floor(ctx_create_time) as ctx_create_time, session_id, participants, trans_type, part_trans_action, sql_no, log_size_byte from (select tenant_id, svr_ip, trans_id,`partition`, unix_timestamp(ctx_create_time) *1000000 as ctx_create_time, session_id, participants, (pending_log_size + flushed_log_size) as log_size_byte, trans_type, part_trans_action, sql_no from __all_virtual_trans_stat where svr_ip = ? and svr_port = ? and is_exiting != 1) a left join __all_virtual_global_transaction b on a.tenant_id = b.tenant_id and a.trans_id = b.trans_id```</li></ul></li><li>ハングしたトランザクションの遅延：```select max((collect_time - ctx_create_time)/1000000) as trans_max_duration_seconds from ob_hist_trans_stat where trans_type != 3 and ctx_trans_state=3```</li></ul>  |
| 収集サイクル | 5秒 |

## システムへの影響

ハングしたトランザクションが発生すると、MemStoreダンプが異常に一時停止し、業務が停止します。

## 考えられる原因

* 一般的には、少数派、ディスク満杯、またはメモリ不足などの要因によってこのアラートが発生します。
* マシンのクロック同期偏差が100msを超えています。

## 解決策

1. 少数派が発生していないか確認します。

   少数派が発生するのは通常、OBServerノードの異常やネットワーク障害が原因であり、同時に[ob_cannot_connected OBサーバー接続不可](../200.ob-alert/100.ob_cannot_connected.md)アラートが報告されます。

   このアラートが報告されている場合は、まずそのアラートのドキュメントに従って対処してください。その後、5分間様子を見て、このセクションで説明しているアラートが解消されたかどうか確認します。

2. ディスク容量が不足していないか確認します。

   ディスク容量が不足している場合、以下のアラートが同時に報告されます。まず、それぞれのアラートの対応ドキュメントに従って問題を解決した後、5分間様子を見て、このセクションで説明しているアラートが解消されたかどうか確認します。

   * [ob_host_data_disk_percent_over_threshold OBホストデータディレクトリのディスク使用率が限度を超えています](../200.ob-alert/3500.ob_host_data_disk_percent_over_threshold.md)

   * [ob_host_log_disk_percent_over_threshold OBホストログディレクトリのディスク使用率が限度を超えています](../200.ob-alert/3600.ob_host_log_disk_percent_over_threshold.md)

   * [ob_host_install_disk_percent_over_threshold OBホストインストールディレクトリのディスク使用率が限度を超えています](../200.ob-alert/3700.ob_host_install_disk_percent_over_threshold.md)

3. メモリが不足していないか確認します。

   メモリが不足している場合、[ob_host_mem_percent_over_threshold OBサーバーのメモリ使用率が限度を超えています](../300.application-alert/300.ob_host_mem_percent_over_threshold.md)アラートが報告される可能性があります。解決方法については、そのアラートの解決策を参照してください。

4. 上記の方法でも問題が解決しない場合は、以下のコマンドを参照してテクニカルサポートにお問い合わせください。

   ```sql
   -- すべてのサーバー情報を確認し、異常なOBServerノードが存在するかどうかを判断します。
   select * from __all_server;

   -- 現在のハングしたトランザクションを確認します。
   SELECT *
   FROM __all_virtual_trans_stat
   WHERE is_exiting !=1 AND part_trans_action > 2 AND ctx_create_time < DATE_SUB(NOW(), INTERVAL 500 SECOND)
   LIMIT 100;
   ```
