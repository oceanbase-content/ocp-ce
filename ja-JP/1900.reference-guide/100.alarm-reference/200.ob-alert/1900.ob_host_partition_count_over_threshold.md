# ob_host_partition_count_over_threshold OceanBaseサーバーのパーティション数がしきい値を超えた

## 前提条件

このアラートは、OceanBase V4.0以下のバージョンにのみ適用されます。

## アラートの説明

OBServerノード上のパーティション数（テナントを区別せず、sysなどの組み込みテナントは除外しない）がしきい値を超えた場合、このアラートがトリガーされます。

## アラートの仕組み

以下の表は、このアラートの監視ロジックに関連する主要なパラメータを示しています。

| パラメータ | 値 |
|-------|-----|
| 監視指標 | partition_count。この指標は、OceanBaseサーバーのパーティション数がしきい値を超えているかどうかを示し、パーティション数がしきい値を超えた場合にアラートがトリガーされます。 |
| 監視式 | ```sum(ob_partition_num{@LABELS}) by (@GBLABELS)```  |
| 取得指標 | ob_partition_num  |
| データソース | 内部ビューから取得します。取得SQL：```select /*+ MONITOR_AGENT READ_CONSISTENCY(WEAK) QUERY_TIMEOUT(100000000) */ tenant_id, 1 as role, case when cnt is null then 0 else cnt end as cnt from (select tenant_id, count(*) as cnt from __all_virtual_partition_info where svr_ip = ? and svr_port = ? group by tenant_id)```  |
| 取得周期 | 5秒  |

## ルール情報

|   監視指標      | デフォルトしきい値  | 持続時間 | 検出周期 | 解消周期 |
|-----------------|-----------|---------|----------|------|
| partition_count | 30000     | 0秒    | 30秒    | 15分 |

## アラート情報

|   アラートトリガー方式   | アラートレベル | 対象範囲  |
|------------|------|-----|
| 監視指標の式に基づく | 重大   | ホスト |

## アラートテンプレート

* **アラート概要**

  * テンプレート：\${alarm_target} ${alarm_name}
  * サンプル：alarm_template_id=0:ob_cluster=obcluster-1:host=xxx.xxx.xxx.xxx OceanBaseサーバーのパーティション数がしきい値を超えた

* **アラート詳細**

  * テンプレート：クラスタ：\${ob_cluster_name}、ホスト：\${host}、アラート：\${alarm_name}。パーティション数 \${value} が \${alarm_threshold} を超えました。
  * サンプル：クラスタ：obcluster-1、ホスト：xxx.xxx.xxx.xxx、OceanBaseサーバーのパーティション数がしきい値を超えた。パーティション数 30001.0 が 30000.0 を超えました。

* **アラートの復旧**

  * テンプレート：アラート：${alarm_name}、OBServerパーティション数：\${value}
  * サンプル：アラート：OceanBaseサーバーのパーティション数が上限を超えました、OBServerパーティション数：28888.0

## システムへの影響

* レプリカ間のハートビートRPCがネットワークリソースを消費します。
* 閾値に達すると、ユーザーによる新規テーブル作成や新規パーティション追加などの操作、および内部のパーティション均等化に影響を与えます。

## 考えられる原因

一般的な原因は以下のとおりです：

* テーブル作成が過剰です。

* 業務でパーティションテーブルの使用が多く、時間順にパーティションが分割され続けているため、パーティション数が増加し続けています。

## 解決策

実際の状況に応じて適切な解決策を選択できます：

* 不要なテナント、データベース、テーブルを削除し、ゴミ箱を空にします。操作完了後、パーティションレプリカ数を削減するには、2回のメジャーコンパクションが必要です。

  1. レプリカ数が最も多いテナントを特定します。

     ```sql
     -- パーティションレプリカ数が最も多い上位10個のテナントを照会する
     SELECT t2.tenant_name, t1.replica_count
     FROM
      (SELECT tenant_id, COUNT(*) AS replica_count
       FROM __all_virtual_partition_info
       GROUP BY tenant_id
       ORDER BY replica_count DESC
       LIMIT 10) t1
     JOIN
      (SELECT tenant_id, tenant_name
       FROM __all_tenant) t2
     ON t1.tenant_id=t2.tenant_id
     ORDER BY replica_count DESC;
     ```

  2. データの削除については、以下のコマンドを参照してください。

     ```sql
     -- テナントの削除
     -- ご注意ください。削除する前に、そのテナントが不要であることを確認してください！
     DROP TENANT IF EXISTS `your tenant name`;

     -- データベースの削除
     DROP DATABASE IF EXISTS `your database name`;

     -- テーブルの削除
     DROP TABLE IF EXISTS `your table name`;

     -- ごみ箱から指定したデータベースを物理的に削除する
     PURGE DATABASE `object_name`;

     -- ごみ箱から指定したテーブルを完全に物理的に削除する
     PURGE TABLE `object_name`;

     -- ごみ箱全体を空にする
     PURGE RECYCLEBIN;

     -- メジャーコンパクションの開始
     ALTER SYSTEM MAJOR FREEZE;
     ```

* ユニットを他のOBServerノードに移行する場合、利用可能なターゲットOBServerノードがない場合は、まずクラスタノードの拡張（OBServerノードの追加）を行う必要があります。クラスタの拡張については、「ユーザーガイド」の「OBServerノードの追加」の章を参照してください。
