# ob_tenant_partition_leader_absent OceanBaseテナントのパーティションがリーダーなし

## アラートの概要

OceanBase V4.0.0 より前のバージョンでは、リーダー不在時の選出にかかる時間はパーティション数に密接に関連しています。そのため、単一マシン上のパーティション数についてはアラートを発報する必要があります。パーティションにリーダーがいない場合、リーダー不在時の選出が実施され、その選出が完了するまで、テナントの当該パーティションテーブルは使用できず、業務に影響を与えます。

## アラートの仕組み

| パラメータ | 値 |
| -------- | ----------- |
| モニタリング指標 | tenant_partition_leader_absent_count。この指標はテナントのパーティションでリーダーが欠けている数を示します。パーティションのリーダー不在数がしきい値を超えた場合にアラートがトリガーされます。 |
| モニタリング式 | ```max(partition_leader_absent_count{@LABELS}) by (@GBLABELS)``` |
| 収集指標 | partition_leader_absent_count |
| 指標ソース | 内部ビューから収集。収集SQL：```SELECT /*+ MONITOR_AGENT QUERY_TIMEOUT(20000000) */ tenant.tenant_id, tenant.tenant_name, IFNULL(stat.cnt, 0) cnt FROM __all_tenant tenant LEFT JOIN (SELECT /*+QUERY_TIMEOUT(20000000)*/ tenant.tenant_id, count(distinct a.table_id,a.partition_id) cnt FROM v$ob_cluster cluster, __all_tenant tenant JOIN __all_virtual_meta_table a ON a.tenant_id=tenant.tenant_id LEFT JOIN __all_virtual_meta_table b ON a.table_id=b.table_id AND a.partition_id=b.partition_id WHERE (cluster.cluster_role='PRIMARY' and b.role=1 or cluster.cluster_role='STANDBY' and b.role=3) and b.tenant_id IS NULL GROUP BY tenant.tenant_id) stat ON stat.tenant_id=tenant.tenant_id``` |
| 収集サイクル | 5秒 |

## ルール情報

|   モニタリング指標      | デフォルトしきい値  | 持続時間 | 検出サイクル | 解消サイクル |
|-----------------|-----------|---------|----------|------|
| tenant_partition_leader_absent_count | 100     | 180秒    | 20秒    | 5分 |

## アラート情報

| アラートトリガー方式 | アラートレベル | 対象範囲 |
| ------------ | ------- | -------- |
| モニタリング指標の式に基づく | 悪質 | テナント |

## アラートテンプレート

* **アラート概要**

  * テンプレート：${alarm_target} ${alarm_name}
  * 例：alarm_template_id=0:ob_cluster=TEST-1:tenant_name=t1 OceanBaseテナントのパーティションがリーダーなし

* **アラート詳細**

  * テンプレート：クラスタ：${ob_cluster_name}、テナント：${tenant_name}、アラート：${alarm_name}。
  * 例：クラスタ：TEST、テナント：t1、アラート：OceanBaseテナントのパーティションがリーダーなし。

* **アラート回復**

  * テンプレート：アラート：${alarm_name}、テナントのリーダー不在パーティション数：\${recover_value}
  * 例：アラート：OceanBaseテナントのパーティションがリーダーなし、テナントのリーダー不在パーティション数：85

## システムへの影響

* sysテナントのテーブル1がリーダーを持たず、OBServerの再起動に失敗し、OBServerにログインできません。
* Rレプリカのリーダー切り替え後、location cacheが更新されず、SQLやトランザクションがタイムアウトするまで4038エラーが発生します。

## 考えられる原因

* memstoreメモリ使用量が上限を超えています。`__all_core_table`が継続的にリーダーを持たないのは、reconfirmがログ再生終了を待つ必要があり、memstoreメモリ使用量が上限を超えているためログ再生が進まないためです。
* クロック偏差が大きすぎて、選出に失敗しています。V4.xバージョンが許容するクロック偏差は2秒で、2秒を超えると選出に失敗します。
* OBServerの状態異常により、テナントのパーティションレプリカが多数派を満たさず、リーダー選出ができません。
* clogのリーダー就任タイムアウトによりリーダー不在となっています。詳細については、[clogのリーダー就任タイムアウトによるリーダー不在](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000207763)を参照してください。
* その他の原因については、[OBServerログにおけるパーティションリーダー不在に関する情報](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000207762)を参照してください。

## 解決策

1. memstoreメモリを増やすことを試みます(memstore_limit_percentage)。
2. クロック偏差を修正します。詳細な操作については、[クロックソースの設定](https://docs.oceanbase.com/oceanbase-database/V4.2.1-configure-clock-source-oceanbase-enterprise-optional)を参照してください。
3. OceanBaseサポートチームにお問い合わせください。
