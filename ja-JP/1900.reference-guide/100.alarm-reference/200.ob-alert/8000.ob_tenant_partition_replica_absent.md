# ob_tenant_partition_replica_absent OceanBaseテナントのパーティションにレプリカが欠けています

## アラートの概要

このアラートは、テナント内でレプリカが不足しているパーティションの数を監視し、その数がしきい値を超えた場合にアラートを発報します。

## アラートの仕組み

| パラメータ | 値 |
| -------- | -------- |
| 監視指標 | tenant_partition_replica_absent_count。このパラメータは、テナント内でレプリカが不足しているパーティションの数を表します。レプリカが不足しているパーティションの数がしきい値を超えた場合にアラートがトリガーされます。  |
| 監視式 | ```max(partition_replica_absent_count{@LABELS}) by (@GBLABELS)``` |
| 取得指標 | partition_replica_absent_count |
| 指標ソース | 内部ビューから取得します。取得SQL：```SELECT /*+ MONITOR_AGENT READ_CONSISTENCY(WEAK) QUERY_TIMEOUT(20000000) */ tenant.tenant_id, tenant.tenant_name, IFNULL(stat.cnt, 0) cnt FROM __all_tenant tenant LEFT JOIN (SELECT table_id>>40 AS tenant_id, COUNT(1) cnt FROM __all_virtual_election_info WHERE member_list NOT LIKE CONCAT(replica_num,'{%') AND SUBSTR(member_list, 1, 1) != '0' GROUP BY tenant_id) stat ON tenant.tenant_id=stat.tenant_id where stat.tenant_id not in (select tenant_id from __all_rootservice_job where job_type='ALTER_TENANT_LOCALITY' and job_status='INPROGRESS')``` |
| 取得サイクル | 5秒 |

## ルール情報

|   監視指標      | デフォルトしきい値  | 持続時間 | 検出サイクル | 解消サイクル |
|-----------------|-----------|---------|----------|------|
| tenant_partition_replica_absent_count | 100     | 180 秒    | 20 秒    | 5 分 |

## アラート情報

| アラートのトリガー方法 | アラートレベル | 対象範囲 |
| ------------ | ------- | ------ |
| 監視指標の式に基づく | 重大 | テナント |

## アラートテンプレート

* **アラート概要**

  * テンプレート：${alarm_target} ${alarm_name}
  * サンプル：alarm_template_id=0:ob_cluster=TEST-1:tenant_name=t1 OceanBaseテナントのパーティションにレプリカが欠けています

* **アラート詳細**

  * テンプレート：クラスタ：${ob_cluster_name}、テナント：${tenant_name}、アラート：${alarm_name}。
  * サンプル：クラスタ：TEST、テナント：t1、アラート：OceanBaseテナントのパーティションにレプリカが欠けています。

* **アラート回復**

  * テンプレート：アラート：${alarm_name}、テナント内でレプリカが不足しているパーティションの数：${recover_value}
  * サンプル：アラート：OceanBaseテナントのパーティションにレプリカが欠けています、テナント内でレプリカが不足しているパーティションの数：85

## システムへの影響

パーティションのレプリカが不足している場合、last_merged_versionを進めることができず、メジャーコンパクションが実行できません。

## 考えられる原因

マシンが永続的にオフラインになり、ターゲットパーティションのレプリカが不足したためです。

## 解決策

1. マシンが永続的にオフラインになると、ターゲットパーティションはメンバーリストから削除されますが、ソースパーティションからのメンバーの追放は行われません。ターゲットパーティションのダンプが完了した後、移行レプリケーション操作を実行して不足しているレプリカを補うことができます。

2. 現在のクラスタにパーティションのレプリカ不足が存在するか確認します：

   ```sql
   select * from __all_virtual_replica_task;
   ```

   対応するzone関連のserverにエントリがある場合、該当するpartitionでロードバランシングタスクを開始する必要があることを意味します。現在ロードバランシングタスクがない場合、仮に現在メジャーコンパクションするターゲットバージョンが25だとすると、metaテーブルで`data_version != 25`のレプリカを確認し、調査範囲を絞り込むことができます。ここでいうmetaテーブルは一連のテーブルを指し、通常は最終レベルのmetaテーブル（__all_meta_table/__all_virtual_meta_table）にdata_versionが反映されていないレプリカがないかを確認します。それがない場合、さらに上位のmetaテーブルを探します。

   1. 2.0未満のバージョンでは、metaテーブルは`__all_virtual_core_meta_table`、`__all_virtual_core_root_table`、`__all_root_table`、`__all_meta_table`を指します。
   2. 2.0以上のバージョンでは、metaテーブルは`__all_virtual_core_meta_table`、`__all_virtual_core_root_table`、`__all_root_table`、`__all_virtual_meta_table`を指します。
   3. `__all_virtual_partition_table`で`data_version != 25`のレプリカを検索します。
   4. RSのマシンでコマンド`grep "replica not merged to version" rootservice.l`を実行します。
