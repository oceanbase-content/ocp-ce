# arbitration_node_connection_with_observer_error Arbitrationノードがobserverに接続できない

## アラートの概要

このアラートは、アービトレーションサービスノードが対応するobserverに接続できないことを示します。

## アラートの仕組み

| 監視式 | `{ログレベル=EDIAG、キーワード=arb active keepalive probe_connectivity、継続時間=0秒、アラートレベル=サービス停止}` |
| 収集指標 | arbitration_log |
| 指標ソース | アービトレーションサービスのログ。例：`/home/admin/oceanbase/log/observer.log`。 |

## システムへの影響

アービトレーションレプリカとフォロワーはネットワークが分離されているため、リーダーがダウンした場合に選出できず、2F1A/4F1Aの高可用性が影響を受ける可能性があります。障害発生時には、システムサービスに直接影響します。

## 考えられる原因

* ハードウェア障害。
* ファイアウォール、iptablesなどの設定障害。
* ルーター、ゲートウェイの設定が通じない。

## 解決方法

1. 故障対象と接続失敗のターゲットを確認します。アラートの詳細に記載されている`address`、`host`、`error_code`およびログ内の`dst="ip:port"`に基づき、具体的なアービトレーションサービスインスタンスと接続できないobserverノードを特定します。ログに`in_blacklist=true`が表示されている場合、そのobserverはアービトレーション側から「新規接続失敗」としてマークされたターゲットであることを意味し、このターゲットノードとリンクを重点的に調査する必要があります。

   ```bash
   grep -n "arb active keepalive probe_connectivity" /home/admin/oceanbase/log/observer.log*
   ```

2. ターゲットobserverプロセスとリスニングポートを確認します。アラートに記載されているターゲットobserverノードにログインし、observerプロセスが正常に実行されていること、およびログ内のターゲットポートがリスニング状態にあることを確認します。observerが終了している、フリーズしている、またはポートがリスニングされていない場合は、まずobserverサービスを復旧する必要があります。

   ```bash
   ps -ef | grep observer
   ss -lntp | grep <アラートログ内のターゲットポート>
   ```

3. アービトレーションノードからobserverノードへのネットワーク接続性を検証します。アービトレーションノード上でログ内の`dst`アドレスとポートに対して接続性テストを実行し、接続失敗の原因を確認します。例えば、機器全体が到達不能、ポートが到達不能、またはリンクのジッターなどです。`ping`が正常だがTCP接続に失敗する場合、通常はファイアウォール、セキュリティグループ、ポートリスニング、またはルーティングポリシーに問題があることを示しています。

   ```bash
   ping <observer_ip>
   nc -vz <observer_ip> <observer_port>
   traceroute <observer_ip>
   ```

4. ホストとネットワーク設定を確認します。アービトレーションノードとobserverノード間のファイアウォール、iptables/nftables、スイッチACL、セキュリティグループ、ルーティング、ゲートウェイ設定を重点的に確認し、アービトレーションノードがobserver RPCポートにアクセスする際に遮断が発生していないかを確認します。同時に、ターゲットobserverノードのバインディングアドレスやRPCポート設定に変更がないかを確認し、サービスは起動済みだがアラートのターゲットアドレスやポートをリスニングしていないという状況を避けます。

5. 復旧後、アラートが解消されているかを検証します。修正後、アービトレーションノードで再度TCP接続性テストを実行し、アービトレーションサービスのログを継続的に観察し、「arb active keepalive probe_connectivity failed」または「blacklisted for new connections」というキーワードがログに再び現れないことを確認します。ログレベルが許す場合、アラートが解消された後にはprobe connect okなどの成功ログが見られるはずです。

   1～2分後もエラーが継続する場合は、両ノードの`observer.log`、ネットワークポリシー設定、リンクプローブ結果をさらに収集し、詳細な分析を続ける必要があります。

   ```bash
   grep -E "probe connect ok|probe_connectivity" /home/admin/oceanbase/log/observer.log*
   ```

6. 必要に応じて、より詳細なサポートを求めます。observerサービスが正常で、ポートのリスニングも正常なのに、アービトレーションノードからobserverノードへのTCPプローブが依然として失敗する場合は、障害発生時の両端の`observer.log`、システムログ、ネットワークポリシー、リンクプローブ結果を収集し、ネットワークまたはシステム管理者に連絡して、ハードウェア障害、スイッチ/ゲートウェイの異常、サブネット間のポリシーによる遮断などの問題をさらに特定することを推奨します。
