# tenant_active_memstore_percent_over_threshold OceanBaseテナントのアクティブMemStore比率がしきい値を超えた場合

## アラートの概要

OceanBaseテナントのアクティブMemStore比率がしきい値を超えると、このアラートがトリガーされます。アクティブメモリの割合 = 使用済みアクティブメモリ (active memstore used) / 凍結をトリガーするしきい値 (major freeze trigger)。

## アラートの仕組み

次の表は、このアラートの監視ロジックに関連する主要なパラメータを示しています。

| パラメータ | 値 |
|-------|---------|
| 監視指標 | active_memstore_percent。この指標はテナントのアクティブMemStore比率を示し、この値がしきい値を超えるとアラートがトリガーされます。 |
| 監視式 | ```100 * sum(ob_sysstat{stat_id="130000",@LABELS}) by (@GBLABELS) / sum(ob_sysstat{stat_id="130002",@LABELS}) by (@GBLABELS)```</br><ul><li>統計イベントID 130000：テナントのアクティブメモリ量を集計します。</li><li>統計イベントID 130002：テナントの凍結をトリガーするしきい値を集計します。</li></ul>監視式は、「stat_id=130000 の value の合計」と「stat_id=130002 の value の合計」の比率をテナントのアクティブメモリ比率として表します。 |
| 収集指標 | ob_sysstat |
| データソース | 内部ビューから収集。収集SQL：<li>OceanBase V4.0未満のバージョン：```select /*+ MONITOR_AGENT READ_CONSISTENCY(WEAK) */ con_id tenant_id, stat_id, value from v$sysstat where stat_id IN (130000, 130002) and (con_id > 1000 or con_id = 1)```</li><li>OceanBase V4.0以降のバージョン：```select /* MONITOR_AGENT */ con_id tenant_id, stat_id, value from v$sysstat where stat_id IN (130000, 130002) and (con_id > 1000 or con_id = 1) and con_id in (select tenant_id from DBA_OB_TENANTS WHERE tenant_type<>'META')```</li>    |
| 収集サイクル | 5秒 |

## ルール情報

|         監視指標        | デフォルトしきい値（単位：%） | 持続時間 | 検出サイクル | 解消サイクル |
|-------------------------|------------|---------|-------|-------|
| active_memstore_percent | 110        | 120秒  | 10秒 | 5分 |

|   アラートトリガー方式   | アラートレベル | 対象範囲 |
|------------------|---------|------|
| 監視指標の式に基づく | 極度   | テナント |

## システムへの影響

このアラートがトリガーされると、OBServerノードのメモリが満杯になる可能性があり、極端な場合は業務の書き込みが停止します。

## 考えられる原因

使用済みアクティブメモリ量がフリーズしきい値を超えると、メジャーコンパクション（compaction）操作がトリガーされ、アクティブメモリがフリーズされてディスクにダンプされ、メモリが解放されます。書き込み速度がダンプ速度を上回ると、アクティブメモリ使用率が上限を超え、ダンプが間に合わず、このアラートがトリガーされます。

## 対処方法

* 業務トラフィックが過大でないか確認します。例：データインポートシナリオ。

  OCPのそのクラスタのテナント画面に移動し、**SQL診断 \> TopSQL** を選択します。**TopSQL**画面で、SQLのテキスト量と実行回数が過大でないか確認します。

  * はい、業務トラフィックが相対的に大きいです。

    [OceanBaseクラスタのトラフィック制限](../500.appendix/200.limit-the-inbound-traffic-of-the-oceanbase-cluster.md) を参照して、そのOceanBaseクラスタのトラフィックを制限します。10分待ってから、OCP上のそのアラートが解消されているか確認します。まだ解消されていない場合は、他の原因が考えられます。

  * いいえ、他の原因によりアラートがトリガーされています。

* ダンプまたはメジャーコンパクションに異常がないか確認します。

  このような異常は通常、OBServerノードの再起動で復旧できます。OBServerノードの再起動については、[OBServerノードの再起動](../../../600.cluster-functions/600.manage-an-observer/200.restart-observer.md) を参照してください。

* ディスク書き込みに問題がないか確認します。

  業務トラフィックが正常であり、OBServerノードを再起動してもダンプやメジャーコンパクションがフリーズする問題が解消されない場合、ディスク書き込みに問題がある可能性があります。例：ディスクが故障している、またはディスク書き込み速度が非常に遅い。

  ディスク障害の場合は、[OceanBaseクラスタのメジャーコンパクション異常処理](../500.appendix/100.exception-handling-for-oceanbase-cluster-compactio.md) を参照して処理してください。
