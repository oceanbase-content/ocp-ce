# ob_cluster_sync_delay_time_too_long OceanBaseクラスタの同期遅延時間が長すぎる

## アラートの概要

<main id="notice" type='explain'>
<h4>説明</h4>
<p>このアラートは、OceanBaseデータベースのバージョン4.0.0.0未満のクラスタにのみ適用されます。</p>
</main>

プライマリデータベースとスタンバイデータベースの間ではredoログが同期され、プライマリクラスタとスタンバイクラスタのデータ一貫性を保ちます。非同期ログ転送モードでは、プライマリクラスタとスタンバイクラスタ間のログ転送はリアルタイムではないため、スタンバイクラスタでのログ同期には一定の遅延が生じる可能性があります。通常、この遅延は10分を超えませんが、10分を超えた場合にこのアラートがトリガーされます。

## アラートの仕組み

次の表は、このアラートの監視ロジックに関連する主要なパラメータを示しています。

|     パラメータ     |       値    |
|------------|---------------|
| 監視指標    | sync_delay_time、この指標はOceanBaseプライマリ/スタンバイクラスタの遅延時間を示し、遅延時間がしきい値を超えた場合にアラートをトリガーします。      |
| 監視式  | ```max(sync_delay_time{@LABELS}) by (@GBLABELS)```    |
| 取得指標    | sync_delay_time     |
| データソース    | OCP-Serverが内部テーブル`v$OB_CLUSTER`のCURRENT_SCNフィールドの値を取得します。</br>OceanBaseクラスタ作成後1時間経過し、かつプライマリデータベースにシステムテナントのみでなく通常テナントが存在する場合に取得を開始します。CURRENT_SCNフィールドはプライマリ/スタンバイデータベースが一致した時点を示し、現在時刻からこのフィールドの値を引くことで同期遅延時間を表します。 |
| 取得周期    | 5秒    |

## ルール情報

|   監視指標      | デフォルトしきい値（単位：秒） | 持続時間 | 検出周期 | 解消周期 |
|-----------------|------------|------|------|------|
| sync_delay_time | 600秒      | 0秒  | 15秒 | 5分 |

## アラート情報

|   アラートトリガー方式   | アラートレベル |  対象範囲   |
|------------|------|-------|
| 監視指標の式に基づく | 警告   | クラスタ |

## アラートテンプレート

* **アラート概要**

  * テンプレート：\${alarm_target} \${alarm_name}
  * サンプル：alarm_template_id=0:ob_cluster=obcluster-1 OceanBaseクラスタの同期遅延時間が長すぎる

* **アラート詳細**

  * テンプレート：クラスタ：\${ob_cluster_name}、アラート：\${alarm_name} ログ転送遅延 \${value_shown} 秒が ${alarm_threshold} 秒を超えました。
  * サンプル：クラスタ：obcluster-1、アラート：OceanBaseクラスタの同期遅延が長すぎます。ログ転送遅延3994.293秒が600.0秒を超えています。

* **アラートの復旧**

  * テンプレート：アラート：${alarm_name}、OceanBaseプライマリ/スタンバイクラスタの転送遅延：\${value_shown}
  * サンプル：アラート：OceanBaseクラスタの同期遅延が長すぎます。OceanBaseプライマリ/スタンバイクラスタの転送遅延：566.0秒

ここで、${alarm_target} の形式は ob_cluster=xxxxxxx です。ob_cluster はアラートが発生したクラスタ名です。

## システムへの影響

スタンバイクラスタの遅延が大きすぎると、データの不整合が生じ、結果としてプライマリ/スタンバイ切り替えが正常に行われない可能性があります。

## 考えられる原因

* プライマリ/スタンバイクラスタ間のネットワーク障害。

* スタンバイクラスタの負荷が高すぎるかリソース不足。

* プライマリ/スタンバイクラスタに異常なサーバーが存在する。

* プライマリクラスタが利用不可。

* スタンバイクラスタに異常な一時停止状態の同期テナントタスクが存在する。

## 解決策

以下の手順を参照して、アラートがトリガーされた具体的な原因を特定し、その原因に対処してアラートを解消します。

1. 以下のコマンドを実行して、プライマリ/スタンバイクラスタの同期遅延が依然として大きいかどうか確認します。

   ```sql
   use oceanbase;
   select (time_to_usec(now(6)) - current_scn)/1000000 from v$ob_cluster;
   ```

   クエリ結果が600未満の場合、遅延は正常であり、手動でアラートを解消できます。

   クエリ結果が600を超える場合、遅延は依然として大きいため、次の手順に進みます。

2. アラートがトリガーされた原因を確認し、障害を除去します。

   * `ping` コマンドを使用して、プライマリ/スタンバイクラスタ間のネットワーク障害がないか確認します。

   * スタンバイクラスタの負荷が高すぎるかリソース不足がないか確認します。

     負荷が高すぎるかリソース不足の場合、このアラート以外にも他のアラートがトリガーされます。該当するアラートの説明を参考に、障害を解消してください。

   * プライマリ/スタンバイクラスタのサーバーが正常に動作しているか確認します。

     プライマリクラスタとスタンバイクラスタにそれぞれログインし、以下のステートメントを実行して、起動していないサーバーが存在しないか確認します。

     ```sql
     SELECT * FROM __all_server WHERE start_service_time <=0;
     ```

     サーバーが起動していない場合は、それらのサーバーを再起動します。

   * プライマリクラスタへの接続が可能かどうか、DDL文およびDML文が正常に実行できるかどうかを確認します。

     異常がある場合は、テクニカルサポートに連絡し、プライマリクラスタの異常原因を特定して復旧してもらいます。

   * スタンバイクラスタで一般テナントの同期に異常がないかどうかを確認します。

     スタンバイクラスタにログインし、以下のステートメントを実行して、状態異常なテナントが存在するかどうかを確認します。

     ```sql
     SELECT TENANT_ID,USEC_TO_TIME(REFRESHED_SCHEMA_VERSION),DDL_LAG,USEC_TO_TIME(MIN_SYS_TABLE_SCN),USEC_TO_TIME(MIN_USER_TABLE_SCN)
     FROM V$OB_CLUSTER_STATS;
     ```

     状態異常なテナントがある場合は、これらのテナントの同期タスクが一時停止した原因を特定する必要があります。

   * スタンバイクラスタでシステムテナントの同期に異常がないかどうかを確認します。

     1. プライマリクラスタとスタンバイクラスタにそれぞれログインし、以下のSQLを実行して、両クラスタのテナントの差異を比較し、そのテナントを記録します。

        ```sql
        select * from __all_tenant;
        ```

     2. プライマリクラスタにログインし、以下のSQLを実行して、該当テナントのDDL実行時間を確認し、その時間を記録します。

        ```sql
        select * from __all_ddl_operation where ddl_stmt_str !='';
        ```

     3. 以下のコマンドを実行して、該当時間帯にfreeze操作が行われていないかどうかを確認します。freeze操作は循環依存問題を引き起こす可能性があります。

        ```sql
        select * from __all_core_table where table_name like "%freeze%"
        ```

        freeze操作があった場合は、スタンバイクラスタを削除して再構築する必要があります。
