# monitor_exporter_unavaliable サーバーのモニタリングデータ収集に異常が検出されました

## アラートの概要

このアラートは、exporterの収集状態を監視するために使用されます。モニタリングメトリクスmonitor_exporter_avaliableの値が0（利用不可）のまま、その状態の継続時間が所定のしきい値に達した場合にトリガーされます。

一般的なexporterの種類（ホストに実際にデプロイされているサービスによって決定）は以下のとおりです：

* OBServerモニタリング：`/metrics/node/ob`、`/metrics/ob/basic`、`/metrics/ob/extra`
* OBProxyモニタリング：`/metrics/node/obproxy`、`/metrics/obproxy`
* ホストモニタリング：`/metrics/node/host`
* Agent自己モニタリング：`:62888/metrics/stat`、`:62889/metrics/stat`
* Binlog/LogProxyモニタリング：`/metrics/logproxy`、`/metrics/node/logproxy`

例：

* ホストにOBServerとOBProxyが同時にデプロイされている場合、通常は上記の最初の4種類のexporterが存在します。
* ホストにBinlogサービスもデプロイされている場合、LogProxy関連のexporterが追加されます。

## アラートの仕組み

ocp_metaテナントの`ocp_exporter_address`テーブルには、各exporterの情報が記録されています。exporterのステータス（statusフィールド）がinactiveの場合、モニタリングデータが収集できない可能性があり、注意が必要です。

次の表は、このアラートの監視ロジックに関わる主要なパラメータを示しています。

| パラメータ | 値 |
| ---------- | ---------------------------------------------------------------------------------------------------------- |
| モニタリングメトリクス | monitor_exporter_avaliable。このメトリクスはexporterのステータスが利用可能かどうかを示します。メトリクス値が`1`の場合は利用可能、メトリクス値が`0`の場合は利用不可で、アラートがトリガーされます。 |
| モニタリング式 | ```min(monitor_exporter_avaliable{@LABELS}) by (@GBLABELS)``` |
| 収集メトリクス | monitor_exporter_avaliable |
| メトリクスソース | OCP-ServerがMetaDBからメモリ内のexporterのステータスを収集します。`ocp_exporter_address`テーブルのステータスには一定の遅延があることに注意してください。 |
| 収集サイクル | 5秒 |

## ルール情報

| モニタリングメトリクス | デフォルトしきい値 | 持続時間 | 検出サイクル | 解消サイクル |
| -------------------------- | -------- | -------- | -------- | -------- |
| monitor_exporter_avaliable | 0 | 300秒 | 15秒 | 5分 |

## アラート情報

| アラートのトリガー方法         | アラートレベル | 適用範囲   |
| -------------------- | -------- | ------ |
| モニタリング指標の式に基づく | 警告     | ホスト |

## アラートテンプレート

アラートがトリガーされた際のメッセージ通知について、以下の点にご注意ください：

* 同一ホスト内に複数の異常なエクスポーターが存在する場合、システムはデフォルトでホスト単位に統合して1件のアラートとして表示します。この統合機能を無効にするには、OCPシステムパラメータocp.alarm.exporter.host-merge.enabledを使用します。
* 統合後のアラート詳細には、そのホスト内の異常なエクスポーターリスト、異常開始時刻、最終アラート時刻が動的に表示されます。

* **アラート概要**

  * テンプレート：\${alarm_target} ${alarm_name}
  * サンプル：alarm_template_id=0:host=xxx.xxx.xxx.xxx:exporter=/metrics/obproxy サーバーにモニタリング収集異常が検出されました

* **アラート詳細**（未統合、単一エクスポーターアラートシナリオ）

  * テンプレート：ホスト：\${host}、アラート：モニタリングエクスポーター \${exporter_addr}（タイプ：\${exporter_type}、収集間隔：${scrape_interval}秒）が異常です。
  * サンプル：ホスト：xxx.xxx.xxx.xxx、アラート：モニタリングエクスポーター <http://xxx.xxx.xxx.xxx:62889/metrics/ob/basic>（タイプ：OB_CLUSTER、収集間隔：1>秒）が異常です。

* **アラート詳細**（ホスト単位で統合された場合、システムが動的に生成）

  * テンプレート：
    * ホスト：\${host}、アラート：このホストには \${exporter_count} 個のモニタリングエクスポーター異常があります。
    * 詳細：
      * \${exporter_addr}、異常開始時刻：\${exporter_start_time}、最終アラート時刻：\${exporter_last_time}
      * \${exporter_addr}、異常開始時刻：\${exporter_start_time}、最終アラート時刻：\${exporter_last_time}
      * \${exporter_addr}、異常開始時刻：\${exporter_start_time}、最終アラート時刻：\${exporter_last_time}

  * サンプル：
    * ホスト：xxx.xxx.xxx.xxx、アラート：このホストには3個のモニタリングエクスポーター異常があります。
    * 詳細：
      * http://xxx.xxx.xxx.xxx:62889/metrics/ob/basic、異常開始時刻：2026-03-30 10:00:00、最終アラート時刻：2026-03-30 10:05:00
      * http://xxx.xxx.xxx.xxx:62889/metrics/obproxy、異常開始時刻：2026-03-30 10:01:00、最終アラート時刻：2026-03-30 10:05:00
      * http://xxx.xxx.xxx.xxx:62889/metrics/logproxy、異常開始時刻：2026-03-30 10:02:00、最終アラート時刻：2026-03-30 10:05:00

* **アラート回復**

  * テンプレート：アラート：${alarm_name}、モニタリングエクスポーターの状態：\${recover_value}
  * サンプル：アラート：サーバーにモニタリング収集異常が検出されました、モニタリングエクスポーターの状態：1

ここで、${alarm_target} はアラート対象です：

* 統合有効（デフォルト）：ホスト単位で集約され、形式は `alarm_template_id=0:host=<ip>` となります。
* 統合無効：単一エクスポーターのトリガーによるもので、形式は `alarm_template_id=0:host=<ip>:exporter=<path>` となります。

## システムへの影響

OCPのインターフェースには対応する監視データがなく、システムの実行状況をリアルタイムで確認することができません。また、監視関連のアラートも正常に報告されません。

## 考えられる原因

* 監視収集プログラムOCP-Agentに異常が発生し、監視データを返していません。

* ネットワークが接続されておらず、OCPが監視アドレスにアクセスできません。

## 解決策

ocp_exporter_addressテーブルはエクスポーターの状態を記録していますが、その状態更新には遅延が生じる可能性があります。状態がinactiveに変更されると、OCPはエクスポーターの収集を減らすため、偶発的なエクスポーターの状態は即座にocp_exporter_addressのエクスポーター状態に更新されない場合があります。

1. 障害が発生したマシンでunix-socketインターフェースにリクエストを送信し、エクスポーターへのアクセス可能性を確認できます。

   ```shell
   sudo curl -s --unix-socket /home/admin/ocp_agent/run/ocp_monagent.$(cat /home/admin/ocp_agent/run/ocp_monagent.pid).sock http://unix-socket-server/metrics/ob/basic
   ```

2. OCPから障害が発生したマシンへのネットワークに問題がないか確認します。OCPマシンで以下のコマンドを実行し、監視収集アドレスのエクスポーターにアクセスできるか確認します。

   ```shell
   curl http://xxx.xxx.xxx.xxx:62889/metrics/ob/basic
   ```

   * アクセスできない場合、ネットワーク問題の可能性があります。

     [ネットワーク障害のトラブルシューティング](../500.appendix/300.network-troubleshooting.md) を参照し、ネットワークに障害がないか自己診断し、OCPと該当マシン間のネットワークが接続されていることを確認してください。

   * アクセスできる場合、収集プロセスであるOCP-Agentに障害が発生しています。

     [OCP-Agent運用スクリプト](../../../850.host-features/100.manage-a-host/900.ocp-agent-o-m-scripts.md) を参照し、トラブルシューティングおよび解決を行ってください。
