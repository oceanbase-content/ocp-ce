# message_log_alarm システムメッセージログ

## アラートの概要

このアラートは、ホスト上のシステムメッセージログ（通常はLinuxの`/var/log/messages`またはジャーナル内のカーネル/システムメッセージ）を監視するために使用されます。デフォルトのルールでは、ログにNVMeタイムアウト関連のカーネルメッセージ（例：`kernel: nvme.*timeout`）がマッチした場合にトリガーされ、管理者に対してホストにNVMeディスクまたはドライバーの異常が存在する可能性があることを示します。

## アラートの仕組み

| パラメータ | 値 |
| -------- | -------- |
| 監視指標 | host_message_log / os_message_log（ログ型） |
| 監視式 | `{"excludeKeywords":{"relation":"Or","keywords":[]},"includeKeywords":{"relation":"Or","keywords":["kernel: nvme.*timeout"]},"logLevels":[],"metric":"os_message_log"}` |
| 取得指標 | システムメッセージログ（server_typeはkern / os_message_logに対応） |
| 指標ソース | OCP-Agentがホストのシステム/カーネルログを収集 |
| 取得サイクル | 無し、ログ生成時に評価。 |

このアラートはログ型（Log）アラートであり、ホスト側でログ収集とアラートフィルタリングが完了します。プロセスの概要は以下の通りです：

1. ログ収集：OCP-Agentはホスト上でシステムメッセージログ（例：`/var/log/messages`やジャーナルなど）を収集し、各ログに対応するserver_type（例：os_message_logに対応するkern）やfilenameなどのタグを付加します。

2. アラートフィルタリング：OCPから配信されるアラートルールにはmessage_log_alarmのLog式が含まれており、デフォルト設定は`metric: "os_message_log"`、`includeKeywords: ["kernel: nvme.*timeout"]`、`logLevels: []`（ログレベルでのフィルタリングなし）です。

3. マッチすればアラート：特定のシステムログの内容がキーワード（デフォルトではNVMeタイムアウト関連）と一致すると、アラートを構築してOCPに報告します。アラートタイプはmessage_log_alarmで、クラスタ、ホスト、ログタイプ、ファイル名、キーワード、エラーコード、ログ内容などのタグを含みます。

デフォルトルール：指定したキーワードを含むかどうかでのみ照合し、ログレベルは制限されません。デフォルトのキーワードは正規表現`*kernel: nvme.timeout`で、カーネル出力のNVMeタイムアウト関連メッセージを識別するために使用されます。

## アラートテンプレート

* **アラート概要**

  * **テンプレート**：${alarm_target} ${alarm_name}
  * **例**：ob_cluster=obcluster1:host=xxx.xxx.xxx.xxx システムメッセージログ

* **アラートの詳細**

  * **テンプレート**：[${alarm_name}] クラスタ：${ob_cluster_name}、ホスト：${host}、ログタイプ：${server_type}、ログファイル：${filename}、ログレベル：${log_level}、キーワード=${keyword}、エラーコード=${error_code}、ログの詳細=${error_message}。
  * **例**：[システムメッセージログ] クラスタ：obcluster1、ホスト：xxx.xxx.xxx.xxx、ログタイプ：kern、ログファイル：/var/log/messages、ログレベル：、キーワード=kernel: nvme.*timeout、エラーコード=、ログの詳細=kernel: nvme0n1: I/O 0xffff... timeout。

* **アラートの回復**

  * **テンプレート**：アラート：${alarm_name}、システムメッセージログ ${value_shown}
  * **例**：アラート：システムメッセージログ、システムメッセージログ 回復済み

## システムへの影響

システムメッセージにNVMeタイムアウト関連のログが表示される場合、通常は以下のことを意味します：

* **NVMeデバイスまたはリンクの異常**：ディスクまたはコントローラーの応答がタイムアウトし、I/O遅延の増加、タイムアウトエラー、またはディスクの認識喪失を引き起こす可能性があります。
* **ストレージの安定性リスク**：継続的に発生する場合、ディスクの認識喪失、RAIDの縮退、またはデータ利用不能に発展する可能性があります。
* **データベースへの影響**：OceanBaseのデータやログがそのNVMe上に配置されている場合、インスタンスのフリーズ、ログ書き込み失敗、またはダウンを引き起こす可能性があります。

## 考えられる原因

1. NVMeディスクの故障またはPCIeリンクの不安定。
2. ホストの負荷やI/O圧力が高すぎるために偶発的なタイムアウトが発生しています。

## 解決策

1. **アラート内容の確認**：アラートに記載されているホスト、filename、keyword、error_messageから、具体的なホストとログ行（例：`/var/log/messages`またはjournal）を特定します。

2. **ホストのシステムログの確認**：アラートが発生したホストにログインし、システム/カーネルログ内のNVMe関連のレコードを確認します。

   ```bash
   grep -i nvme /var/log/messages
   # または
   journalctl -k | grep -i nvme
   dmesg | grep -i nvme
   ```

3. **関連デバイスの確認**：ログからタイムアウトに対応するデバイス名（例：nvme0n1、nvme1n1）を確認し、ブロックデバイスとマウントポイントを確認します。

   ```bash
   lsblk
   nvme list
   ```

4. **ハードウェアとドライバの調査**：該当NVMeデバイスの状態をチェックします。

5. **業務とストレージの分離**：問題のあるディスクであることが確認された場合、業務が許す範囲でOceanBaseのデータ/ログを他のディスクに移行するか、そのディスクを交換またはオフラインにしてから、アラートが消えるかどうか観察します。

6. （オプション）**ルールの調整**：他のシステムメッセージ内容を監視する必要がある場合は、OCPアラートルールでmessage_log_alarmのincludeKeywordsまたはexcludeKeywordsを変更できます。一部のNVMe関連アラートを無視する必要がある場合は、除外キーワードを追加できます。

7. **検証**：問題が解消され、一致するログが生成されなくなった後、アラートは解消サイクル（5分）内に自動的にクリアされます。
