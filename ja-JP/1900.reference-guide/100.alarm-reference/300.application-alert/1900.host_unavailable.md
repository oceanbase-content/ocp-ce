# host_unavailable ホストのハートビート検出失敗

## アラートの説明

OCPは、サーバー上のocp_mgragentに対して5秒ごとにハートビートプローブを送信し、タイムアウト時間は5秒です（システムパラメータ`ocp.check.host.http.read.timeout`で設定）。ハートビートプローブに応答がない場合、このアラートがトリガーされます。ネットワークが切断されている可能性があり、そのホストの運用保守および監視情報収集に影響を与えるため、重点的に注意する必要があります。

## アラートの仕組み

OCP-Serverは5秒ごとにハートビート検出タスクを実行します。このタスクは、ocp_mgragentのステータスインターフェース`http://ip:62888/api/v1/agent/status`にアクセスして、OCP-Agentの各プロセスの状態情報を要求します。インターフェースから応答がない場合、または実行時にエラーが発生し、障害が1分以上続く場合にアラートがトリガーされます。

<main id="notice" type='explain'>
<h4>説明</h4>
<p>アラートの検出期間は、V3.3.2より前のバージョンではシステムパラメータによって制御されていました：<code>ocp.host.check.unavailable-time-threshold</code>。このパラメータはOCP Agentの最大オフライン時間を表し、単位はミリ秒です。この時間を超えてオフラインの場合、ホストのハートビート検出失敗アラートが送信されます。</p>
</main>

次の表は、このアラートの監視ロジックに関連する主要なパラメータを示しています。

| パラメータ | 値 |
|-----------|----------|
| 監視指標 | host_available。この指標はホストのハートビート検出に応答があるかどうかを示します。指標値が`1`の場合は応答があり、指標値が`0`の場合は応答がなく、アラートがトリガーされます。 |
| 監視式 | ```min(host_available{@LABELS}) by (@GBLABELS)``` |
| 取得指標 | host_available |
| データソース | OCP Server自身の統計データです。Agentマシンで`sudo curl --unix-socket /home/admin/ocp_agent/run/ocp_monagent.$(cat /home/admin/ocp_agent/run/ocp_monagent.pid).sock http://unix-socket-server/api/v1/time`を実行して、`/api/v1/time`インターフェースにアクセスし、ホストの時刻を取得します。取得した時刻がタイムアウトまたは異常な場合、使用不可と見なされます。 |
| 取得周期 | 5秒 |

## ルール情報

| 監視指標 | デフォルトしきい値（単位：ミリ秒） | 持続時間 | 検出周期 | 解消周期 |
| -------- | ---------------------- | -------- | -------- | -------- |
| host_available      |  0          | 60秒     | 15秒    | 5分   |

## アラート情報

| アラートトリガー方式 | アラートレベル | 対象範囲 |
| ------------ | -------- | ---- |
| 監視指標の式に基づく | サービス停止     | ホスト |

## アラートテンプレート

* **アラート概要**

  * テンプレート：\${alarm_target} \${alarm_name}
  * サンプル：alarm_template_id=0:host=xxx.xxx.xxx.xxx ホストのハートビート検出失敗

* **アラート詳細**

  * テンプレート：クラスタ：\${ob_cluster_name}、ホスト：\${host}、アラート：\${alarm_name}。失敗理由：\${failed_reason}。ocp_mgragentプロセスが正常に動作しているか、またはホスト\${host}へのアクセスが可能か確認してください。
  * サンプル：クラスタ：cluster、ホスト：xxx.xxx.xxx.xxx、アラート：ホストのハートビート検出失敗。失敗理由：[OCPNotFoundException]: status=404 NOT_FOUND, errorCode=COMPUTE_HOST_AGENT_CREDENTIAL_NOT_FOUND, args=9。ocp_mgragentプロセスが正常に動作しているか、またはホストxxx.xxx.xxx.xxxへのアクセスが可能か確認してください。

* **アラート回復**

  * 詳細：アラート：${alarm_name}、サーバーステータス：\${recover_value}
  * サンプル：アラート：ホストのハートビート検出失敗、サーバーステータス：1

ここで、${alarm_target} の形式は ob_cluster=xxxxxxx:svr_ip=xxxxxx です。svr_ip はアラートが発生したクラスタ内の対応するOBServerノードのIPです。

## システムへの影響

OCPはターゲットマシンにリモートコマンドを送信できず、該当マシンの運用機能は利用できません。

## 考えられる原因

一般的な原因は以下のとおりです：

* ターゲットマシンが異常にダウンしました。

* OCPとホスト間のネットワーク通信障害が発生しました。

* OCP-Agentが異常終了しました。

## 解決策

1. ターゲットマシンがダウンしていないか確認します。

   ターゲットホストへのログインを試みるか、同一サブネットのホストで `ping xxx.xxx.xxx.xxx` コマンドを実行します。xxx.xxx.xxx.xxx はターゲットホストのIPです。

   * ログインできない場合、または `ping` コマンド実行後に送信成功したデータのエコー情報がない場合、ターゲットホストはおそらくダウンしています。

     お問い合わせ先：データセンターの運用保守エンジニア。

   * ログインでき、pingも通じる場合、ホストは正常です。他の原因によってアラートがトリガーされた可能性があります。

2. OCPとホスト間のネットワーク通信障害が発生していないか確認します。ネットワークエンジニアにお問い合わせください。

   OCPホストから障害ホストにpingを送信し、その後障害ホストからOCPホストにpingを送信します。

   * 互いにpingが通じる場合、ネットワークに障害はありません。他の原因によってアラートがトリガーされた可能性があります。

   * 互いにpingが通じない場合、ネットワークに障害があります。ネットワークエンジニアにお問い合わせすることを推奨します。ネットワークエンジニアがいない場合は、[ネットワーク障害のトラブルシューティング](../500.appendix/300.network-troubleshooting.md) を参照して障害原因を調査してください。

3. ocp_mgragentプロセスが存在しないか確認します。

   OCP上で **<UI-TERM key="ocp-v2.src.constant.auditEvent.Host">ホスト</UI-TERM>** メニューの **<UI-TERM key="ocp-v2.page.Host.HostList">ホスト一覧</UI-TERM>** から障害ホストに移動し、**OCP Agent** タブでプロセスに異常がないか確認します。

   * 異常がある場合、プロセスリストの 再起動 ボタンをクリックしてそのプロセスを再起動できます。または、付録の [OCP-Agent運用スクリプト](../../../850.host-features/100.manage-a-host/900.ocp-agent-o-m-scripts.md) を参照してOCP-Agentを再起動し、OCP-Agentサービスを復旧することもできます。

   * 異常がなく、かつアラートがまだ解消されていない場合は、次の手順を実行してください。

4. 技術サポートに連絡して、原因の特定を依頼します。
