# host_process_cpu_bind_core_is_invalid CPUバインディング設定の不整合

## 警報の概要

この警報は、ホスト上のOBServerまたはOBProxyプロセスのCPUバインディング設定が、OCPメタデータベースに記録されている設定と一致しているかどうかを監視し、両者が一致しない場合にトリガーされます。

## 警報の仕組み

| パラメータ | 値 |
| -------- | -------- |
| 監視指標 | host_process_cpu_bind_core_alarm_status |
| 監視式 | `max(host_process_cpu_bind_core_alarm_status{@LABELS}) by (@GBLABELS)` |
| 取得指標 | host_process_cpu_bind_core_alarm_status |
| 指標ソース | OCP主動検出 |
| 取得周期 | 60秒 |

OCPは定期的にホスト上のOBServer/OBProxyプロセスのCPUバインディング設定の一貫性をチェックします。具体的な仕組みは以下の通りです：

1. OCPはメタデータベースから、そのホスト上で構成されているすべてのCPUバインディング情報(CpuBindCoreConfigEntity)および対応するサーバーステータス情報(CpuBindCoreServerStateEntity)を取得します。

2. 各CPUバインディング設定について、OCPはOCP-Agent実際のプロセスが現在クエリしているCPUバインディング範囲(プロセスPIDで`taskset -pc pid`コマンドを実行して取得)を確認します。

3. 実際のバインディング範囲をメタデータベースに記録されている期待されるバインディング範囲と比較します。

4. 実際の範囲が期待される範囲と一致しない場合、指標host_process_cpu_bind_core_alarm_statusを1(アラート状態)に設定します。一致する場合は0(正常状態)に設定します。

指標値が1に等しい場合、トリガー条件を満たし、警報が発生します。

| ---------- | ------- | -------- | -------- | -------- |

## システムへの影響

CPUカーネル割り当てが一致しないということは、プロセスが実際に使用するCPUコアが想定された計画と一致しないことを意味し、以下の影響を及ぼす可能性があります：

* リソース競合：複数のプロセスが同じCPUコアを共有することで、CPUリソースを巡る競合が発生し、パフォーマンスの安定性に影響します。

* パフォーマンス低下：プロセスが想定されたCPUコアにバインドされないことで、NUMAによるノード間メモリアクセスが発生し、レイテンシが増加する可能性があります。

* 分離性の低下：CPUカーネルの割り当てはリソース分離を実現することが主な目的です。設定が一致しない場合、分離ポリシーが無効になります。

## 考えられる原因

* ホスト上のプロセスが手動で再起動され、再起動後にCPUカーネルの割り当てが反映されなかったり、正しく再バインドされなかったりした場合。

* tasksetの設定が手動で変更された場合。

## 解決策

1. アラート情報の確認：アラートに記載されているクラスタID（ob_cluster_id）とホストIP（svr_ip）から、該当するホストとプロセスを特定します。

2. 現在のCPUカーネル割り当ての確認：

   ```bash
   # observerプロセスのCPUカーネル割り当て情報を確認します。obproxyプロセスの確認方法も同様です。
   ps -ef | grep observer
   taskset -pc <observer_pid>
   ```

3. 期待される設定との比較：OCPコンソールで、該当ホストのプロセスのCPUカーネル割り当て設定を確認し、実際に確認されたCPUカーネルの範囲と比較して、不一致の具体的な内容を確認します。

4. CPUカーネル割り当ての修正：

   * 方法1（推奨）：OCPコンソールを通じてCPUカーネル割り当て設定を再度配布します。OCPはOCP-Agentを通じて自動的にCPUカーネルの割り当て操作を完了します。

   * 方法2：ホスト上で手動でtasksetコマンドを使用してCPUコアを再バインドします：

     ```bash
     taskset -pc <cpu_range> <PID>
     ```

5. 修正結果の検証：修正後、次の検出サイクル（60秒）を待ち、アラートが自動的に解消されるかどうか観察します。設定が一致していれば、アラートは解消サイクル（300秒）内に自動的にクリアされます。
