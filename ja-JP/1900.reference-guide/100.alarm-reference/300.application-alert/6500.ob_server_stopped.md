# ob_server_stopped サーバーのサービス停止

## アラートの概要

このアラートは、OceanBaseクラスタ内のOBServerノードがサービス停止（stopped）状態にあるかどうかを監視します。OBServerのstop_timeがNULLではない場合（つまり`STOP SERVER`操作が実行されたことがある場合）、かつ停止時間が0秒を超えるとアラートがトリガーされます。

## アラートの仕組み

| パラメータ | 値 |
| -------- | --------- |
| 監視指標 | ob_server_stopped_duration_seconds |
| 監視式 | `max(ob_server_stopped_duration_seconds{@LABELS}) by (@GBLABELS)` |
| 取得指標 | ob_server_stopped_duration_seconds |
| 指標ソース | OCP-AgentがOBServer内部ビューから取得 |
| 取得周期 | N/A |

OCP-AgentはSQLを定期的に実行してOBServerのサービス状態を照会します。具体的な仕組みは以下の通りです：

1. OceanBase V4.0未満のバージョンでは、OCP-Agentは`__all_server`ビューを照会し、stop_timeフィールドから停止時間を計算します。stop_timeが0の場合、指標値は0となります。それ以外の場合、指標値は（現在時刻 - stop_time）の秒数となります。

2. OceanBase V4.0以降のバージョンでは、OCP-Agentは`DBA_OB_SERVERS`ビューを照会し、STOP_TIMEフィールドから停止時間を計算します。STOP_TIMEがNULLの場合、指標値は0となります。それ以外の場合、指標値は現在時刻とSTOP_TIMEの秒単位の差となります。

3. 同時にstatusフィールドもラベルとして取得し、OBServerの現在の稼働状態を反映します。

指標値ob_server_stopped_duration_secondsが0を超えると、トリガー条件を満たし、アラートが発生します。

## ルール情報

| 監視指標 | デフォルトしきい値 | 持続時間 | 検出周期 | 解消周期 |
| ---------- | -------- | -------- | -------- | -------- |
| ob_server_stopped_duration_seconds  | 0 | 60秒 | 10秒 | 300秒 |

## アラート情報

| アラートトリガー方式 | アラートレベル | 対象範囲 |
| ------------ | ------- | -------- |
| 監視指標の式に基づく | 停止サービス | ホスト |

## システムへの影響

OBServerがサービスを停止すると、そのノードは外部にデータベースサービスを提供しなくなり、以下の影響が発生する可能性があります：

* サービス中断：当該ノード上で保持されているリーダーレプリカは選出による切り替えが必要となり、切り替え期間中は関連するパーティションが一時的に利用できなくなります。

* 可用性の低下：クラスタ内の利用可能なノードが減少し、複数のノードが同時にサービスを停止した場合、Paxosの多数派を形成できず、クラスタ全体が利用不能になる可能性があります。

* 負荷の不均衡：サービス停止したノードのトラフィックが他のノードに転送され、残りのノードの負荷が上昇する可能性があります。

## 考えられる原因

* メンテナンス担当者が`ALTER SYSTEM STOP SERVER`操作を実行した場合（計画的メンテナンス、ノード隔離など）。

* OCPコンソールを使用してノードの停止操作を実行した場合。

* OBServerプロセスが異常終了した後、状態がstoppedとしてマークされた場合。

## 解決策

1. 停止原因の確認：当該ノードの停止が計画的メンテナンスによるものかどうかを確認します。計画的な操作であれば、このアラートを無視し、メンテナンス終了後にサービスを再開することができます。

2. ノード状態の確認：SQLを使用してクラスタ内の各ノードの状態を確認します：

   ```sql
   SELECT SVR_IP, SVR_PORT, ZONE, STATUS, START_SERVICE_TIME, STOP_TIME
   FROM oceanbase.DBA_OB_SERVERS;
   ```

3. ノードサービスの回復：

   * 方法1（推奨）：OCPコンソールを使用して、当該ノードのサービス起動操作を実行します。

   * 方法2：SQLコマンドを使用してノードを起動します：

     ```sql
     ALTER SYSTEM START SERVER 'xxx.xxx.xxx.xxx:2882';
     ```

4. ノードの健全性確認：サービスを回復する前に、ノードのobserverプロセスが正常に実行され、ネットワーク接続が正常で、ログ同期に遅延がないことを確認します：

   ```bash
   ps -ef | grep observer
   ```

   ```sql
   SELECT SVR_IP, ROLE, SCN_TO_TIMESTAMP(END_SCN)
   FROM oceanbase.GV$OB_LOG_STAT WHERE TENANT_ID = 1 ORDER BY LS_ID, ROLE;
   ```

5. 修復結果の検証：サービスを回復した後、ノードのSTATUSがACTIVEに変わっていることを確認します。アラートは自動的にクリアされます（クリアサイクル：300秒）。
