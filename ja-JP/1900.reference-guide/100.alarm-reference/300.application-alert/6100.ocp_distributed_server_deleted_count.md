# ocp_distributed_server_deleted_count OCPノードのオフライン

## アラートの概要

OCPノードがオフラインになると、同一のOCPクラスタ内の他のOCPからこのアラートが発報されます。

## アラートの仕組み

次の表は、このアラートの監視ロジックに関連する主要なパラメータを示しています。

| パラメータ  | 値  |
|-------|------|
| 監視指標  | ocp_distributed_server_deleted_count。この指標は、OCPノードがオフラインになった後、同一のOCPクラスタ内の他のOCPがこのアラートを発報することを示します。 |
| 監視式  | ```sum(ocp_distributed_server_change{type="DELETE", @LABELS}) by (@GBLABELS)```  |
| 取得指標  | ocp_distributed_server_change  |
| 指標の出典  | 取得SQL：`SELECT * FROM DISTRIBUTED_SERVER WHERE TIMESTAMPADD(SECOND, ?, UPDATE_TIME) <  CURRENT_TIMESTAM`<br>ここで：<li>`distributed_server`テーブルはOCPノードデータを保存するために使用されます。OCPノードがオフラインになると、他のOCPノードは期限切れのノードをクリーンアップします。</li><li>`?`は有効期限で、デフォルトは60秒です。`ocp.distributed.server.expire.seconds`パラメータで設定できます。</li> |
| 取得サイクル  | 無し。OCPノードがオフラインになるとすぐにトリガーされます。  |

## ルール情報

| 監視指標  | デフォルトしきい値（単位：個）  | 持続時間  | 検出サイクル  | 解消サイクル  |
|-------|------|-------|------|------|
| ocp_distributed_server_deleted_count  | 0  | 0秒  | 10秒  | 5分  |

## アラート情報

| アラートのトリガー方法  | アラートレベル  | 対象範囲  |
|---------------|----------|-------|
| 監視指標の式に基づく  | 極めて深刻  | サービス  |

## アラートテンプレート

* **アラート概要**

  * テンプレート：${alarm_target} ${alarm_name}
  * 例：alarm_template_id=0:svr_ip=xx.xx.xx.xx:svr_port=8080:target_server=xx.xx.xx.xx:8080 OCPノードのオフライン

* **アラート詳細**

  * テンプレート：アラート：${alarm_name}、ノード：${target_server}。
  * 例：アラート：OCPノードのオフライン、ノード：xx.xx.xx.xx:8080。

* **アラート回復**

  * テンプレート：アラート：${alarm_name}、OCPノードのオフライン：${value_shown}
  * サンプル：アラート：OCPノードがオフラインになりました、OCPノードがオフラインになりました：1

## システムへの影響

オフラインになったOCPノードに対する日常的な運用保守はできなくなります。

## 考えられる原因

* OCPがkillされました。
* OCPの再起動処理が滞っています。

## 解決策

OCPプロセスを再起動し、`/home/admin/ocp-server/log` ディレクトリ内の `ocp.log` ログにSpringboot起動プロセスが存在するか確認します。
