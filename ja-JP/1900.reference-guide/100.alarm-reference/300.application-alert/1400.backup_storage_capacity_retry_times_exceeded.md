# backup_storage_capacity_retry_times_exceeded バックアップ・リストア容量取得のリトライ回数が上限を超えた

## 警報の概要

バックアップ・リストア時には容量の取得が必要です。OCPとバックアップサーバー間のネットワーク異常などの原因で取得に失敗した場合、リトライが行われます。リトライ回数が一定数を超えると、この警報がトリガーされます。

## 警報の仕組み

以下の表は、この警報のモニタリングロジックに関連する主要パラメータを示しています。

| パラメータ | 値 |
|-------|-----------|
| モニタリング指標 | storage_capacity_monitor_error_code。この指標は、OCP-Serverがバックアップ・リストアのストレージ容量を監視する際に収集したエラーコードを表します。モニタリング指標の値が1001の場合、警報がトリガーされます。 |
| モニタリング式 | ```max(storage_capacity_monitor_error_code{@LABELS}) by (@GBLABELS)``` |
| 取得指標 | storage_capacity_monitor_error_code |
| 指標の出典 | OCP-Serverがバックアップ・リストアのストレージ容量を監視し、以下の状況が発生した場合に対応するエラーコードを記録し、取得指標に代入します。<li>1001：ディレクトリ容量取得のリトライ回数が上限を超えた。</li><li>1002：ディレクトリ容量取得がタイムアウトしたり、スレッドが中断されたりした場合。</li> |
| 取得サイクル | 5秒 |

## ルール情報

| モニタリング指標 | デフォルトしきい値 | 持続時間 | 検出サイクル | 解消サイクル |
|-------------------------------------|------|------|-------|-------|
| storage_capacity_monitor_error_code | 1001 | 0秒 | 60秒 | 5分 |

## 警報テンプレート

* **警報の概要**

  * テンプレート: ${alarm_target} \${alarm_name}
  * サンプル: alarm_template_id=0:ob_cluster=obcluster-1:storage_url=file:///obbackup/yc225_214/ バックアップ・リストア容量取得のリトライ回数が上限を超えた

* **警報の詳細**

  * テンプレート: クラスタ：\${ob_cluster_name}、警報：\${storage_url} \${alarm_name}。容量取得のリトライ回数が上限を超えました。エラーコード：\${value}。
  * サンプル: クラスタ：obcluster-1、警報：file:///obbackup/yc225_214/ バックアップ・リストア容量取得のリトライ回数が上限を超えた。容量取得のリトライ回数が上限を超えました。エラーコード：1001。

* **警報の復旧**

  * テンプレート：警報：${alarm_name}、ストレージ容量取得エラーコード：\${value}
  * サンプル：アラート：バックアップ・リストア容量取得のリトライ回数が上限を超えました、ストレージ容量収集エラーコード：-

ここで、${alarm_target} の形式は storage_url=xxxxxxx です。

## システムへの影響

バックアップ・リストアページにおけるストレージ容量の傾向データの間隔が30分を超えたり、表示されなかったりします。

## 考えられる原因

* OCPとバックアップストレージサーバー間のネットワーク異常。

* バックアップストレージへのアクセス不可または異常。

* バックアップファイルがOBServerによって期限切れでクリーンアップされた。

## 解決策

* OCPとバックアップストレージサーバー間のネットワーク障害が発生していないか確認します。

  以下のコマンドを参照して、両者の間にネットワーク障害があるかどうかを確認します。

  ```java
  # OCPサーバーからバックアップストレージサーバーにpingを送信します。xxx.xxx.xxx.1はバックアップストレージホストのIPです。
  ping xxx.xxx.xxx.1

  # バックアップストレージサーバーからOCPサーバーにpingを送信します。xxx.xxx.xxx.2はOCPホストのIPです。
  ping xxx.xxx.xxx.2
  ```

  * 連続したデータ送信メッセージが返された場合、ネットワークは正常です。アラートは他の原因による可能性があります。

  * 連続したデータ送信メッセージが返されない場合、ネットワークに障害があります。ネットワーク管理者に連絡し、具体的なネットワーク問題を調査してもらいます。ネットワーク管理者がいない場合は、[ネットワーク障害のトラブルシューティング](../500.appendix/300.network-troubleshooting.md) を参照して調査および修復を行ってください。

* バックアップストレージディレクトリへのアクセスができないか確認します。

  1. バックアップストレージサーバーにログインします。

  2. バックアップストレージディレクトリの上位ディレクトリに移動し、llコマンドを実行して、そのディレクトリにadminユーザーが読み取り権限を持っているか確認します。

     ```shell
     # /obbackupはデフォルトのバックアップストレージディレクトリです。
     cd / && ll | grep obbackup

     # 次の内容が返されます
     drwxrwxrwx   16 root root 4096 Aug 10 14:34 obbackup
     ```

     * rwxrwxrwxは、すべてのユーザーが読み取り、書き込み、実行できることを意味します。

     * 2つのrootは、それぞれバックアップファイルの保存ディレクトリを所有するユーザーと、そのユーザーのグループを表します。

     この権限がない場合、adminユーザーはアクセスできない可能性があります。ユーザーはwww.baidu.comでLinux権限について確認した上で分析してください。

  3. 権限が不足している場合、以下のコマンドを参考にバックアップ保存ディレクトリの権限を変更し、アクセス可能にしてください。

     ```shell
     chmod -R 777 /obbackup
     ```

* バックアップファイルがOBServerによって期限切れでクリーンアップされたかどうかを確認します。

  1. sysテナントでOBServerにログインします。

     ```shell
     obclient -hxxx.xxx.xxx.xxx -P2883 -uroot@sys#**** -p****** -Doceanbase
     ```

  2. ビュー`cdb_ob_backup_set_files`を参照してバックアップ情報を確認します。

     ```sql
     select * from cdb_ob_backup_set_files where tenantid = xx;
     ```

     クエリ結果に基づいて確認します。対応するバックアップレコードの`file_status`がdeletedの場合、そのバックアップファイルは既にクリーンアップされています。
