# backup_storage_capacity_timeout_or_interrupted バックアップ・リストアディレクトリ容量取得タイムアウトまたはスレッドが中断された場合

## アラートの概要

バックアップ・リストア時には、バックアップ保存容量を取得する必要があります。OCPとバックアップサーバー間のネットワーク異常などの理由で取得に失敗した場合、リトライが行われます。取得時間が長すぎるか、スレッドが中断された場合にこのアラートがトリガーされます。

## アラートの仕組み

以下の表は、このアラートの監視ロジックに関連する主要パラメータを示しています。

| パラメータ | 値 |
|---------|----------|
| 監視指標 | storage_capacity_monitor_error_code。この指標は、OCP-Serverがバックアップ・リストアの保存容量を監視する際に収集したエラーコードを表します。監視指標値が1002の場合にアラートがトリガーされます。 |
| 監視式 | ```max(storage_capacity_monitor_error_code{@LABELS}) by (@GBLABELS)```     |
| 取得指標 | storage_capacity_monitor_error_code     |
| 指標ソース | OCP-Serverがバックアップ・リストアの保存容量を監視し、以下の状況が発生した場合に対応するエラーコードを記録し、取得指標に代入します。<li>1001：ディレクトリ容量取得のリトライ回数が上限を超えた場合。</li><li>1002：ディレクトリ容量取得タイムアウトまたはスレッドが中断された場合。</li>    |
| 取得サイクル | 5秒 |

## ルール情報

|            監視指標                 | デフォルトしきい値 | 持続時間 | 検出サイクル  | 解消サイクル |
|-------------------------------------|----------|------|-------|------|
| storage_capacity_monitor_error_code | 1002   | 0秒   | 60秒 | 5分 |

## アラート情報

|  アラートトリガー方式  | アラートレベル | 対象範囲 |
|----------|------|--------|
| 監視指標の式に基づく | 警告   | バックアップ・リストア |

## アラートテンプレート

* **アラート概要**

  * テンプレート：\${alarm_target} \${alarm_name}
  * サンプル：alarm_template_id=0:ob_cluster=obcluster-1:storage_url=file:///obbackup/yc225_214/inc_data/ バックアップ・リストアディレクトリ容量取得タイムアウトまたはスレッドが中断された場合

* **アラート詳細**

  * テンプレート：クラスタ：\${ob_cluster_name}、アラート：\${storage_url} \${alarm_name}。容量取得タイムアウトまたは中断、エラーコード：\${value}。
  * サンプル：クラスタ：obcluster-1、アラート：file:///obbackup/yc225_214/inc_data/ バックアップ・リストアディレクトリ容量取得タイムアウトまたはスレッドが中断された場合。容量取得タイムアウトまたは中断、エラーコード：1002。

* **アラート回復**

  * テンプレート：アラート：${alarm_name}、保存容量取得エラーコード：\${value}
  * サンプル：アラート：バックアップ・リストアディレクトリ容量取得タイムアウトまたはスレッドが中断、ストレージ容量収集エラーコード：-

ここで、${alarm_target} の形式は storage_url=file:///obbackup//yc225_214/inc_data/ です。

## システムへの影響

バックアップ・リストアページのストレージ容量の傾向データの間隔が30分を超えるか、表示されない場合があります。

## 考えられる原因

一般的には、以下の2つの原因が考えられます：

* OCPとバックアップサーバー間のネットワーク異常、またはOceanBaseクラスタとバックアップストレージサーバー間のネットワーク異常。

* バックアップストレージへのアクセス不可、または異常。

## 解決策

1. OCPとバックアップストレージサーバー間のネットワーク障害が発生していないか確認します。

   * ストレージタイプがFileの場合、OceanBaseクラスタとバックアップストレージサーバー間のネットワークに異常がないか確認する必要があります。以下のコマンドを参照して、両者のネットワークに異常がないか確認します。

      以下のコマンドを参照して、両者のネットワークに障害がないか確認します。

      ```java
      # OCPサーバーからバックアップストレージサーバーにpingを送信します。xxx.xxx.xxx.1はバックアップストレージホストのIPです。
      ping xxx.xxx.xxx.1
      # バックアップストレージサーバーからOCPサーバーにpingを送信します。xxx.xxx.xxx.2はOCPホストのIPです。
      ping xxx.xxx.xxx.2
      ```

   * ストレージタイプがOSSの場合、OCPとバックアップストレージサーバー間のネットワークに障害がないか確認する必要があります。

     以下のコマンドを参照して、両者のネットワークに障害がないか確認します。

     ```shell
     # OCPサーバーからバックアップストレージサーバーにpingを送信します。xxx.xxx.xxx.1はバックアップストレージホストのIPです。
     ping xxx.xxx.xxx.1
     # バックアップストレージサーバーからOCPサーバーにpingを送信します。xxx.xxx.xxx.2はOCPホストのIPです。
     ping xxx.xxx.xxx.2
     ```

     * 連続したデータ送信メッセージが返された場合、ネットワークは正常です。アラートは他の原因によって引き起こされている可能性があります。

     * 連続したデータ送信メッセージが返されなかった場合、ネットワークに障害があります。ネットワーク管理者に連絡し、具体的なネットワーク問題の調査を依頼してください。ネットワーク管理者がいない場合は、[ネットワーク障害のトラブルシューティング](../500.appendix/300.network-troubleshooting.md) を参照して調査および修復を行ってください。

2. バックアップストレージディレクトリにアクセスできないか確認します。

   1. バックアップストレージサーバーにログインします。

   2. 以下のコマンドを参照して、adminユーザーがバックアップストレージディレクトリに対する読み取り権限を持っているかどうか確認します。

      ```shell
      # /obbackupはデフォルトのバックアップストレージディレクトリです。
      cd / && ll | grep obbackup

      # 次のような内容が返されます。
      drwxrwxrwx   16 root root 4096 Aug 10 14:34 obbackup
      ```

      * rwxrwxrwxは、すべてのユーザーが読み取り、書き込み、実行できることを意味します。

      * 2つのrootは、それぞれバックアップファイルストレージディレクトリの所有者とそのグループを表します。

      この権限がない場合、adminユーザーはアクセスできない可能性があります。Linuxの権限について検索して確認した上で、原因を調査してください。

   3. 権限が不足している場合、以下のコマンドを参照してバックアップストレージディレクトリの権限を変更し、アクセス可能にします。

      ```shell
      chmod -R 777 /obbackup
      ```
