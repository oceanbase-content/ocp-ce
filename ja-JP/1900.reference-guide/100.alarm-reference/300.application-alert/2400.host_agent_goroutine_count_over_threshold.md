# host_agent_goroutine_count_over_threshold サーバーエージェントのゴルーチン数がしきい値を超えた場合

## 警報の概要

エージェントのゴルーチン数（Go言語におけるゴルーチンの概念は、一般的なスレッド数に類似します）がしきい値を超えた場合に、この警報がトリガーされます。

エージェントサービスは、監視エージェント（ocp_monagent）と運用保守エージェント（ocp_mgragent）に分かれており、OCPがOceanBaseデータベースを管理・監視するための重要なツールです。

## 警報の仕組み

| パラメータ   | 値        |
|---------|--------------|
| 監視指標  | host_agent_goroutine_count。この指標は、エージェントプロセスのGoゴルーチン（goroutine）数を示し、指標値がしきい値を超えた場合に警報がトリガーされます。      |
| 監視式       | ```max(go_goroutines{@LABELS}) by (@GBLABELS)```      |
| 取得指標  | go_goroutines     |
| 指標ソース  | Prometheusが提供するGoプロセス監視に依存し、プロセスの自己監視から取得します。具体的には：<li>運用保守エージェント：`http://localhost:62888/metrics/stat`</li><li>監視エージェント：`http://localhost:62889/metrics/stat`</li>  |
| 取得間隔  | 5秒        |

## ルール情報

|            監視指標        | デフォルトしきい値 | 持続時間 | 検出周期 | 解消周期 |
|----------------------------|------|--------|------|------|
| host_agent_goroutine_count | 3000 | 0秒  | 20秒 | 5分 |

## 警報情報

|   警報トリガー方法   | 警報レベル | 対象範囲  |
|------------|------|-----|
| 監視指標の式に基づく | 警告   | ホスト |

## 警報テンプレート

* **警報概要**

  * テンプレート：\${alarm_target} \${alarm_name}
  * 例：alarm_template_id=0:host=xxx.xxx.xxx.xxx:process=ocp_monagent サーバーエージェントのゴルーチン数がしきい値を超えた場合

* **警報詳細**

  * テンプレート：クラスタ：\${ob_cluster_name}、ホスト：\${host}、警報：エージェントプロセス：\${process}、ゴルーチン数 \${value} が制限 \${alarm_threshold} を超えました。
  * 例：クラスタ：obcluster-1、ホスト：xxx.xxx.xxx.xxx、警報：エージェントプロセス：ocp_monagent、ゴルーチン数 3500 が制限 3000 を超えました。

* **警報回復**

  * テンプレート：警報：${alarm_name}、サーバーエージェントのゴルーチン数：\${value}
  * サンプル：アラート：サーバーエージェントスレッド数が上限を超えました、サーバーエージェントスレッド数：950

## システムへの影響

エージェントプロセスは、OCPがOceanBaseデータベースの運用・監視を行うための重要なツールであり、その安定性は極めて重要です。エージェントがシステムリソースを過度に消費すると、OceanBaseデータベースの動作に影響を与えます。

エージェントはGo言語で実装されたプロセスであり、リソース消費が少なく、高並行性、高性能という利点があります。Goスレッド（goroutine）は、スレッドに比べてリソース消費が軽量です。一般的に、単一のスレッドが消費するリソースはkbレベルです。しかし、Goスレッドの数も多すぎると、数十万を超えると負荷が高くなり、GCが遅くなったり、応答が遅くなったりするパフォーマンス上の問題が発生する可能性があります。通常、エージェントプロセスのGoスレッド数は100個以内です。制御不能な無限増加が見られた場合は、注意が必要です。

## 考えられる原因

1. プログラムにスレッドのリソースリークが存在する。例：ロック処理、並行処理、chan処理が不適切など。

2. 複雑なシナリオでは、エージェントのリソース使用が不適切になる可能性があり、複雑な環境がリソースリークを引き起こす可能性がある。

## 解決策

アラートが発生した場合、アラートの詳細を確認し、エージェントが占有するメモリを確認します。

* メモリ使用量が過大（10GBを超える）またはGoスレッド数が10万を超える場合は、直ちにエージェントプロセスを再起動し、問題がOceanBaseデータベースコンポーネントの正常な動作に影響を与えるのを防ぎます。

* エージェントが占有するメモリが許容範囲内（例：2GB以内）の場合、当面OceanBaseデータベースの動作に影響はないため、スレッドリークによるプロセスメモリの増加と判断できます。以下の操作を実行できます：

  1. 環境コンテキスト情報を保存した後、直ちにエージェントを再起動します。

  2. 環境コンテキスト情報を運用保守担当者に提供します。情報には以下が含まれます：

     * 現在のプロセスが占有するメモリ、親子プロセスが占有するメモリ（ocp_agentdは現在のプロセスの親プロセスです）。

     * 現在のプロセスのメモリ性能分析ファイル。

       ```sql
       PID=$(cat /home/admin/ocp_agent/run/ocp_monagent.pid)
       SOCKET=$PID
       # スレッド性能データ
       curl --unix-socket /home/admin/ocp_agent/run/ocp_monagent.$PID.sock http://11/debug/pprof/goroutine?debug=1 --output /tmp/goroutine.txt
       # cpu性能サンプリングデータ
       curl --unix-socket /home/admin/ocp_agent/run/ocp_monagent.$PID.sock http://localhost/debug/pprof/profile?seconds=30 --output pprof.profile.gz
       # メモリサンプリングデータ
       curl --unix-socket /home/admin/ocp_agent/run/ocp_monagent.$PID.sock http://localhost/debug/pprof/heap --output pprof.heap.gz
       ```
