# アラートをDingTalkグループに連携する

DingTalkグループを使用してアラートメッセージを受信できます。ボットがDingTalkグループにメッセージを送信すると、グループの全メンバーがアラートメッセージを確認できます。

## 適用シナリオ

OCPのアラートメッセージは、DingTalkグループ内のボットにプッシュされ、ボットがグループにアラートメッセージを送信します。DingTalkボットと連携するには、DingTalkボットのWebhookアドレスを提供するだけで済みます。

一部の拡張機能は以下のとおりです：

* @特定のグループメンバー：@されるメンバーの携帯電話番号を設定する必要があります。DingTalkの使用説明に従えば、@された際に通知が表示されます。グループメッセージの通知をオフに設定していても同様です。
* ボットのセキュリティ設定での署名追加：より安全な通知方法です。OCPは提供された秘密鍵を使用して送信されるメッセージに署名を追加し、悪意のあるメッセージ送信を防ぎます。
* メッセージのMarkdown形式の定義：アラート名を太字にし、アラート情報をリスト形式で表示できます。
* プロキシの設定：社内ネットワークとパブリックネットワークが接続されていない場合は、ネットワークプロキシを設定する必要があります。アラートメッセージはまずプロキシに送信され、プロキシからDingTalkグループに転送されます。

## 前提条件

* 現在OCPにログインしているユーザーが以下の権限を持っていることを確認してください：

  * **クラスタメンテナンス**、**テナントメンテナンス**、**OBProxyメンテナンス**、**アービトレーションサービスメンテナンス**、**Binlogサービスメンテナンス**、または **ホストメンテナンス** のいずれかのリソース権限。
  * アラートセンターの **<UI-TERM key="ocp-v2.component.common.BinlogClusterSelect.All">すべて</UI-TERM>** メニュー権限。

* DingTalkグループボットの作成と設定が完了していること。DingTalk Standard EditionのAPIは、月間最大1万回まで呼び出し可能です。各ボットは1分間にグループに最大20件のメッセージを送信できます。20件を超えると、10分間制限されます。

  DingTalkボットへの接続については、[DingTalkボット公式ドキュメント](https://open.dingtalk.com/document/orgapp/custom-robot-access)を参照してください。

* ボットのWebhookを取得していること。DingTalkボットの設定後、ボットのWebhookを取得します。これはOCP DingTalkアラートチャネルを設定するための必須項目です。アラートメッセージのセキュリティを確保するため、このWebhookが漏洩しないようにしてください。

  DingTalkボットのWebhookを取得したら、ネットワークが正常に接続されていることを確認してください。以下のコマンドを使用して、テストメッセージを送信できます：

    ```shell
    curl 'https://oapi.dingtalk.com/robot/send?access_token=替换为您的webhook-token' \
    -H 'Content-Type: application/json' \
    -d '{"msgtype": "text","text": {"content":"DingTalkボットテストメッセージ"}}'
    ```

## 注意事項

上記のテスト例からわかるように、アラートメッセージはDingTalk APIにリクエストすることで配信されます。API内のaccess_tokenはDingTalkグループボットの一意の識別子であり、適切に保管する必要があります。access_tokenが漏洩すると、攻撃者はこのAPIにリクエストすることで、広告や違反コンテンツなどの悪意のあるメッセージを送信できます。DingTalkボットは3種類のセキュリティ設定を提供しており、そのうち1つを選択する必要があります。セキュリティ設定は以下のとおりです：

* カスタムキーワード：アラートメッセージにこのキーワードが含まれている必要があります。キーワードに一致すれば、アラートメッセージはグループに送信されます。このセキュリティ方式は安全ではありません。Webhookが漏洩すると、悪意のあるアラート送信のリスクがあります。
* IPアドレス（アドレス範囲）：特定のIPからのアラートメッセージのみ送信を許可します。この方式には運用上のリスクがあります。後にOCPの場所が変更された場合、DingTalkボットの設定も同期して変更する必要があります。
* 署名付き：送信されるメッセージに秘密鍵を使用して署名を設定します。DingTalkは署名が正しいかどうか検証し、悪意のあるメッセージ送信のリスクを防ぎます。このセキュリティ設定の使用を推奨します。

## よくある質問

### メッセージレート制限

Q：レート制限によりメッセージ送信が失敗した場合、どう処理すればよいですか？例：`{"status":1111,"wait":5,"source":"x5","punish":"deny","uuid":"xxx","errcode": 130101,"errmsg": "send too fast, exceed 20 times per minute"}`。

A：DingTalk標準版のAPIは、月間累計1万回まで呼び出し可能です。各ボットは1分間にグループへ最大20件のメッセージを送信できます。20件を超えると10分間レート制限されます。レート制限中はDingTalkに送信されるすべてのメッセージが失敗し、一定のリスクが伴います。解決策：

* アラートチャネルで集約機能を有効にすると、同種のアラートや同一のアラートは集約期間内に一度だけ送信されます。
* プッシュ制限：OCPのプッシュ設定では制限戦略を提供しており、日単位または時間単位での制限をサポートしています（制限の次元はプッシュ設定 + アラートチャネルです）。
* コマンドラインで `ocp.alarm.event.resend-interval-seconds` システム構成を調整できます。デフォルトでは3分ごとにアラートイベントが生成されます。

上記の手順により、アラートメッセージの数を効果的に削減し、アラートが制限される可能性を低減できます。ただし、瞬時に多数の異なるアラートが発生した場合は、制限される可能性があります（1分以内に20件を超えるメッセージを送信した場合）。

### ネットワークが接続できない

Q：ユーザー環境から直接DingTalk APIにアクセスできない場合はどう対処しますか？

A：まず、curlを使用してテストメッセージを送信できるかどうかテストします。ネットワークが接続できない場合は、**<UI-TERM key="ocp-v2.Alarm.Channel.New.CreateAChannel">新規チャネル</UI-TERM>** > **<UI-TERM key="ocp-v2.Alarm.Rule.Detail.BasicConfiguration">基本設定</UI-TERM>** > **<UI-TERM key="ocp-v2.Channel.FormComponent.FeishuForm.Proxy">代理人</UI-TERM>** でネットワークプロキシを設定する必要があります。

### アップグレードと移行

Q：アップグレードまたは移行後、アラートプッシュを更新する方法は何ですか？

A：OCP 4.0.1より前のバージョンでは、HTTPチャネルまたはスクリプトチャネルを通じてDingTalkアラートメッセージを送信していました。4.0.1以降のバージョンでは、組み込みのDingTalkチャネルの追加を推奨します。送信結果の検証に失敗することを避けるため、以下の説明を参照してください：

* 使用しているチャネルタイプがHTTPまたはスクリプトチャネルで、アラートがDingTalkグループ宛ての場合、組み込みのDingTalkチャネルの使用を推奨します。この記事の設定を参照してください。

* 顧客のアラートプラットフォーム宛てで、その後顧客のアラートプラットフォームからDingTalkグループに送信される場合は、組み込みのDingTalkチャネルに変更する必要はありません。元のアラートチャネルタイプを引き続き使用してください。

### Response検証の失敗

Q：Response検証の失敗を解決する方法は何ですか？

A：Response検証は、スクリプトの記述が不適切でユーザーがアラートを受信できない、アラートが漏れるなどの問題を防ぐために行われます。アラートスクリプトには、有効な情報を一度だけ出力することが求められます（API応答コードまたはAPI応答ボディのいずれか）。OCPが情報の一致を検証し、正規表現マッチングとJSONキー値ペアマッチングをサポートしています。DingTalkボットAPIが返すのはJSON内容であるため、JSONキー値ペアマッチングを使用する必要があります。DingTalkグループメッセージチャネルのResponse検証情報は `{"errcode":0,"errmsg":"ok"}` に設定する必要があります。スクリプトチャネルでは、Response以外の内容を出力しないでください（例えば、curlコマンドには進捗情報の出力を防ぐために -s パラメータを追加する必要があります）。
