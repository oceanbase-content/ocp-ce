# HTTPを通じたアラートプッシュのカスタマイズ

システムに既に成熟したアラート管理機能があり、OCPのアラートと連携するためのHTTP APIを提供できる場合は、この方法を利用できます。

## 適用シナリオ

一般的な2つのシナリオ：

1. 各クラウドプラットフォームが提供するアラートボット、例えばDingTalkボットやLarkボットなど。これらのボットはカスタムメッセージの送信とWebhook（API）を提供しています。要求されたメッセージ形式でAPIにリクエストすることで、アラートメッセージを送信できます。
2. ユーザー側がアラートインターフェースを提供する場合。通常、インターフェースに署名を追加したり、特別なフィールド（現在時刻のタイムスタンプなど）を追加したりする必要はありません。固定形式のメッセージをAPIにプッシュするだけで、アラートメッセージを送信できます。

## 技術原理

HTTP APIアラートチャネルは、HTTPリクエストの送信に対応しています。リクエストフィールドには、DingTalkを例にすると以下のものが含まれます：

* APIアドレス：DingTalkのWebhookアドレス。
* リクエストメソッド：POST。ほとんどのアラート受信インターフェースはPOSTインターフェースです。
* Header：HTTPリクエストのヘッダー部分。一般的なものには`Content-Type:application/json; charset=utf-8`、`Authorization: Basic xxxx`などがあります。
* リクエストBody：リクエストパラメータ。クライアントはAPIの具体的な形式、必要なフィールド、各フィールドの意味、空欄を許容するかどうか（空欄不可で対応するフィールドがない場合は、デフォルトフィールドを記入する必要がある場合）を提供する必要があります。DingTalkを例にすると、Bodyは次のとおりです：`{"msgtype": "markdown","markdown": {"content":"${message}","title":"${alarm_name}"}}`。
* プロキシ：APIがパブリックネットワークのアドレスで、内部ネットワークとパブリックネットワークが接続されていない場合は、ネットワークプロキシを設定する必要があります。アラートメッセージはまずプロキシに送信され、プロキシがAPIに転送します。例えば、DingTalk APIなどです。

## 前提条件

* 現在OCPにログインしているユーザーが以下の権限を持っていることを確認してください：

  * **クラスタメンテナンス**、**テナントメンテナンス**、**OBProxyメンテナンス**、**アービトレーションサービスメンテナンス**、**Binlogサービスメンテナンス**、または**ホストメンテナンス**のいずれかのリソース権限。
  * アラートセンターの**<UI-TERM key="ocp-v2.component.common.ServerDropdown.All">すべて</UI-TERM>**メニュー権限。

* アラートメッセージを受信するための明確なAPIを提供する必要があります。簡単なコマンドを作成してこのインターフェースをテストできます。具体的なリクエスト内容は実際の状況に応じて決定する必要があります：

    ```shell
    curl -XPOST 'クライアントが提供するAPIインターフェース' \
    -H 'Content-Type:application/json; charset=utf-8' \
    --data '{"message":"アラートテストメッセージ"}' \
    --compressed \
    --insecure
    ```

    APIに認証が必要な場合、例えばBasic Auth認証の場合は、Headerに認証情報を追加できます：`-H'Authorization: Basic xxxx'`

## 注意事項

1. APIが署名の追加や現在時刻のタイムスタンプなどの特別な要件を伴わない複雑なリクエストパラメータを必要としないことを確認してください。
2. APIは必要な応答内容を返す必要があります。例えば、success（非JSONメッセージ）、{"err_code":0,"message":"success"}（JSONメッセージ）などです。これにより、OCPがメッセージの送信成功を判断しやすくなります（詳細はよくある質問を参照してください）。

## よくある質問

### Response検証情報

Q：Response検証情報の失敗を解決するにはどうすればよいですか？

A：OCP 3.3.0バージョン以降、Response検証情報の設定が必要です。Response検証情報の設定失敗は、アラートスクリプトの記述が不適切であったり、API応答が不規則であったり（送信失敗でも200応答コードを返す）した場合に、ユーザーがアラートを受信できない、アラートが漏れるなどの問題を防ぐためです。アラートスクリプトでは、有効な情報を1回だけ出力する必要があります（API応答コードまたはAPI応答ボディのいずれか）、そしてOCPが情報が一致するかどうかを検証します。正規表現マッチングとJSONキー値ペアマッチングをサポートしています。検証フィールドとAPIが返す内容が一致しない場合、OCPはアラート送信失敗と判断し、再送信を試みます。その結果、ユーザーはすでにメッセージを受信済みであるにもかかわらず、インターフェース上で失敗と判定されたため、複数回のアラートを受信する可能性があります。検証ルールは以下の通りです：

<main id="notice" type='explain'>
  <h4>説明</h4>
  <p>これらはあくまで例です。具体的な設定はAPIの応答結果に基づいて決定する必要がありますので、直接コピー＆ペーストすることは避けてください。</p>
</main>

* 返された結果がJSON形式の場合、Response検証情報もJSON文字列（デフォルトは{}）に設定し、両者が等しいかどうかを比較します。APIが返す内容には、Response検証情報内のすべてのkey-value内容が含まれている必要があります。例えば、APIが`{"成功的标志1":"成功","错误码":0,"当前时间戳":"2023-09-12T10:00:00+8:00"}`を返した場合、Response検証情報は以下のいずれかの設定が可能です：`{"成功的标志1":"成功","错误码":0}`、`{"成功的标志1":"成功"}`、`{"错误码":0}`。

* 返された結果がJSON形式でない場合、Response検証情報は返された結果と同じである必要があります。例えば、APIの応答結果がsuccessの場合、Response検証情報はsuccessに設定する必要があります。APIの応答結果が`success:2023-09-12T10:00:00+8:00`の場合、Response検証情報は正規表現`success.*`に設定する必要があります。

* 現在、返された結果がJSONかどうかの判断は、最初と最後に`{}`文字があるかどうかを判断する方法のみです。応答結果がちょうどこの状況でありながらJSON形式でない場合、誤判が発生する可能性があります。

### アラートインターフェースのタイムアウト

OCPがアラートを送信するデフォルトのタイムアウト時間は10秒です。カスタマーが提供するアラートインターフェースの応答時間が10秒を超えると、送信失敗と見なされ、アラートメッセージの再送信が試みられます。設定パラメータ：

* アラート送信タイムアウトパラメータ：`ocp.alarm.send.once-timeout-ms`、デフォルトは10000ミリ秒。
* アラート送信失敗時の再送信回数：`ocp.alarm.send.once-retry-times`、デフォルトは1回です。
