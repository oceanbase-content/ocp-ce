# デュアルデータセンタースキームにおけるOceanBaseテナントレベルの日常的な切り替え

このセクションでは、デュアルデータセンタースキームにおいて、OceanBaseテナントレベルのプライマリ/スタンバイデータベースを日常的に切り替える方法について説明します。

## 適用シナリオ

ほとんどの場合、ユーザーの業務アプリケーションはテナントごとに分離されています。このようなシナリオでクラスタレベルのプライマリ/スタンバイデータベースを使用すると、以下の影響が発生します：

* テナントが配置されているOBServerが故障し、そのテナントが利用不能になった場合、クラスタ全体をフェイルオーバーする必要があり、他のアプリケーションにも影響が及びます。
* 重要な業務に対してのみ高可用性が必要な場合、システムはすべてのテナントデータを同期する必要があり、データセンター間のトラフィックが過大になります。

OceanBase V4.1では、クラスタレベルのプライマリ/スタンバイデータベースからテナントレベルのプライマリ/スタンバイデータベースへと変更されました。テナントレベルのプライマリ/スタンバイデータベースは、テナントレベルでのログ同期、Switchover、Failover機能を提供し、上記の問題を解決します。

OceanBaseのプライマリ/スタンバイテナントには、アーカイブベースのログ同期とネットワークベースのログ同期の2種類のログ同期モードがあります。アーカイブベースの同期モードでは、プライマリテナントが完全なデータバックアップ（ベースラインデータ）とログバックアップ（増分ログ）を提供し、スタンバイテナントを復元する必要があります。その後、スタンバイテナントはプライマリテナントのアーカイブアドレスからアーカイブを取得し、解析して再生し続けます。プライマリ/スタンバイ間の同期遅延は、ネットワーク遅延やプライマリテナントのアーカイブ遅延などに依存し、通常はかなり大きくなります。

デュアルデータセンタースキームにおいて、それぞれのデータセンターにテナントレベルのプライマリ/スタンバイデータベースをデプロイする概要図は以下のとおりです。

* ネットワークを介してログを転送するプライマリ/スタンバイテナント:

    ![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/%E6%9C%80%E4%BD%B3%E5%AE%9E%E8%B7%B5/%E7%BD%91%E7%BB%9C%E4%BC%A0%E8%BE%93.png)

* ログアーカイブを介してログを転送するプライマリ/スタンバイテナント:

    ![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/%E6%9C%80%E4%BD%B3%E5%AE%9E%E8%B7%B5/%E6%97%A5%E5%BF%97%E5%BD%92%E6%A1%A3.png)

## 前提条件

* 指定したプライマリテナントをスタンバイテナントに切り替える際は、現在OCPにログインしているユーザーが以下の権限を持っていることを確認してください：

  * **クラスタメンテナンス** または **テナントメンテナンス** のリソース権限。
  * テナント **<UI-TERM key="ocp-v2.Backup.Overview.Statistics.SummaryInvestingComZa">概要</UI-TERM>** メニュー権限。

* クラスタ内のすべてのプライマリテナントをスタンバイテナントに切り替える際は、現在OCPにログインしているユーザーが以下の権限を持っていることを確認してください：

  * **クラスタメンテナンス** リソース権限。
  * クラスタ **<UI-TERM key="ocp-v2.src.hook.useMenu.Overview">概要</UI-TERM>** メニュー権限。

* テナントレベルのプライマリ/スタンバイデータベースの日常的な切り替えを実行する際、OceanBaseクラスタは以下の基本条件を満たしている必要があります：

  * プライマリ/スタンバイテナントはどちらもNORMAL状態にあること。
  * プライマリ/スタンバイテナントが属するOceanBaseクラスタは、**<UI-TERM key="ocp-v2.Detail.Log.TaskGraph.Running">実行中</UI-TERM>** 状態であること。
  * プライマリ/スタンバイテナントのSwitchover StatusはNORMAL状態であること。`root@sys` でクラスタに接続し、以下のSQLを使用して確認できます。

    ```sql
    SELECT TENANT_ID, TENANT_NAME, TENANT_TYPE, SWITCHOVER_STATUS FROM oceanbase.CDB_OB_TENANTS WHERE TENANT_NAME = ?;
    ```

  * プライマリ/スタンバイテナントのタイプ（TENANT_TYPE）はUSERタイプであること。SQLのクエリは同じです。
  * プライマリテナントの復元終了時刻（RECOVER UNTIL SCN）は無限大である必要があります。以下のSQLを使用して確認できます。検索結果が `4611686018427387903` の場合、それは無限大を表します。

    ```sql
    SELECT RECOVERY_UNTIL_SCN FROM oceanbase.CDB_OB_TENANTS WHERE TENANT_NAME = ?;
    ```

  * プライマリおよびスタンバイテナントのすべてのログストリームは、無主状態になってはなりません。以下のSQLクエリを実行して確認できます。クエリ結果が `0` の場合、すべてのログストリームにプライマリが存在します。

    ```sql
    SELECT COUNT(1) FROM CDB_OB_LS A LEFT JOIN GV$OB_LOG_STAT B ON A.LS_ID = B.LS_ID
        AND A.TENANT_ID = B.TENANT_ID
        AND B.ROLE = 'LEADER'
    WHERE B.LS_ID IS NULL
        AND A.STATUS NOT IN ('CREATING', 'CREATED', 'TENANT_DROPPING', 'CREATE_ABORT', 'PRE_TENANT_DROPPING')
        AND A.TENANT_ID IN (?, (? - 1));
    ```

  * プライマリおよびスタンバイテナントはいずれもロック状態にあってはなりません。
  * スタンバイテナントが属するOceanBaseクラスタ内のすべてのOBServerは、ACTIVE状態でなければなりません。
  * プライマリおよびスタンバイテナントが属するOceanBaseクラスタのバージョンは、常に同一でなければなりません。

## 注意事項

元のプライマリテナントがBinlogサービスのMetaDB情報を格納している場合、プライマリ/スタンバイテナントの切り替えによりBinlogサービスが利用不可になる可能性があります。ご注意ください。

## 手順

### 方法1：指定したプライマリ/スタンバイテナントの日常的な切り替え

この方法は、指定したプライマリテナントをスタンバイテナントに切り替えるシナリオに適用されます。

1. OceanBaseクラウドプラットフォームにログインします。

2. 左側のナビゲーションバーの **<UI-TERM key="ocp-v2.Backup.SecondaryBackup.Data.Tenant">テナント</UI-TERM>** をクリックし、**<UI-TERM key="ocp-v2.component.TenantList.TenantList">テナント一覧</UI-TERM>** からプライマリテナントに移動します。

3. 右上のメニューアイコンをクリックし、**<UI-TERM key="ocp-v2.Detail.Component.DailyChangeTenantModal.DailySwitching">日常の切り替え</UI-TERM>** を選択します。

   ![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/420/%E7%A7%9F%E6%88%B7%E6%97%A5%E5%B8%B8%E5%88%87%E6%8D%A2.png)

4. ダイアログボックスでテナント切り替えの情報を確認し、**<UI-TERM key="ocp-v2.Detail.Component.DailyChangeTenantModal.StartSwitching">切り替え開始</UI-TERM>** をクリックします。

    ![11221339](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/430/%E6%97%A5%E5%B8%B8%E5%88%87%E6%8D%A2.png)

5. ダイアログボックスのタスクIDをクリックして、タスクの進捗状況を確認します。

### 方法2：クラスタ内のすべてのプライマリ/スタンバイテナントの日常的な切り替え

この方法は、クラスタの運用保守操作を実施する前に、事業継続性を確保するためにスタンバイテナントで業務をサポートする必要があるシナリオに適用されます。この方法を参考に、クラスタ内のすべてのプライマリテナントをスタンバイテナントに切り替えることができます。

1. OceanBaseクラウドプラットフォームにログインします。

2. 左側のナビゲーションバーの **<UI-TERM key="ocp-v2.Cluster.Component.WaterLevel.Cluster">クラスタ</UI-TERM>** をクリックし、**<UI-TERM key="ocp-v2.Cluster.Component.ClusterList.ClusterList">クラスタ一覧</UI-TERM>** からクラスタ **<UI-TERM key="ocp-v2.Backup.Overview.Statistics.SummaryInvestingComZa">概要</UI-TERM>** ページに移動します。

3. 右上のメニューアイコンをクリックし、**<UI-TERM key="ocp-v2.Detail.Overview.TenantDailySwitching">テナントの日常切り替え</UI-TERM>** を選択します。

   ![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/420/%E7%A7%9F%E6%88%B7%E6%97%A5%E5%B8%B8%E5%88%87%E6%8D%A2-%E9%9B%86%E7%BE%A4.png)

4. ダイアログボックスで切り替えるテナントを選択し、**<UI-TERM key="ocp-v2.Detail.Component.SwitchoverModal.DailySwitchover">日常の切り替え</UI-TERM>** をクリックします。

    ![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/430/%E7%A7%9F%E6%88%B7%E6%97%A5%E5%B8%B8%E5%88%87%E6%8D%A2.png)

5. ダイアログのタスクIDをクリックして、タスクの進捗状況を確認します。

## よくある質問

**OCP V4.2.0でスタンバイテナントを作成する際、「FETCH LOG TIMEOUT」というエラーがCreate standby tenantサブタスクで発生する**

![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/%E6%9C%80%E4%BD%B3%E5%AE%9E%E8%B7%B5/%E5%88%9B%E5%BB%BA%E5%A4%87%E7%A7%9F%E6%88%B7%E5%A4%B1%E8%B4%A5.png)

エラーメッセージは上図のとおりです。エラーの原因は、プライマリテナントのCLOGが過剰で、スタンバイテナントがCLOGを取得する際にRPCタイムアウトが発生したためです。プライマリテナントのパラメータ管理で、パラメータ`standby_db_fetch_log_rpc_timeout`の値を大きくすることで解決できます。

**日常切り替え時に「テナントのログ同期遅延xx msがxxx msを超えているため、この操作は許可されません」というエラーが発生する**

* ネットワークベースのプライマリ/スタンバイテナントの場合。

  1. 現在のプライマリ/スタンバイテナントのログ同期が正常かどうかを確認します。OCPでテナントのトポロジーダイアグラムを確認し、同期異常のヒントがないか見てください。
  2. 同期遅延がそれほど大きくなく、かつ継続的に増加していない場合は、ネットワーク遅延またはスタンバイテナントのCPUリソース不足が原因ではないか調査します。
  3. 上記の手順で具体的な原因を特定した後でも日常切り替えを完了したい場合は、OCPのシステムパラメータ`ocp.standby.tenant.delay_threshold`を変更し、プライマリ/スタンバイの遅延しきい値を引き上げてから切り替えを続行します。

* アーカイブベースのプライマリ/スタンバイテナントの場合、プライマリテナントのパラメータ`archive_lag_target`が設定されすぎていないか確認します。このパラメータはプライマリテナントのバックアップ遅延です。
