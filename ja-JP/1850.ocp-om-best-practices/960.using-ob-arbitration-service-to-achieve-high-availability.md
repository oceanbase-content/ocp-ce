# 2つのデータセンターを使用する構成におけるOceanBaseアービトレーションサービスを利用した高可用性の実現

この記事では、2つのデータセンターを使用する構成において、OceanBaseアービトレーションサービスを利用して高可用性を実現する方法について説明します。

## 適用シナリオ

OceanBaseの外部ユーザーは同一都市内で利用可能なデータセンターが通常2つしかない場合が多いです。データセンターレベルの災害復旧機能を提供するため、OceanBaseは2リージョン3データセンターのソリューションを提供しています：

![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/%E6%9C%80%E4%BD%B3%E5%AE%9E%E8%B7%B5/%E4%B8%A4%E5%9C%B0%E4%B8%89%E4%B8%AD%E5%BF%83.png)

リージョン1のゾーン1とゾーン2の2つのデータセンターにそれぞれ2つのFレプリカを配置し、リージョン2のゾーン3のデータセンターに1つのLレプリカを配置します。このように、ゾーン1またはゾーン2のいずれかのデータセンターがダウンした場合でも、Paxosの5つのレプリカのうち3つがサービスを提供し続けるため、サービスの継続性が保証されます。

上記の2リージョン3データセンター構成を採用した後、実際の災害復旧シナリオでは、ユーザーは以下のような問題に直面する可能性があります：

* **データセンター障害時の業務の応答時間（RT）の増大**

  * ゾーン1とゾーン2がどちらも正常にサービスを提供できる場合、Paxosの多数派は同一都市内で成立すればよく、1回あたりのログ同期遅延は1ms以下です。
  * ゾーン1またはゾーン2のいずれかのデータセンターがダウンした場合、Paxosの多数派は異なる都市間で成立する必要があり、1回あたりのログ同期遅延は通常5〜10msかかります。
  * 同期遅延の変化は業務体験に大きな影響を与えます。

    この問題に対処するため、OceanBaseは5レプリカ構成を3レプリカ構成にダウングレードする機能を提供しています。この変更は運用保守のアクションであり、ユーザーが手動で実行する必要があります。操作の詳細については、[OceanBaseクラスタおよびテナントの高可用性構成の縮小](400.reduce-the-high-availability-of-ob-clusters-and-tenants.md)を参照してください。

* **異なる都市間のネットワーク帯域幅リソースの不足**

    2リージョン3データセンターが正常に動作するための前提条件は、リージョン2とリージョン1のネットワーク帯域幅が十分であることです。帯域幅が不足すると、業務のピーク時にリージョン2のログが遅延し、リージョン2のログが追いつく前にリージョン1のデータセンターで障害が発生した場合、クラスタ全体が利用不能になる可能性があります。異なる都市間のネットワーク帯域幅は希少でコストの高いリソースであり、多くの外部ユーザーがOceanBaseの導入を検討する際、どの程度の帯域幅が必要かを検討する必要があります。しかし、この問題に対して、OceanBaseはこれまで有効な答えを提供できていませんでした。

    OceanBaseの典型的なデプロイメントパターンは2F+1Lです。3レプリカはPaxosの高可用性による災害復旧要件から生じ、1Lはデータストレージコストをさらに削減する要件から生じています。2F+1Lのデプロイメントパターンでは、1Lが配置されているノードのログストレージコストとそれに伴うCPUリソース消費は依然として内部で吸収する必要があり、OceanBase全体のソリューションの競争力を低下させています。

以上の点を踏まえ、アービトレーションソリューションは2F+1Aの機能をサポートし、2F+1Lのデプロイメントパターンを置き換える必要があります。これにより、OceanBaseの総コストをさらに削減できます。同時に、他社のクラウド上のMySQL系製品の同期モデルと比較して、OceanBaseのアービトレーションソリューションは、任意のノードまたはデータセンター障害時のロスレスデュアルアクティブ機能を提供できるため、他の製品に比べて顕著な製品優位性を有しています。

## 前提条件

* 現在OCPにログインしているユーザーが**ADMIN**ロールまたは**ORG_ADMIN**ロールであることを確認してください。
* OceanBaseクラスタのバージョンがV4.1.0.0より高いこと。
* RPC形式の互換性を確保するため、AのバージョンはFのバージョンと同じ、またはわずかに高い必要があります（可能であればAとFのバージョンを一致させてください）。
* OceanBaseテナントは2Fまたは4Fデプロイメントである必要があります。現在、2F+1Aまたは4F+1Aのみがサポートされています。

## 手順

**ステップ1: アービトレーションサービスの新規作成**

1. OCPにログインします。

2. 左側のナビゲーションバーで**<UI-TERM key="ocp-v2.component.ParameterTemplate.Cluster">クラスタ</UI-TERM>**をクリックすると、システムはデフォルトで**<UI-TERM key="ocp-v2.page.Cluster.ClusterList">クラスタ一覧</UI-TERM>**タブに移動します。

3. **<UI-TERM key="ocp-v2.Detail.Component.ReplaceArbitrationServerDrawer.ArbitrationService">アービトレーションサービス</UI-TERM>**タブをクリックし、**<UI-TERM key="ocp-v2.Component.ArbitrationServerList.ArbitrationServiceList">アービトレーションサービス一覧</UI-TERM>**ページに移動します。

4. 右上の**<UI-TERM key="ocp-v2.src.component.AddArbitrationDrawer.CreateArbitrationService">新規アービトレーションサービス</UI-TERM>**をクリックします。

5. **<UI-TERM key="ocp-v2.Cluster.Arbitration.CreateArbitrationService">新規アービトレーションサービス</UI-TERM>**パネルで、アービトレーションサービスの基本情報を設定します。

6. **<UI-TERM key="ocp-v2.component.Compaction.MergePolicyDrawer.Ok">確定</UI-TERM>** をクリックし、ポップアップウィンドウのタスクIDをクリックしてタスクの実行状態を確認できます。

    システムは入力された情報を検証します。検証に失敗した場合は、ページの指示に従って調査または修正を行ってください。

**ステップ2: アービトレーションサービスをOceanBaseクラスタに関連付ける**

1. OCPにログインします。

2. 左側のナビゲーションバーで **<UI-TERM key="ocp-v2.Cluster.Component.WaterLevel.Cluster">クラスタ</UI-TERM>** をクリックすると、システムはデフォルトで **<UI-TERM key="ocp-v2.page.Cluster.ClusterList">クラスタ一覧</UI-TERM>** タブに移動します。

3. 操作対象のクラスタを選択し、そのクラスタ名をクリックします。

4. クラスタの **<UI-TERM key="ocp-v2.page.Overview.Overview">概要</UI-TERM>** ページでは、以下の2つの方法でクラスタにアービトレーションサービスを追加できます。

   * 右上の **...** アイコンをクリックし、**<UI-TERM key="ocp-v2.Detail.Component.AddArbitrationServerDrawer.AddArbitrationService">アービトレーションサービスを追加する</UI-TERM>** を選択します。
   * **<UI-TERM key="ocp-v2.Component.ArbitrationServerList.ArbitrationServiceList">アービトレーションサービス一覧</UI-TERM>** モジュールで、**<UI-TERM key="ocp-v2.Cluster.New.AddArbitrationService">アービトレーションサービスを追加する</UI-TERM>** をクリックします。

5. **<UI-TERM key="ocp-v2.Detail.Overview.AddArbitrationService">アービトレーションサービスを追加する</UI-TERM>** パネルで、クラスタに関連付けるアービトレーションサービスのアドレスを選択します。

6. **<UI-TERM key="ocp-v2.Detail.Parameter.List.Submitted">送信</UI-TERM>** をクリックします。

**ステップ3: テナントのアービトレーションを有効にする**

2. 左側のナビゲーションバーで **<UI-TERM key="ocp-v2.Detail.Overview.Tenant">テナント</UI-TERM>** をクリックすると、システムはデフォルトで **<UI-TERM key="ocp-v2.Information.Detail.CollectDetails.TenantList">テナント一覧</UI-TERM>** タブに移動します。

3. 操作対象のテナントを選択し、そのテナント名をクリックします。

## よくある質問

**OceanBaseクラスタのアップグレード時に「OceanBaseクラスタxxバージョンxxは、アービトレーションサービスバージョンxxへの直接昇格ができません。両バージョンの互換性は保証されません」というエラーが発生します**

以下のシナリオでは、OceanBaseクラスタのバージョンとアービトレーションサービスのバージョンの互換性を保証する必要があります。そのため、OceanBaseクラスタをアップグレードする際には、アービトレーションサービスに関連付けられたクラスタのバージョン互換性チェックを実行する必要があります。

* シナリオ1：OceanBaseクラスタとアービトレーションサービスを関連付ける場合、Aがアービトレーションサービスのバージョン、BがOceanBaseクラスタのバージョンです。
* シナリオ2：OceanBaseクラスタを作成する際にアービトレーションサービスを選択した場合、Aがアービトレーションサービスのバージョン、BがOceanBaseクラスタのバージョンです。
* シナリオ3：OceanBaseのアービトレーションサービスを置き換える場合、Aがターゲットのアービトレーションサービスのバージョン、BがOceanBaseクラスタのバージョンです。
* シナリオ4：OceanBaseクラスタをアップグレードする場合、Aがアービトレーションサービスのバージョン、BがターゲットのOceanBaseバージョンです。
* シナリオ5：アービトレーションサービスをアップグレードする場合、Aがターゲットのアービトレーションサービスのバージョン、BがOceanBaseバージョンです。

AとBのバージョン互換性のルールは以下の通りです。このルールは前提条件のバージョン要件と一致しています：AのバージョンはBのバージョン以上でなければなりません。つまり、アービトレーションサービスのバージョンはOceanBaseクラスタのバージョンより低くてはなりません。

* AとBのメジャーバージョンとマイナーバージョン番号がすべて一致する場合、互換性が保証されます。例：A、BともにV4.2.x.x。
* AのメジャーバージョンとマイナーバージョンがBのメジャーバージョンとマイナーバージョンより小さい場合、つまりアービトレーションサービスのバージョンがOceanBaseクラスタのバージョンより低い場合、互換性がないと判断されます。例：AがV4.1.x.x、BがV4.2.x.x。
* AのメジャーバージョンとマイナーバージョンがBのメジャーバージョンとマイナーバージョンより大きい場合、BがAに直接アップグレード可能で、中間に他のバージョンがない場合は、AとBは互換性があると判断されます。そうでない場合は、互換性がないと判断されます。

**テナントアービトレーションを有効にする際に「アービトレーションサービスのCPU利用率：{0}％、メモリ利用率：{1}％、Clogディスク利用可能：{2}MB。CPU利用率 < {3}％、メモリ利用率 < {4}％、Clogディスク利用可能 > {5}MBを満たさないため、テナントアービトレーションを有効にできません」というエラーが発生します**

アービトレーションサービスは、テナントアービトレーションを有効にするたびに、一部のホストリソース（CPU、メモリ）を消費します。アービトレーションによる高可用性サービスを提供できるようにするため、OCPはテナントアービトレーションを有効にする際に、ホストの残りリソースをチェックします。以下のシステムパラメータを変更することで、このチェックをバイパスできます。

* `ocp.arbitration.min.remain.disk.size`：テナントアービトレーションを有効にする際の、アービトレーションサービスホストのCLOGディスクの最小残存値。単位は`MB`です。データ形式`(a,b)`は、テナントレプリカがそれぞれ2F、4Fの場合の値を表します。
* `ocp.arbitration.max.cpu.used.percentage`：テナントアービトレーションを有効にする際の、アービトレーションサービスホストの最大CPU利用率。単位は`%`です。
* `ocp.arbitration.max.memory.used.percentage`：テナントアービトレーションを有効にする際の、アービトレーションサービスホストの最大メモリ利用率。単位は`%`です。
