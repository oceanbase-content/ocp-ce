# 標準的な運用保守プロセスによる障害回復

このセクションでは、OCPの標準運用保守プロセス(SOP)を使用してOceanBaseデータベースの障害回復操作を実行する方法について説明します。

## 適用シナリオ

OceanBaseデータベースの日常的な運用保守において、一部の障害回復操作は複数のステップを含み、ステップ間に依存関係が存在します。手動で実行すると、操作の抜けや順序の誤りが発生しやすいです。OCP標準運用保守プロセス(SOP)は、これらの複雑な操作を標準化されたプロセステンプレートに編成し、自動実行と手動での確認を組み合わせることで、安全で標準化された手順による障害回復を支援します。

SOPは以下の典型的なシナリオに適用されます：

* **スタンバイテナントデータ異常回復**：スタンバイテナントのデータが破損または同期異常が発生し、プライマリテナントのデータからスタンバイテナントを再構築する必要がある場合、「スタンバイテナント再構築」プロセスを使用できます。

* **レプリカ障害時のアービトレーションサービスの有効化**：クラスタ内のレプリカに異常が発生し、アービトレーションサービスによってテナントの可用性を保証する必要がある場合、「レプリカ異常時のアービトレーションサービス開始」プロセスを使用できます。

* **OBServerノード障害回復**：OBServerノードが障害を起こし回復不能な場合、ノードを交換してデータを再構築する必要がある場合、「OBServer異常後のデータ再構築」プロセスを使用できます。

## 前提条件

* 現在OCPにログインしているユーザーが以下の権限を持っていることを確認してください：

  * **クラスタ管理**、**テナント管理**、または**ホスト管理**のいずれかのリソース権限（対応する操作の対象リソースには**管理**または**メンテナンス**権限が必要です）。
  * 運用管理 **標準プロセス** メニュー権限。

* SOP機能はOCP Enterprise版にのみ適用され、OCP Community版ではこの機能は提供されません。

* 各SOPタイプには、さらに以下の条件が必要です：

  | SOPタイプ | 前提条件 |
  |---------|---------|
  | スタンバイテナント再構築 | プライマリテナントが利用可能でデータが完全であること。再構築対象のスタンバイテナントがログ同期リンクで最も下流に位置するスタンバイテナントであること。スタンバイテナントが属するクラスタの状態が正常であること。新しいスタンバイテナントをアーカイブモードに基づいて選択し、SOPタスクで「プライマリテナントのバックアップ」を実行する場合、プライマリテナントにバックアップポリシーが設定されていること。 |
  | レプリカ異常時のアービトレーションサービス開始 | 対象クラスタの状態が正常であること。利用可能なアービトレーションサービスまたはアービトレーションサービスグループを持っていること。 |
  | OBServer異常後のデータ再構築 | 対象クラスタの状態が正常であること。クラスタ内に他の利用可能なOBServerノードが存在すること。代替ホストは事前に準備することを推奨します。 |

## 手順

### スタンバイテナントの再構築

スタンバイテナントのデータ異常や同期中断が回復不能な場合、SOPに従ってスタンバイテナントを再構築できます。

1. OCPにログインします。

2. 左側のナビゲーションバーで、**<UI-TERM key="ocp-v2.src.hook.useMenu.OMManagement">運用および保守管理</UI-TERM>** > **<UI-TERM key="ocp-v2.pages.Sop.StandardProcess">標準プロセス</UI-TERM>** をクリックします。

3. **<UI-TERM key="ocp-v2.components.ModifyLogServiceDataStorageModal.NewCreation">新規作成</UI-TERM>** をクリックし、表示された **<UI-TERM key="ocp-v2.Sop.Main.CreateNewTask">新しいタスクを作成</UI-TERM>** ダイアログで以下の情報を設定します：

   1. **<UI-TERM key="ocp-v2.Sop.CreateTaskDrawer.TaskNameField.TaskName">タスク名</UI-TERM>**：タスク名を入力します（2～32文字。先頭には英字または日本語の仮名、末尾には英字、数字、または日本語の仮名を使用できます。途中にはアンダースコアも使用できます）。

   2. **<UI-TERM key="ocp-v2.Main.Filter.TaskTypeFilter.TaskType">タスクの種類</UI-TERM>**：**<UI-TERM key="ocp-v2.Sop.core.constants.RebuildStandbyTenant">スタンバイテナントの再構築</UI-TERM>** を選択します。

   3. **<UI-TERM key="ocp-v2.Tenant.New.Remarks">備考</UI-TERM>**（オプション）：タスクの備考情報を入力します。

   4. **<UI-TERM key="ocp-v2.Alarm.Event.Detail.ExecuteNow">今すぐ実行</UI-TERM>**：必要に応じて、作成後すぐに実行するかどうかを選択します。初回操作時はチェックを入れず、手順の設定を確認してから手動で開始することをお勧めします。

   5. **<UI-TERM key="ocp-v2.New.Content.DataStorage.NewCreation">新規作成</UI-TERM>** をクリックします。

4. 手順設定ページで、各手順の自動実行スイッチを確認し、調整します：

   | 手順 | 説明 | 推奨設定 |
   |------|------|---------|
   | 操作対象の確認 | 再構築対象のスタンバイテナントとプライマリテナントの情報を確認する | 自動実行 |
   | プライマリテナントのバックアップ | プライマリテナントに対してデータバックアップを実行する | **自動実行を無効** にし、手動で確認してから実行する |
   | プライマリ/スタンバイの分離 | スタンバイテナントとプライマリテナントの同期関係を切断する | 自動実行 |
   | 元のスタンバイテナントのロック | スタンバイテナントをロックして新規書き込みを防ぐ | 自動実行 |
   | 元のスタンバイテナントの削除 | 元のスタンバイテナントを削除する | 自動実行 |
   | スタンバイテナントの新規作成 | 新しいスタンバイテナントを作成する。この手順を実行する前に作成パラメータを設定する必要がある | **自動実行を無効** にし、手動で確認してから実行する |
   | プライマリ/スタンバイ同期の検証 | 新しいスタンバイテナントとプライマリテナントの同期状態を検証する | 自動実行 |

   <main id="notice" type='notice'>
   <h4>注意</h4>
   <p>"スタンバイテナントの新規作成"手順では、実行前に <code>createStandbyTenantParamJson</code> パラメータを設定する必要があります。これには、新しいスタンバイテナント名、互換モード、Zoneレプリカ構成などが含まれます。この手順は手動確認に設定し、パラメータ設定が完了してから進めることをお勧めします。</p>
   </main>

5. **<UI-TERM key="ocp-v2.Component.BinlogInstanceList.Start">起動</UI-TERM>** をクリックして実行を開始します。

6. "スタンバイテナントの新規作成"手順を実行する前に、実行詳細ページでその手順のパラメータを更新します：

   * 手順の右側にある **<UI-TERM key="ocp-v2.ObjectStorage.Component.getColumns.Edit">編集</UI-TERM>** をクリックし、表示されたダイアログで `createStandbyTenantParamJson` パラメータを設定します。これには、新しいスタンバイテナント名、プライマリテナントID、スタンバイクラスタID、プライマリ/スタンバイ同期方式、Zoneレプリカ構成、リソースプール仕様などが含まれます。

7. パラメータに誤りがないことを確認したら、**次へ進む** をクリックして"スタンバイテナントの新規作成"手順を進めます。

8. その後の手順は自動的に実行され、"プライマリ/スタンバイ同期の検証"が完了するまで続きます。

### レプリカ異常時のアービトレーションサービスの有効化

クラスタ内のレプリカに異常が発生し、アービトレーションサービスによってテナントの可用性を確保する必要がある場合には、このプロセスを使用します。

1. OCPにログインします。

2. 左側のナビゲーションバーで、**<UI-TERM key="ocp-v2.src.hook.useMenu.OMManagement">運用および保守管理</UI-TERM>** > **<UI-TERM key="ocp-v2.pages.Sop.StandardProcess">標準プロセス</UI-TERM>** をクリックします。

3. **<UI-TERM key="ocp-v2.New.Content.DataStorage.NewCreation">新規作成</UI-TERM>** をクリックし、表示された **<UI-TERM key="ocp-v2.Sop.CreateTaskDrawer.NewStandardOperationAndMaintenance">標準運用プロセスの新規作成</UI-TERM>** ダイアログで以下の情報を設定します：

   1. **<UI-TERM key="ocp-v2.pages.Schedule.CreateTaskDrawer.TaskName">タスク名</UI-TERM>**：タスク名を入力します。
   2. **<UI-TERM key="ocp-v2.Main.Filter.TaskTypeFilter.TaskType">タスクの種類</UI-TERM>**：**<UI-TERM key="ocp-v2.Sop.core.constants.QuorumServiceEnabledWithCopy">レプリカ異常時のアービトレーションサービスの有効化</UI-TERM>** を選択します。
   3. 対象クラスタを選択し、アービトレーションサービスまたはアービトレーションサービスグループのいずれか一方を選択します（二者択一）。アービトレーションサービスグループを選択した場合、システムはサービスグループ内の優先順位に従って関連するアービトレーションサービスを自動的に選択します。
   4. **<UI-TERM key="ocp-v2.Component.AddBackupStrategy.New">新規作成</UI-TERM>** をクリックします。

4. 手順の設定を確認した後、**<UI-TERM key="ocp-v2.Restore.SamplingStrategy.Detail.Start">起動</UI-TERM>** をクリックして実行を開始します。

   このプロセスには、操作対象の確認、アービトレーションサービスの追加、テナントレプリカの削除、OBServerの削除、テナントのアービトレーションサービスの開始、およびテナントのアービトレーションサービスの可用性検証などのステップが含まれます。すべてのステップはデフォルトで自動実行されますが、実際のニーズに応じて調整できます。

### OBServer異常後のデータ再構築

OBServerノードが障害を起こし回復不能な場合、このプロセスを通じてノードを置き換え、データを再構築できます。

1. OCPにログインします。

2. 故障したOBServerノードと利用可能な代替ホストを確認します。

3. 左側のナビゲーションバーで、**<UI-TERM key="ocp-v2.src.hook.useMenu.OMManagement">運用および保守管理</UI-TERM>** > **<UI-TERM key="ocp-v2.pages.Sop.StandardProcess">標準プロセス</UI-TERM>** をクリックします。

4. **<UI-TERM key="ocp-v2.Cluster.New.New">新設</UI-TERM>** をクリックし、表示された **<UI-TERM key="ocp-v2.Sop.CreateTaskDrawer.NewStandardOperationAndMaintenance">標準運用プロセスの新規作成</UI-TERM>** ダイアログで以下の情報を設定します：

   1. **<UI-TERM key="ocp-v2.pages.Schedule.CreateTaskDrawer.TaskName">タスク名</UI-TERM>**：タスク名を入力します。
   2. **<UI-TERM key="ocp-v2.Main.Filter.TaskTypeFilter.TaskType">タスクの種類</UI-TERM>**：**OBServer異常後のデータ再構築** を選択します。
   3. 対象クラスタを選択します。事前に代替ホストを選定している場合は、それも一緒に選択できます。または、「OBServerの追加」ステップの前に設定することもできます。
   4. **<UI-TERM key="ocp-v2.Component.AddSamplingInspectStrategy.New">新規作成</UI-TERM>** をクリックします。

5. 手順の設定を確認した後、**<UI-TERM key="ocp-v2.Component.ZoneList.Start">起動</UI-TERM>** をクリックして実行を開始します。

   | ステップ | 説明 | 推奨設定 |
   |------|------|---------|
   | 操作対象の確認 | 故障したOBServerの情報を確認する | 自動実行 |
   | テナントレプリカの削除 | 故障したOBServer上のテナントレプリカを削除する | 自動実行 |
   | OBServerの削除 | クラスタから故障したOBServerノードを削除する | 自動実行 |
   | ホストの強制削除（オプション） | OCPから故障したホストを強制的に削除する。このステップはオプションであり、タスクの作成時または編集時に有効にするかどうかを決定できます | **自動実行はオフにし、手動で確認してから進めることを推奨します** |
   | OBServerの追加 | 新しいOBServerノードを追加する。代替ホストを設定する必要があります | **自動実行をオフにし、代替ホストの設定後に進める** |
   | テナントレプリカの追加 | 新しいOBServerにテナントレプリカを追加する | 自動実行 |
   | テナントレプリカの再構築成功の検証 | レプリカの再構築が成功したかどうかを検証する | 自動実行 |

   <main id="notice" type='notice'>
   <h4>注意</h4>
   <p>"ホストの強制削除"はオプションのステップであり、タスクの作成時または編集時に有効にするかどうかを決定できます。このステップはOCPから故障したホストのレコードを削除するもので、操作は不可逆です。有効にした場合は、自動実行をオフにし、手動で確認してから進めることを推奨します。"OBServerの追加"ステップでは代替ホストを選択する必要があります。代替ホストが既にOCPに追加されており、状態が正常であることを確認してください。</p>
   </main>

6. 「OBServerの追加」ステップに進む前に、実行詳細ページでそのステップのパラメータを更新します：

   * ステップの右側にある **<UI-TERM key="ocp-v2.src.constant.parameter.Edit">編集</UI-TERM>** をクリックし、代替ホストを選択します。代替ホストがOCPに追加されており、状態が正常であることを確認してください。

7. パラメータを確認した後、**次へ進む** をクリックして「OBServerの追加」ステップに進みます。

8. 次のステップは、「テナントレプリカの再構築が成功しました」が完了するまで自動的に実行されます。

## よくある質問

**Q：SOPタスクの実行中にステップが失敗した場合はどうすればよいですか？**

A：ステップの実行が失敗すると、タスクの状態は **<UI-TERM key="ocp-v2.NewVersion.Task.Failure">失敗</UI-TERM>** に変わります。実行詳細ページで失敗したステップのエラーメッセージを確認し、エラーの原因に基づいて問題を調査した後、次の操作を実行します。
* 単一の失敗したステップのみを再試行する場合は、そのステップの **<UI-TERM key="ocp-v2.component.PreCheck.CheckResult.Retry">再試行</UI-TERM>** をクリックします。
* すべての失敗したステップを再試行する場合は、ページ上の **すべての失敗したステップを再試行** をクリックします。

**Q：SOPタスクのステップ実行順序は変更できますか？**

A：タスクの作成時または編集時に、テンプレート内で `userMovable=true` とマークされたステップは、許可された番号範囲内で位置を調整できます。ただし、ステップ識別子（stepKey）と固定で有効なステップは変更できません。

**Q：SOPタスクを開始した後で編集できますか？**

A：タスクは一度開始すると編集できません。未開始（待機中）のタスクは、名前、ターゲットパラメータ、ステップ設定、備考を編集できます。開始済みタスクで未実行のステップの自動実行スイッチやステップパラメータを変更する必要がある場合は、ステップ更新機能を使用できます。

**Q："スタンバイテナントの再構築" プロセスにおいて、プライマリ/スタンバイ同期方式のネットワークベースとアーカイブベースの違いは何ですか？**

A：
* **ネットワークベース（NETWORK）**：プライマリテナントとスタンバイテナント間でネットワークを介して直接ログを同期します。遅延は小さいですが、プライマリクラスタとスタンバイクラスタ間のネットワーク接続が必要です。
* **アーカイブベース（LOG_BACKUP）**：スタンバイテナントがバックアップストレージからアーカイブログを取得して再生します。直接のネットワーク接続は不要ですが、同期遅延は通常大きくなります。

**Q：SOPタスクの実行完了後は削除できますか？**

A：可能です。**<UI-TERM key="ocp-v2.Sop.core.constants.Finished">終了</UI-TERM>** および **<UI-TERM key="ocp-v2.SQLDiagnosis.Component.MaterializedView.Failed">失敗</UI-TERM>** 状態のタスクは削除でき、**<UI-TERM key="ocp-v2.src.constant.task.ToBeExecuted">実行待ち</UI-TERM>** 状態のタスクも直接削除できます。しかし、**<UI-TERM key="ocp-v2.src.constant.alarm.WaitingForConfirmation">確認待ち</UI-TERM>** および **<UI-TERM key="ocp-v2.src.util.task.Running">実行中</UI-TERM>** 状態のタスクは削除できません。タスクの削除は、実行インスタンスとステップ実行記録を連鎖的にクリーンアップします。
