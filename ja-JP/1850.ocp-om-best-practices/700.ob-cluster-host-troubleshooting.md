# OceanBaseクラスタホストの障害対処

このセクションでは、OceanBaseクラスタのホストに発生した障害に対処するための運用保守手順について説明します。

## 適用シナリオ

OceanBaseのマルチレプリカ高可用性アーキテクチャは、一部ノードの障害を許容できます。例えば、3レプリカ構成では任意の1つのノードが障害を起こしても過半数に影響は出ません。5レプリカ構成では任意の2つのノードが障害を起こしても過半数に影響は出ません。しかし、OceanBaseクラスタ内の一部のホストで障害が発生した場合は、速やかに対処する必要があります。これは、さらに多くのノードが障害を起こして過半数に影響が及ぶのを防ぐためです。

ホスト障害は以下のシナリオに分類されます：

* 交換用の予備マシンがある場合。

* 交換用の予備マシンがない場合。

  * CPUやメモリのみの修理で、データ再構築が不要な場合。

  * ディスクの修理が必要で、データ再構築が必要な場合。

それぞれ対応する操作手順を参照して処理してください。

## 前提条件

* 現在OCPにログインしているユーザーが以下の権限を持っていることを確認してください：

  * **クラスタメンテナンス** リソース権限。
  * クラスタ **<UI-TERM key="ocp-v2.Detail.Overview.Overview">概要</UI-TERM>** メニュー権限。
  * ホスト **<UI-TERM key="ocp-v2.Plan.Component.PlanTemplateTable.All">すべて</UI-TERM>** メニュー権限。

* OceanBaseクラスタ内でホスト障害が発生しています。OBServerノードの状態が利用不可で、かつホストの状態がオフラインの場合、通常はホストが障害によりダウンしています。

## 手順

### 交換用の予備マシンがある場合

1. OCPでホストを追加し、予備マシンを管理します。

2. **<UI-TERM key="ocp-performance-report.ReportTables.LockStatInfo.LatchStatTable.Cluster">クラスタ</UI-TERM>** > **<UI-TERM key="ocp-v2.Component.OBServerList.ObserverList">OBServerリスト</UI-TERM>** で、障害のあるOBServerノードを選択し、OBServerノードを交換します。

     <main id="notice" type='notice'>
     <h4>注意</h4>
     <p>
     <ul>
     <li>交換の手順は以下のとおりです：まず新しいOBServerノードを追加し、次にOBServerノードを削除します。交換対象のOBServerノードがオンライン状態である必要はありません。</li>
     <li>ホストがすでに障害を起こしているため、OBServerノードを交換する際には、ホストの運用操作をスキップするかどうか尋ねられます。<b>はい</b>を選択するだけです。</li>
     <li>OBServerノードを交換する前に、拡張したすべてのホストの時刻がOceanBaseクラスタの時刻ソースと一致しており、時刻のずれが10msを超えないことを確認する必要があります。確認方法：OceanBaseクラスタのRS Leaderホストで追加するホストのIPアドレスを指定してclockdiffを実行し、具体的な時刻のずれを確認します。</li>
     <li>新しいOBServerノードのリソース仕様は、交換されるOBServerノードのリソース仕様以上である必要があります。これにより、Unitとデータが完全に移行されることが保証されます（特別な要件については個別に評価する必要があります）。</li>
     </ul>
     </p>
     </main>

     <!-- ![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/%E6%9C%80%E4%BD%B3%E5%AE%9E%E8%B7%B5/%E6%9B%BF%E6%8D%A2observer.png) -->

    OBServerノードの削除タスクが長時間停止している場合、データの自動バランシングがデータ移行に影響を与えている可能性があります。以下のコマンドを参照して、<code>resource_soft_limit</code>パラメータを変更し、Unitのバランシングを無効にしてみてください。<code>resource_soft_limit</code>パラメータの詳細については、[resource_soft_limit](https://docs.oceanbase.com/oceanbase-database/V4.2.1-resource_soft_limit)を参照してください。

    ```SQL
    # クラスタのresource_soft_limitパラメータを確認し、このパラメータをロールバック設定に使用するために記録する
    show parameters like "%resource_soft_limit%";

    # Unitのバランシングを無効にする
    alter system set resource_soft_limit=100;
    ```

    データレプリケーションが遅く、ネットワーク帯域幅に余裕がある場合、データレプリケーションの並列パラメータを適切に引き上げて、移行を加速できます。

    ```SQL
    -- OceanBase V4.0より前のバージョンでは、以下のパラメータを使用してレプリカの移行速度を設定できます
    alter system set data_copy_concurrency = 100;
    alter system set server_data_copy_out_concurrency = 40;
    alter system set server_data_copy_in_concurrency = 40;

    -- OceanBase V4.0以降のバージョンでは、以下のパラメータを使用してテナントレベルのレプリカ移行速度を設定できます
    alter system set ha_high_thread_score = 80;
    alter system set ha_mid_thread_score = 80;
    ```

    パラメータの説明については、以下を参照してください：

    * OceanBase V4.0より前のバージョン：[data_copy_concurrency](https://docs.oceanbase.com/oceanbase-database/V4.2.1-data_copy_concurrency)、[server_data_copy_out_concurrency](https://docs.oceanbase.com/oceanbase-database/V4.2.1-server_data_copy_out_concurrency)、[server_data_copy_in_concurrency](https://docs.oceanbase.com/oceanbase-database/V4.2.1-server_data_copy_in_concurrency)。
    * OceanBase V4.0以降のバージョン：[ha_high_thread_score](https://docs.oceanbase.com/oceanbase-database/V4.2.1-ha_high_thread_score)、[ha_mid_thread_score](https://docs.oceanbase.com/oceanbase-database/V4.2.1-ha_mid_thread_score)。

      <main id="notice" type='notice'>
      <h4>注意</h4>
      <p>タスクが成功した後は、直ちにパラメータ値を元の設定に戻してください。クラスタ機能への影響を防ぐためです。</p>
      </main>

3. ホストリストから、オフラインの障害ホストを強制的に削除します。

### 交換用の予備マシンがない場合：CPUとメモリのみ修理、データ再構築は不要

1. **<UI-TERM key="ocp-v2.component.ParameterTemplate.Cluster">クラスタ</UI-TERM>** > **<UI-TERM key="ocp-v2.Component.OBServerList.ObserverList">OBServerリスト</UI-TERM>** で、障害のあるOBServerノードを停止します。

   **<UI-TERM key="ocp-v2.src.constant.oceanbase.StopProcess">プロセスを停止する</UI-TERM>** を選択してください。OBServerノードはすでに動作していないため、この手順は実際にはOCPに対し、OBServerノードが停止して修理中であることを認識させるだけです。

2. 障害ホストをシャットダウンして修理し、修理完了後にホストを起動します。

3. ホストの状態を確認します。ホストが依然として **<UI-TERM key="ocp-v2.src.constant.backup.Offline">オフライン</UI-TERM>** 状態の場合は、OCP-Agentを再インストールします。

   再インストール完了後、ホストの状態は **<UI-TERM key="ocp-v2.Backup.Component.RestoreNow.Online">オンライン</UI-TERM>** である必要があります。

4. **<UI-TERM key="ocp-v2.Detail.Component.RestartModal.Cluster">クラスタ</UI-TERM>** > **<UI-TERM key="ocp-v2.Component.OBServerList.ObserverList">OBServerリスト</UI-TERM>** で、OBServerノードを起動します。

   起動完了後、OBServerノードの状態は **<UI-TERM key="ocp-v2.Detail.Log.TaskGraph.Running">実行中</UI-TERM>** である必要があります。

### 交換用の予備マシンがない場合：データ再構築が必要

1. **<UI-TERM key="ocp-v2.Detail.Monitor.Cluster">クラスタ</UI-TERM>** > **<UI-TERM key="ocp-v2.Component.OBServerList.ObserverList">OBServerリスト</UI-TERM>** のリストから、障害のあるOBServerノードを削除します。

     <main id="notice" type='notice'>
     <h4>注意</h4>
     <p>以下の場合、OBServerノードの削除は失敗し、予備マシンを使用して処理する必要があります。
     <ul>
     <li>ゾーン内にOBServerノードが1台しかなく、そのノードにデータレプリカまたはユニットがある場合、OBServerノードの削除は失敗します。</li>
     <li>残りのOBServerノードがすべてのテナントのデータレプリカまたはユニットを収容できない場合、OBServerノードの削除は失敗します。</li>
     <li>残りのOBServerノードがデータの多数派要件を満たせない場合、OBServerノードの削除は失敗します。</li>
     </ul>
     </p>
     </main>

     <!-- ![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/%E6%9C%80%E4%BD%B3%E5%AE%9E%E8%B7%B5/%E5%88%A0%E9%99%A4observer1.png) -->

    OBServerノードの削除タスクが長時間停止している場合、データの自動バランシングがデータ移行に影響を与えている可能性があります。以下のコマンドを参照して、<code>resource_soft_limit</code> パラメータを変更し、ユニットの均等化を無効にしてみてください。<code>resource_soft_limit</code> パラメータの詳細については、[resource_soft_limit](https://docs.oceanbase.com/oceanbase-database/V4.2.1-resource_soft_limit)を参照してください。

    ```SQL
    # クラスタのresource_soft_limitパラメータを確認し、このパラメータをロールバック設定に使用するために記録します
    show parameters like "%resource_soft_limit%";

    # ユニットの均等化を無効にします
    alter system set resource_soft_limit=100;
    ```

    データレプリケーションが遅く、かつネットワーク帯域幅に余裕がある場合は、データレプリケーションの並列処理パラメータを適宜引き上げて、移行を加速できます。

    ```SQL
    # クラスタのデータレプリケーション並列処理パラメータを確認し、ロールバック設定に使用するためにこのパラメータを記録します。
    show parameters like "%data_copy_concurrency%";
    show parameters like "%server_data_copy_out_concurrency%";
    show parameters like "%server_data_copy_in_concurrency%";

    # 並列処理パラメータを引き上げます。
    alter system set data_copy_concurrency=100;
    alter system set server_data_copy_out_concurrency=40;
    alter system set server_data_copy_in_concurrency=40;
    ```

2. **<UI-TERM key="ocp-v2.page.Host.HostList">ホスト一覧</UI-TERM>** で、オフラインの障害ホストを強制的に削除します。

3. 障害ホストをシャットダウンして修理し、修理完了後にホストを起動します。

4. 修理後のホストをOCPに追加します。

5. OceanBaseクラスタにこのOBServerノードを再追加します。
