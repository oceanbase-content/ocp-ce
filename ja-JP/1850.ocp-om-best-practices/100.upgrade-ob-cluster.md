# OceanBaseクラスタのアップグレード

このセクションでは、OceanBaseクラスタをCLIでアップグレードする方法について説明します。

## 適用シナリオ

業務用OceanBaseクラスタのアップグレード。

## 前提条件

* OceanBaseクラスタのアップグレード前に、**<UI-TERM key="ocp-v2.src.constant.compute.Running">実行中</UI-TERM>**状態である必要があります。

* アップグレード前に、クラスタのメジャーコンパクション（OceanBaseクラスタがV4.0未満の場合）またはテナントのメジャーコンパクション（OceanBaseクラスタがV4.0以上の場合）が行われていないことを確認してください。

* アップグレード対象のOceanBaseクラスタがV4.0以前のバージョンの場合、アップグレードプログラムではsysテナントにプライマリゾーンの設定が必要です。OceanBaseクラスタがV4.0同士のアップグレード、またはV4.0からV4.1へのアップグレードの場合は、通常テナントにプライマリゾーンの設定が必要です。アップグレード対象のOceanBaseクラスタがV4.1以降のバージョンの場合、アップグレードプログラムではプライマリゾーンの設定は不要です。

* アップグレード対象のOceanBaseクラスタがV4.0以前のバージョンの場合、アップグレードプログラムではsysテナントのプライマリゾーンの第一優先ゾーン数が1つを超えてはなりません。これは、アップグレード中にシステムテーブルが分散されることで異常が発生する可能性があるためです。

* OceanBaseクラスタがV4.0未満のバージョンの場合、V4.0以下のバージョンへのアップグレードのみをサポートします。

## 技術的原理

OCPは、アップグレードの開始バージョンと終了バージョンに基づき、アップグレードパスファイルから最短のアップグレードパスを取得します。アップグレードパスファイルの一部の内容は以下のとおりです：

```SQL
- version: 2.2.74
  can_be_upgraded_to:
      - 2.2.75
- version: 2.2.75
  can_be_upgraded_to:
      - 2.2.76
- version: 2.2.76
  can_be_upgraded_to:
      - 2.2.77
- version: 2.2.77
  can_be_upgraded_to:
      - 2.2.78
  can_be_direct_upgraded_to:
      - 3.1.2
- version: 3.1.0
  can_be_upgraded_to:
      - 3.1.1
- version: 3.1.1
  can_be_upgraded_to:
      - 3.1.2
- version: 3.1.2
  can_be_upgraded_to:
      - 3.1.3
# ...
```

OCPでは、アップグレードパスの設定ファイルは以下の3箇所に保持されます：

1. OceanBase RPMパッケージをアップロードする際、OCPはRPMパッケージ内のアップグレードパスファイルを解析し、MetaDBに保存します。

2. OCPの作業ディレクトリ内の`./ocp-server/etc`パス下。

3. OCPのJARパッケージ内。

アップグレード前にOCPがアップグレードパスを取得する際は、1、2、3の順に照会し、元のバージョンからターゲットバージョンへのアップグレードパスを取得するまで続けます。

## 注意事項

* OceanBase V4.0は大幅な変更を伴うバージョンであり、アップグレード時にはV4.0を境に分けて行う必要があります。V4.0を跨いだアップグレードはサポートされません。

* OCP V4.0.0 ～ V4.0.2はOceanBase V4.0同士のアップグレードのみをサポートします。OCP V4.0.3以降はOceanBase V4.xシリーズのバージョンアップグレードをサポートします。

* ゾーンごとにローテーションでアップグレードする場合、任意のゾーンを停止した際にクラスタ内のすべてのテナントのレプリカが過半数を維持できるようにする必要があります。そうでない場合、アップグレードの事前チェックで失敗します。

* ゾーンごとにローテーションでアップグレードする場合、OCPはRootServiceノードが存在するゾーンを優先的にアップグレードします。

* 強制的なアップグレードは、クラスタ内のすべてのゾーンを並行してアップグレードするため、アップグレード処理中は業務が利用できなくなります。

OCPのバージョンと管理対象のOceanBaseクラスタのバージョンの互換関係は以下のとおりです：

| OceanBase バージョン | OCP バージョン |
|--------|---------|
| version < 4.0 | ALL |
| 4.0 <= version < 4.2 | version >= 4.0 |
| version >= 4.2 | version >= 4.2 |

## 手順

OceanBaseのアップグレード手順の詳細については、公式サイトの[バージョンアップグレード](https://www.oceanbase.com/docs/enterprise-oceanbase-ocp-cn-10000000002099472)を参照してください。

## よくある質問

Q1: アップグレード時に「バージョンaからバージョンbへのアップグレードパスが見つかりません」というエラーが発生しました。

A: まず、関連するOceanBaseテクニカルサポートにお問い合わせいただき、aからbへのアップグレードが可能かどうかご確認ください。bのバージョンがaよりも高い場合でも、aのリリース日がbより後であるためアップグレードできないことがあります。

アップグレードが可能であることが確認された場合、以下の2つの方法で解決できます。順番に試すことを推奨します：

1. OCP上でbのRPMパッケージを削除し、再度アップロードします。
2. OCPの作業ディレクトリに移動し、`./ocp-server/etc/oceanbase_upgrade_dep.yml`ファイルを確認し、aからbへのアップグレードパスが存在するかどうかを確認します。存在しない場合、bのRPMパッケージを解凍し、etcディレクトリ内の`oceanbase_upgrade_dep.yml`ファイルを確認し、そこに記載されているaからbへのパスをOCPの作業ディレクトリ内のアップグレードファイルにコピーします。

Q2: アップグレード時に「テナントxxのプライマリゾーンはRANDOMに設定できません」というエラーが発生しました。
A: OceanBaseのアップグレードでは、PrimaryZoneの設定に要件があります：

1. アップグレード対象のOceanBaseクラスタがV4.0以前のバージョンの場合、アップグレードプログラムはsysテナントにPrimary Zoneの設定が必要です。
2. OceanBaseクラスタがV4.0同士のバージョンアップグレード、またはV4.0からV4.1へのバージョンアップグレードの場合、一般テナントにPrimary Zoneの設定が必要です。
3. アップグレード対象のOceanBaseクラスタがV4.1以降のバージョンの場合、アップグレードプログラムはPrimary Zoneについて要件を設けていません。

Q3: アップグレード中に、アップグレードスクリプトが「current standby cluster not syncronizing!!!」というエラーを返しました。
A: プライマリ/スタンバイクラスタのアップグレード時には、ビジネステナントが存在する必要があります。OceanBaseのアップグレードスクリプトでは、プライマリ/スタンバイクラスタにビジネステナントが存在しない場合、スタンバイクラスタのcurrent_scnは常に0を維持する必要があります。しかし、実際のアップグレード処理では、スタンバイクラスタのcurrent_scnが0であってはならないとチェックされ、そうである場合はプライマリ/スタンバイ間で同期が取れていないと判断されます。

一時的な解決策：

1. プライマリ/スタンバイクラスタのsysテナントでそれぞれ`alter system end upgrade`を実行し、アップグレードモードを終了します。
2. 一時テナントを作成します。
3. スタンバイクラスタの`v$ob_cluster`ビューをクエリし、current_scnの値が現在のタイムスタンプに近づくのを待ちます。
4. プライマリ/スタンバイクラスタでそれぞれ`alter system begin upgrade`を実行し、アップグレードモードを再開します。
5. タスクを再試行します。

OCP V3.3.5バージョンでは、この問題に対処するための事前チェック項目が追加されています。アップグレード前に、クラスタ内にビジネステナントが存在するかどうかを事前に確認できます。
