# 自動インクリメント列の可用性チェック

このセクションでは、クラスタの自動インクリメント列の可用性をチェックする方法について説明します。

## 適用シナリオ

この点検項目は、既存のグローバルな自動インクリメント列が十分かどうかをチェックします。

## 前提条件

なし。

## 技術原理

OceanBaseは分散データベースであり、テーブルは通常複数の異なるマシンに分散配置されます。MySQLとの互換性を可能な限り保ちつつ、分散マシン環境での自動インクリメント列の生成パフォーマンスを保証する必要があり、その結果、自動インクリメント値の生成過程でジャンプが発生します。

OceanBase V4.xバージョンでは、`AUTO_INCREMENT_MODE`モードとして`ORDER`モードと`NOORDER`モードの2種類の自動インクリメント列が存在し、デフォルトは`ORDER`モードです。`show create table`を使用して、自動インクリメント列を含むテーブルの自動インクリメントモードを確認できます：

```sql
CREATE TABLE `T1` (
  `c1` int(11) NOT NULL AUTO_INCREMENT,
  `c2` smallint(6) DEFAULT NULL,
  PRIMARY KEY (`c1`)
) AUTO_INCREMENT = 1 AUTO_INCREMENT_MODE = 'ORDER'
```

OceanBase V4.xで`AUTO_INCREMENT_MODE = 'NOORDER'`を指定して作成されたテーブルや、OceanBase V4.0未満のバージョンで作成された自動インクリメント列を含むテーブルは、すべて`NOORDER`モードの自動インクリメントテーブルです。OceanBase V4.xでは`ORDER`モードの自動インクリメント列が新たに追加され、テーブル作成時のデフォルトモードとなり、MySQLの動作との互換性が向上しました。

## 手順

点検で自動インクリメント列の異常な増加（しきい値を急速に超えることで示される）が検出された場合、上記の2種類の自動インクリメント列モードについて調査が必要です。異なるモードではさまざまな自動インクリメント列のシナリオが存在するため、具体的なシナリオに基づいて問題の根本原因を特定し、解決することができます：

* **ORDER**

  * **シナリオ1：マシンの再起動またはダウン**

      `ORDER`モードはリーダーノードのメモリ内にキャッシュ区間を維持します。リーダーノードが再起動またはダウンした場合、その区間内で未使用の自動インクリメント値は引き続き使用されないため、ジャンプが発生します。

      <main id="notice" type='notice'>
      <h4>注意</h4>
      <p>ここでのジャンプシナリオはリーダーノードでのみ発生します。他のフォロワーノードはキャッシュを保存しないため、ダウンしても自動インクリメント値の生成連続性に影響しません。</p>
      </main>

  * **シナリオ2：リーダー切り替え**

      リーダー切り替えが発生した場合、往復切り替えによる自動インクリメント値の非増加問題を避けるために：
        1. 例えば、OBServer2の初期キャッシュが[1, 100]で、1、2を生成します。
        2. リーダーがOBServer1に切り替わり、OBServer1が新しいキャッシュ区間[101, 200]を取得して、101、102を生成します。
        3. 再びOBServer2に切り替えると、前回のキャッシュを再利用して3、4を生成します。これにより、101から3へ値が小さくなる問題が発生します。

* **NOORDER**

  * **シナリオ1：複数マシン・複数パーティションでの自動インクリメント値生成**

      `auto_increment_cache_size` を100と仮定し、パーティションテーブルが配置されているOBServer1、OBServer2、OBServer3がそれぞれ均等に `insert into values (null)` リクエストを受信した場合の動作を例示します：
        1. OBServer1は自身のキャッシュに値がないことを検出すると、内部テーブルから自動インクリメント区間[1, 100]を申請し、自動インクリメント値1を生成します。
        2. OBServer2は自身のキャッシュに値がないことを検出すると、内部テーブルから自動インクリメント区間[101, 200]を申請し、自動インクリメント値101を生成します。
        3. OBServer3は自身のキャッシュに値がないことを検出すると、内部テーブルから自動インクリメント区間[201, 300]を申請し、自動インクリメント値201を生成します。
        4. OBServer1はキャッシュ[2，100]を使用して自動インクリメント値2を生成します。
        5. OBServer2はキャッシュ[102，200]を使用して自動インクリメント値102を生成します。
        6. ...

      このように、テーブル内へのデータ挿入順序は1、101、201、2、102、...となり、自動インクリメント値が常にジャンプしていることがわかります。

  * **シナリオ2：INSERTで指定された最大値を挿入する**

      MySQLの動作では、自動インクリメント列に明示的に指定値を挿入すると、その後生成される自動インクリメント値はその値より小さくなりません。

      OceanBaseの分散シナリオでは、OBServer自身が現在最大値が挿入されたことを認識するだけでなく、他のサーバーや内部テーブルにも同期する必要があります。この同期処理は非常に時間がかかるため、毎回指定された最大値に対して同期操作を行うことを避けるために、最大値を挿入する際には現在のキャッシュを破棄します。これにより、現在の値から次のキャッシュ値に至るまでの範囲で同期を行う必要がなくなります。

      パーティションテーブルが配置されているOBServer1、OBServer2、OBServer3がそれぞれ均等に明示的に指定されたインクリメントシーケンス(1, 2, 3, ...)のリクエストを受信した場合、および元々すべてキャッシュを持っていると仮定した場合の動作です：

      1. OBServer1は1を受信し、キャッシュ[1，100]を破棄し、内部テーブルから新しいキャッシュ区間[301，400]を取得し直し、101をsync値として内部テーブルおよび他のOBServerに同期します。
      2. OBServer2は2を受信し、現在のキャッシュ区間[101，200]より小さいことを検出し、操作を行いません。
      3. OBServer3は3を受信し、現在のキャッシュ区間[201，300]より小さいことを検出し、操作を行いません。
      4. OBServer1は4を受信し、現在のキャッシュ区間[301，400]より小さいことを検出し、操作を行いません。
      5. ...

      このように、一部の値を挿入した後に自動インクリメント列を使用してシーケンスを生成し続けると、ジャンプが発生します。例えば、OBServer1の最初の区間[1，100]を使用せずに直接301にジャンプします。この問題は単一マシンのシナリオでも発生します：

      ```sql
      obclient> create table t1 (c1 int not null auto_increment);
      obclient> insert into t1 values (null);
      obclient> insert into t1 values (3);
      obclient> insert into t1 values (null);
      obclient> select * from t1;
      +-----+
      | c1  |
      +-----+
      |   1 |
      |   3 |
      | 104 | -- cache sizeサイズ分ジャンプ
      +-----+
      3 rows in set (0.05 sec)
      ```

  * **シナリオ3：マシンの再起動またはダウン**

      自動インクリメント列のキャッシュはメモリ構造であり、OBServerが再起動またはダウンした場合、使用されていない区間は内部テーブルに書き戻されません。その結果、この区間は再利用されなくなります。例えば、OBServer1の初期の自動インクリメント列キャッシュ区間が[1，100]で、既に1、2が生成されていたとします。この時点でダウンが発生し、再起動後には新しい区間[101，200]になります。次の自動インクリメント値は101となり、シーケンス1、2、101、...がジャンプします。

  * **シナリオ4：プライマリ切り替え**

      OceanBase V4.0未満のバージョンでは、自動インクリメント列は連続性を保証しませんが、パーティション内で値が増加することは保証されます。この動作を保証するため、プライマリ切り替えのたびに現在のキャッシュ区間を破棄します。これにより、マシンの再起動に似た自動インクリメント値のジャンプが発生しますが、詳細は省略します。
