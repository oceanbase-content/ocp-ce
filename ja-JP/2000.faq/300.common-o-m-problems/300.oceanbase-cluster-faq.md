# OceanBaseクラスタのよくある質問
このセクションでは、OceanBaseクラスタ管理に関連するよくある質問について説明します。

## 機能の実装

**Q1: X86環境のOCPは、ARMアーキテクチャのOceanBaseクラスタを管理できますか？**
A: OCP V2.5.2以降のバージョンがサポートしています。

**Q2: OCPは、OceanBaseのプライマリクラスタがX86、スタンバイクラスタがARMのデプロイメント計画をサポートしますか？**

A: OCP V3.1.0以降のバージョンがサポートしています。

## OceanBaseクラスタ管理

**Q1: プライマリ/スタンバイクラスタのレイテンシはどこで確認できますか？**

A：クラスタ概要に移動し、クラスタトポロジーダイアグラムに切り替えて、ダイアグラム上でプライマリ/スタンバイクラスタ間のレイテンシを確認します。
**Q2: タスクエラー `machine resource is not enough to hold a new unit` が発生した場合、どう対処すればよいですか？**

A：マシンのリソース不足により、レプリカ移行などの運用保守タスクが正常に実行できません。ホストを追加することで問題を解決できます。

**Q3: OCP-Agentがobserver.logを自動的にクリーンアップするクリーンアップポリシーは何ですか？**

A： スペース使用率が80%に達すると、最新の100件のログレコードのみが保持されます。

**Q4: クラスタのトポロジーダイアグラムの状態はどのように取得されますか？**

A: 状態はMetaDB内のob_serverテーブルレコードから取得されます。

**Q5: OCPのセッション総数はどのように集計されますか？**

A: OceanBase内部テーブル__all_virtual_processlistからクエリします。

**Q6: 非アクティブセッションとは何ですか？管理メカニズムは何ですか？**

A: 接続後一定時間操作がないセッションは非アクティブセッションです。デフォルトでは28800秒間操作がないセッションはinactive状態にマークされます。クライアントのタイムアウトによる接続解放に依存しており、OceanBaseは積極的に接続を解放しません。

**Q7: inactiveのセッションはUnitの最大接続数を消費しますか？**

A: Unitの最大接続数は実際の接続数の割り当てには影響しません。実際に有効なのはOBServerの接続数の上限であり、OCPはUnit接続数を用いてアラートを出します。

**Q8: OCPとOceanBaseが異なるネットワークセグメントにある場合、どのポートを開放する必要がありますか？**

A: 詳細は[コンポーネントリスニングポートリスト](../../2100.appendix/400.component-listening-port-list.md)を参照してください。

**Q9: 失敗したタスクがあるクラスタを迅速に削除する方法は何ですか？**

A: MetaDBのob_clusterテーブルにおけるクラスタの状態`Operating`を`NORMAL`に変更します。

**Q10: OceanBaseクラスタのヘルス巡回検査の結果説明に `ゾーンレプリカ数：unknown > 100000、重大` と表示されていますが、これはどういう意味ですか？**

A: unknownは、パーティション数の取得に失敗したことを示します。以下の順序で原因を調査することをお勧めします：

1. OceanBaseクラスタ内の**<UI-TERM key="ocp-v2.src.util.menu.TenantManagement">テナント管理</UI-TERM>**画面の**容量_パーティション数**グラフに関連データが表示されていないか確認します。

2. 対応するホストの**<UI-TERM key="ocp-v2.Host.Detail.OCPAgent.Processes">プロセス一覧</UI-TERM>**でプロセスが正常に動作しているか確認し、obstatとlogtailerプロセスが異常終了していないか確認します。

3. ドメイン名解決に問題があり、ホストがデータベースにアクセスできず、obstatとlogtailerの起動に失敗している可能性があります。

エラーが発生したホストの`/etc/resolve.conf`にDNSサーバーのアドレスを設定してから再度確認することをお勧めします。

**Q11: OCPでクラスタの削除を実行することも中止することもできません。何が原因ですか？**

A: ユーザーがCLIでOBServerクラスタのホストを削除したため、そのホストが異常オフラインとなり、MetaDBに保存されているクラスタ情報がOceanBaseクラスタ内の情報と一致しなくなりました。OceanBaseクラスタ内に個別のOBServerがオフラインの場合、クラスタの強制削除は推奨されません。このような場合は、テクニカルサポートエンジニアに連絡し、MetaDB内の関連データを手動で修正することをお勧めします。

**Q12：OCPをアップグレードした後、特定のOceanBaseクラスタのproxyroパスワード設定が失われ、そのクラスタが使用不能になり、クラスタの再起動も失敗します。どう対処すればよいですか？**

A：OCPを再起動すれば解決します。

## OceanBaseクラスタのデプロイ

**Q1: 新規クラスタ作成時にillegal argument exceptionエラーが発生しました。どう解決しますか？**

A: RPMパッケージ名が重複していないか確認してください。

**Q2: OceanBaseのインストール時に、コミット情報の確認画面で`未知のエラーが発生しました。エラー原因：{0}、エラーメッセージ：{1}、管理者に連絡してください`というエラーが表示されました。何が原因ですか？**
A: 使用しているOceanBaseソフトウェアパッケージの名前が変更されていないか確認してください。

**Q3: プライマリクラスタはX86、追加予定のスタンバイクラスタのホストはAArch64で、デプロイするスタンバイクラスタではX86ソフトウェアパッケージを使用します。可能ですか？**

A：異種プラットフォームのプライマリ/スタンバイクラスタにはリスクが伴います。異種デプロイは推奨されません。

**Q4: OCPを使用してクラスタを作成する際に`zone優先順位が不正です`というエラーが発生しました。何が原因ですか？**

A: 最高優先順位のZoneに対応するRegionには、少なくとも2つのZoneが存在している必要があります。

**Q5: OCPを使用してスタンバイデータベースを作成しますが、このスタンバイデータベース作成タスクが終了した時点でデータのプライマリ/スタンバイ同期も完了しますか？**

A: 現在、スタンバイデータベース作成タスクの所要時間とスタンバイデータベースの同期開始時刻との間に直接的な関係はありません。ただし、スタンバイデータベース作成タスクが完了して初めて、そのスタンバイデータベースは外部へのサービス提供が可能になります。

**Q6: OCP V2.5.xバージョンでプライマリ/スタンバイデータベースを作成する際、tenantとtableのprimary_zoneをRANDOMに設定しましたが、タスク実行時に`Add cluster not allowed`というエラーが発生し、`CHECK PRIMARY ZONE OR LOCALITY CONFIG`というメッセージが表示されました。何が原因ですか？**

A：ユーザーテーブルにprimary_zoneまたはlocalityが設定されています。以下の方法を参考に修正してください：

1. システムテナントのOceanBaseデータベースで、primary_zoneまたはlocalityが設定されているテーブルを確認します。

```sql

select table_id,tenant_id,primary_zone,locality,table_name from __all_virtual_table；

```

primary_zoneまたはlocalityが設定されたテーブル名をt、テナントIDを1001とします。

   2. 対応するテナントのデータベースで `alter table t set primary_zone = default;` を実行し、テーブルレベルのプライマリゾーン設定を解除します。
   3. 対応するテナントのデータベースで以下のステートメントを実行し、テーブルレベルのローカリティ設定を解除します。
   ```sql

   select locality from __all_tenant where tenant_id = 1001;     #クエリ結果が F@zone1,F@zone2,F@zone3 であることを記録します。

alter table t set locality = 'F@zone1,F@zone2,F@zone3'；

```

   **Q7: プライベートクラウドの同一ネットワーク環境において、既にOceanBaseを構築したOCPが一式存在します。新たにOCPを一式デプロイし、その上にOceanBase V2.2.7xを構築する場合、OCPデプロイ時に `/root/t-oceanbase-antman/obcluster.conf` の `cluster_id` のデフォルト値を `100000` に変更する必要がありますが、ビジネスクラスタ作成時に、他に変更が必要な点はありますか？**
   A: OCPを使用してOceanBaseクラスタを作成する際、clusteridとclusternameの値は一意である必要があります。
   **Q8: 新規クラスタのDo io benchサブステップで失敗した場合、どのようにトラブルシューティングしますか？**
   A: `io bench` 失敗で返されたエラーコードを確認します。エラーコードが87の場合、通常はホストのリソース不足が原因です。ディスクに100GiBの利用可能空き容量を確保する必要があります。

## OceanBaseクラスタの引き継ぎ

**Q1: クラスタをインポートする際、ホスト準備タスクで `python 依存関係が存在しない` と報告されました。どのように解決しますか？**

A：ホストのセットアップにインストールテンプレートを使用せず、Pythonスクリプトを手動でインストールしたことが原因です。正規のインストールテンプレートを使用したインストールを推奨します。

**Q2: OCP V2.5.xを使用してクラスタを引き継ぐ際、`error code:11042 クラスタ引き継ぎ事前チェック失敗、失敗原因：OBServerノードチェックに合格しない` というエラーが発生しました。どのように解決しますか？**

A: 事前チェックインターフェースを使用して、OBServerノードチェックに合格しない具体的な原因を確認することを推奨します。インターフェースメソッドの呼び出しは以下のとおりです：
```shell

curl -X POST --user admin:xxx \

-H "Content-Type:application/json" \

-d '{"rootSysPassword":"xxxxx",                   #必須、root@sysパスワード。

"address":"xxxxx",                                 #必須、クラスタ接続アドレス。

"port":2888,                                           #必須、クラスタ接続ポート。
"connectionMode": "proxy"                  #オプション、接続モード。指定可能な値はdirect | proxy、デフォルトはdirect。
  "clusterName": "xxx",                            #オプション、接続モードがproxyの場合は必須。
  "obClusterId": xxx                                 #オプション、接続モードがproxyで、引き継がれるクラスタがスタンバイクラスタの場合は必須。
         }' \
         "http://example.com:8080/api/v2/ob/clusters/takeOverPreCheck"
```

**Q4：OCPが他のOCPでデプロイされたクラスタを引き継ぐ際の注意点は何ですか？**
         A：OCPが他のOCPでデプロイされたクラスタを引き継ぐ際には、以下の点に注意してください：
        * 引き継ぐOceanBaseクラスタへのビジネスアクセス方法を確認し、クラスタ引き継ぎがビジネスに与える影響を確認する必要があります。
  * 引き継ぐクラスタを他のOCPから移出するか、他のOCPを停止する必要があります。
* 単一OCPシナリオでクラスタを引き継ぐ場合は、まずOceanBaseプライマリクラスタを引き継ぎ、その後OceanBaseスタンバイクラスタを引き継ぐ必要があります。

* OCPマルチクラスタシナリオでクラスタを引き継ぐ場合は、まず任意のOCPでOceanBaseプライマリクラスタを引き継いだ後、任意のOCPでOceanBaseスタンバイクラスタを引き継ぐ必要があります。

## OceanBaseクラスタのアップグレード

**Q1: プライマリ/スタンバイクラスタはどのようにアップグレードしますか？**

A: プライマリクラスタとスタンバイクラスタの概要ページの右上には、**<UI-TERM key="ocp-v2.Topo.TopoGraph.UpgradedVersion">バージョンをアップグレード</UI-TERM>**ボタンがあります。プライマリクラスタでもスタンバイクラスタでも、このエントリからプライマリ/スタンバイクラスタ全体のアップグレード操作を開始できます。

**Q2: OCPでOceanBaseクラスタをアップグレードする際、schema infoを更新すると`timeout`エラーが発生します。どう解決しますか？**

A: 以下のコマンドを実行して、スキーマとバージョンを確認します：

```code
select tenant_id, refreshed_schema_version from __all_virtual_server_schema_info " + " where svr_ip = '%s' and svr_port = %d and refreshed_schema_version >
select max(value) value from oceanbase.__all_virtual_sys_parameter_stat where name = 'min_observer_version'
```


確認後、手動で`CheckRefreshSchemaTask`を再試行します。

**Q3: OceanBaseクラスタをアップグレードする際、execute upgrade checkerでエラーが発生します。なぜですか？**

A: RPMパッケージのダウンロードがタイムアウトした可能性があります。再試行をお勧めします。

**Q4: OceanBase V2.2.71からOceanBase V2.2.74にアップグレードする際、`対応するバージョンノードが存在しません`というエラーが発生します。何が原因ですか？**

A: OCPマシン上の`/home/admin/ocp-server/etc/oceanbase_upgrade_dep.yml`ファイルで定義されているアップグレードパスが不完全です。バージョン情報をOceanBase V2.2.74まで補完することをお勧めします。例：



```yaml
#前略
- version: 2.2.70
  can_be_upgraded_to:
      - 2.2.71
- version: 2.2.71
  can_be_upgraded_to:
      - 2.2.72
- version: 2.2.72
  can_be_upgraded_to:
      - 2.2.73
- version: 2.2.73         # 最後のバージョンも定義する必要があります。定義しないと、同じバージョンへのアップグレード時にパスが見つかりません。今後も最後のバージョンは同様に定義してください。   欣煦
  can_be_upgraded_to:
      - 2.2.74
```
  **Q5: OceanBaseクラスタのアップグレードパス確認画面で`binaryを置き換える必要があります`と表示されますが、これはどういう意味ですか？**
      A: binaryを置き換えるとは、OBServerノードを置き換えることを指します。V2.2.72とV2.2.73では、プレ/ポストスクリプトを実行するだけで、OBServerノードのbinaryファイルを置き換える必要はありません。この表示はあくまでヒントであり、ユーザーが手動で操作する必要はありません。アップグレードタスクは自動的に置き換えを完了します。
**Q6: OceanBaseクラスタをアップグレードする際、`[alter system stop zone ?]; SQL state [25000]; error code [4012]; Statement is timeout`というエラーが発生します。どう解決しますか？**
  A: 再試行をお勧めします。
      **Q7: OceanBaseクラスタをV2.2.30からV2.2.50にアップグレードする際に失敗しました。原因は何ですか？**
A: OceanBaseのアップグレードに依存するV2.2.40バージョンのRPMパッケージがアップロードされていません。アップロードしてから再試行することをお勧めします。

**Q8: 顧客はマイナーバージョンをアップグレードしてからメジャーバージョンをアップグレードする必要がありますが、OCPは同一バージョンでのアップグレードをサポートしますか？**

A: サポートしますが、マイナーバージョン番号は異なる必要があります。

**Q9: OCPを使用してOceanBaseクラスタをアップグレードする際、`Install rpm` ステップで1台のマシンが失敗し、`Cannot allocate memory` エラーが発生しました。**

A: メモリ不足です。実際の状況に応じて、メモリのクリーンアップまたは拡張を選択することを推奨します。

**Q10: OceanBaseクラスタをアップグレードする際、`upgrade_checker.py` が `MyError: "(1, Decimal('1.0000')) check_logonly_replica_unit failed, not found log_type resource_pool for this tenant` エラーを返しました。原因は何ですか？**

A: アップグレード対象のOceanBaseクラスタにログ型レプリカが存在するかどうかを確認してください。存在する場合は、ログ型レプリカをFレプリカに置き換えることを推奨します。

**Q11: OceanBaseクラスタにsys、ocp-meta、ocp-monitorテナントの他にomsmetaやodpmetaテナントがある場合、どのようにアップグレードすればよいですか？**

A: OceanBaseのテクニカルサポートに連絡し、アップグレードマニュアルを取得して通常通りアップグレードを実行してください。あるクラスタのアップグレードは他のアプリケーションのテナントに影響しません。

## OceanBaseクラスタ監視

**Q1: OCPでクラスタを作成する際、ocp_monitorユーザーは自動的に作成されますか？このユーザーのデフォルトパスワードは何ですか？**

A: ocp_monitorユーザーは自動的に作成されますが、このユーザーのデフォルトパスワードは、システムがモニタリング時にこのユーザーを呼び出すためにのみ使用され、ユーザーが意識する必要はありません。

**Q2: クラスタ内のパフォーマンス監視画面におけるトランザクションログ時間は、SQLの平均時間を指すのでしょうか、それともトランザクションの平均時間を指すのでしょうか？**

A: トランザクションです。

**Q3: OCPにおけるプライマリ/スタンバイデータベース間の非同期ログ転送遅延は、どのように統計されますか？**

A: OCPのプライマリ/スタンバイデータベース間の非同期ログ転送遅延のデータソースは以下のとおりです：

```sql
SELECT cluster_id, cluster_name, created, cluster_role, cluster_status, current_scn, standby_became_primary_scn, primary_cluster_id, (time_to_usec(now(6)) - current_scn)/1000000 as delay_time FROM oceanbase.v$ob_cluster
```


すなわち `(time_to_usec(now(6)) - current_scn)/1000000`、単位は秒です。

## クラスタ巡回検査

**Q1: OceanBaseの `/data/1` データディスクはデフォルトでホストディスクの最大90%を占有できますが、クラスタ健全性巡回検査におけるホストディスク使用率のしきい値は85%に設定されています。これは適切ですか？**

A: 健全性巡回検査では、OceanBaseデータディスクの巡回検査は無視されます。
