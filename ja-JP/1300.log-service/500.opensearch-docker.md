# OpenSearch関連の説明

## 背景

OceanBase V4.xバージョンのエンドツーエンド・トレース機能をサポートするため、OCP V3.3.0ではデータプラットフォーム機能が新たに追加されました。これにはエンドツーエンド・トレースやログ検索などの機能が含まれており、これらの機能はOpenSearchクラスタに依存してデータの保存とクエリを実行します。また、プライベートクラウドの出力シナリオにおいても、OCPクラスタと同時にOpenSearchクラスタをデプロイすることがより便利になり、サポート担当者のデプロイメント学習コストを効果的に削減できます。

## 前提条件

**クラスタ仕様評価** を参照し、OpenSearchクラスタのリソース計画を立てていること。

## OpenSearchクラスタのデプロイ

1. まず、OCPホスト上でOpenSearchのDockerイメージを取得する必要があります。実際の状況に応じて以下のコマンドを実行して必要なイメージを取得できます。イメージのダウンロードについては、デリバリーサービス担当者にお問い合わせください。

   <main id="notice" type='explain'>
    <h4>説明</h4>
    <p>現在のイメージの最新バージョンはV3.3.2です。</p>
   </main>

    ```shell
    docker pull oceanbase/opensearch:3.3.2
    ```

2. Dockerを使用してOpenSearchをデプロイします。

    1. ルート証書の生成

        ```shell
        cd ${pem-path}
        openssl genrsa -out ./root-ca-key.pem 2048
        openssl req -new -x509 -sha256 -key ./root-ca-key.pem -subj "/C=CA/ST=ONTARIO/L=TORONTO/O=ORG/OU=UNIT/CN=ROOT" -out ./root-ca.pem
        ```

    2. コンテナの起動。

        ```shell
        docker run -d --net host -v ${pem-path}/root-ca-key.pem:/opt/opensearch/config/root-ca-key.pem -v ${pem-path}/root-ca.pem:/opt/opensearch/config/root-ca.pem --env  OPENSEARCH_USERNAME=xxx --env OPENSEARCH_PASSWORD=xxx --env OPENSEARCH_NODE_URLS=ip1,ip2,ip3 --env HOST_IP=xxx.xxx.xxx.xxx --env OPENSEARCH_JVM_HEAP=4g --name ocp-opensearch reg.docker.alibaba-inc.com/oceanbase-platform/ocp-opensearch:3.3.2-x64
        ```

        <main id="notice" type='notice'>
          <h4>注意</h4>
          <ul>
          <li>OpenSearchのDockerイメージは、hostネットワークモードで起動する必要があります。</li>
          <li>コンテナ起動コマンド内の${pem-path}は、ルート証書が保存されているディレクトリを指します。</li>
          <li>ホストのディレクトリをOpenSearchのディレクトリにマウントする場合は、まずホストのマウントディレクトリの権限をadminに設定する必要があります。コンテナ内のadminユーザーのuidとgidはどちらも500です。ホストのadminユーザーIDと一致しない場合はマウントに失敗します。この問題を解決するには、コンテナ起動後、コンテナ内で<code>chown admin:admin /data/1/opensearch</code>を実行してからコンテナを再起動してください。</li>
          <li>複数ノードのデプロイメントでは、ルート証書を各ノードにコピーしてから起動操作を行う必要があります。</li>
          </ul>
        </main>

    イメージ起動時の関連環境変数の説明は以下の通りです：

    | 環境変数 | 必須 | 説明 |
    |---------|--------|-------|
    | OPENSEARCH_USERNAME | 必須 | OpenSearchのユーザー名であり、cerebroへのログインユーザー名でもあります。 |
    | OPENSEARCH_PASSWORD | 必須 | OpenSearchのパスワードであり、cerebroへのログインパスワードでもあります。 |
    | OPENSEARCH_NODE_URLS | 必須 | OpenSearchノードのリスト。 |
    | HOST_IP | 任意 | ホストIPアドレス。実際のIPアドレスに基づいて入力してください。指定しない場合、`hostname -i` で取得されます。`/etc/hosts` が正しく設定されていることを確認してください。 |
    | OPENSEARCH_JVM_HEAP | 任意 | OpenSearchのJVMメモリ。ノードメモリの半分（最大32GB）に設定することを推奨します。デフォルトは4GBです。 |
    | OPENSEARCH_HTTP_PORT | 任意 | OpenSearchが外部と通信するポート。デフォルトは9200です。 |
    | OPENSEARCH_TCP_PORT | 任意 | OpenSearchノード間で通信するポート。デフォルトは9300です。 |
    | CEREBRO_PORT | 任意 | cerebroポート。デフォルトは9100です。 |
    | ELASTICSEARCH_EXPORTER_PORT | 任意 | elasticsearch_exporterポート。デフォルトは9114です。 |

3. OCPがOpenSearchに接続します。

    OCP起動後、**<UI-TERM key="ocp-v2.src.util.menu.SystemParameters">システムパラメータ</UI-TERM>** でOpenSearchのアドレスとアカウント情報を手動で追加する必要があります。詳細は [リンククエリ関連パラメータの設定](../1300.log-service/300.configuration-trace-paremeters.md) を参照してください。

    |パラメータ名|説明|
    |----|----
    |ocp.analyze.es.client.addresses|構築したopensearchクラスタのアドレス。複数のエントリ（client）アドレスがある場合は、カンマで区切ってください。   |
    |ocp.analyze.es.client.username|構築したopensearchクラスタのユーザー名。   |
    |ocp.analyze.es.client.password|構築したopensearchクラスタのパスワード。     |

## OpenSearchサービスの説明

OCP-OpenSearchのDockerイメージには、opensearch、elasticsearch_exporter、cerebroの3つのサービスが統合されています。

### OpenSearch

OpenSearchは、Apache Luceneをベースとしたコミュニティ主導の分散型検索・分析エンジンです。ES 7.10.2から派生し、プロトコルはApache License 2.0です。
OpenSearchにデータを追加した後、全文検索を実行できます。フィールド検索、複数インデックスの検索、フィールドの昇順・降順、結果のスコア順・フィールド順での並べ替え、および結果の集計などが可能です。

### elasticsearch_exporter

elasticsearch_exporterは、OpenSearchの各種メトリクスをPrometheus形式でエクスポートするエクスポーターであり、ocp/prometheusに統合されています。オープンソースライセンスはApache License 2.0です。
elasticsearch_exporterを使用することで、インデックスのパフォーマンス、JVMメモリ使用量とガベージコレクション、クラスタの健全性とノードの可用性、システムおよびネットワークメトリクスなど、OpenSearchの監視データを取得できます。

### cerebro

cerebroはOpenSearch管理ツールであり、Webページを通じてOpenSearchの運用保守操作を行うことができます。インデックスの作成と削除、クラスタ設定パラメータの変更などをサポートしています。このソフトウェアもオープンソースで、ライセンスはMIT License 2.0です。

### ログの場所

ログディレクトリ：`/home/admin/logs`。

## OpenSearchクラスタ仕様の見積もり

### ディスク容量

ディスク容量に影響を与える要因は以下のとおりです：

* レプリカ数。
* インデックスのオーバーヘッド：通常、ソースデータの10%大きくなります。
* オペレーティングシステムの予約：デフォルトで5%の領域が予約されます。
* OpenSearch内部のオーバーヘッド：セグメントのメジャーコンパクションやログなどの内部処理のため、一般的に20%を予約します。
* セキュリティのための余裕：一般的には少なくとも20%の余裕を確保することが望ましいです。

上記の要素から、最小ディスクサイズ = ソースデータ量 × (1 + レプリカ数) × 1.7 と算出されます。この公式を用いてディスク容量を管理することができます。

### CPUとメモリ

OpenSearchの計算リソースは主に書き込みとクエリで消費されるため、CPUの要件はそれほど高くありません。メモリは16GB、32GB、または64GBを推奨します。同時にOpenSearchに割り当てるメモリは、システムの利用可能なメモリの半分を超えず、かつ32GBを超えないようにしてください。

### シャードの評価

シャードのサイズと数は、OpenSearchクラスタの安定性とパフォーマンスに影響を与える重要な要素の一つです。

割り当ての推奨事項は以下の通りです：

* シャードを割り当てる前に、OpenSearchのデータテストを実施してください。データ量が非常に多い場合は、書き込み量を減らしてOpenSearchの負荷を軽減するため、マルチマスター1レプリカを選択することを推奨します。データ量が少なく、書き込み量も比較的少ない場合は、シングルマスターマルチレプリカまたはシングルマスター1レプリカを使用できます。
* 1シャードあたりのストレージ容量は30GB以内（最適）に保つことを推奨します。特別な状況下では50GB以内に引き上げることができます。過大または過小は避けてください。過大だとESの障害回復速度が遅くなり、過小だと非常に多くのシャードが発生し、各シャードが一定量のCPUとメモリを消費するため、読み書き性能の低下やメモリ不足などの問題が発生します。評価結果がこの容量を超える場合は、インデックス作成前に適切にシャードを割り当て、後からreindexを行うことを推奨します。これによりダウンタイムを回避できますが、時間がかかります。
* シャードの個数（レプリカを含む）は、データノード数に等しくするか、データノード数の整数倍にすることを推奨します。これにより、シャードがすべてのノードに均等に分散し、ロードバランシングが図れます。

### OB OpenSearchクラスタの見積もり

1オブザーバーの1日あたりのログ量は約6～8GBです。トレース機能はまだ開発中で、仮に8GBとして計算します。データはOpenSearch内で1週間保存されます。したがって、1台のオブザーバー、レプリカ数1、データ保存期間7日の場合、必要なOpenSearchのディスク容量は380GBです。したがって、クラスタのデプロイメント仕様は以下の表の通りです：

| オブザーバー数 | OSクラスタ規模 | ノード仕様 | ディスク容量 |
|---------------|------------|---------|----------|
| 20 | 4 | 8コア32GB | 2TB |
| 50 | 10 | 8コア32GB | 2TB |
| 200 | 20 | 16コア64GB | 4TB |
| 400 | 40 | 16コア64GB | 4TB |
