# XAトランザクションと一時停止トランザクションの診断

本記事では、OceanBaseデータベースのトランザクション診断方法について説明します。

## 基本情報

OceanBaseデータベースのトランザクションは、参加者の数と位置に基づいて、通常トランザクション、分散トランザクション、XAトランザクションの3種類に分類されます。通常トランザクションと分散トランザクションは、非XAトランザクションと総称することもあります。
また、トランザクションは実行時間と状態に基づいて、他のトランザクション、長時間トランザクション、一時停止トランザクションの3種類に分類されます。長時間トランザクションと一時停止トランザクションは、リソースが長時間解放されず、待機セッションが長時間ブロックされることで、業務システムに影響を与えます。日常業務では、このような異常なトランザクションに重点的に注目する必要があります。以下では、これらのトランザクションについて個別に説明します。

## シナリオの概要

### 長時間トランザクション

長時間トランザクションとは、長時間コミットされていないトランザクションを指します。通常トランザクション、分散トランザクション、XAトランザクションがすべて長時間トランザクションの状態になる可能性があります。通常トランザクションや分散トランザクションが長時間トランザクションの状態にある場合は、kill sessionによってトランザクションをロールバックできます。XAトランザクションが長時間トランザクションの状態にある場合は、XAトランザクションを終了できます。

長時間トランザクションが発生する原因は、トランザクション内の特定のSQLの実行時間が長い場合、またはSQLの実行後にコミットまたはロールバックが長時間完了しない場合があります。現在の長時間トランザクションがシステムのリソースをブロックしている場合は、通常の長時間トランザクションセッションをロールバックするか、XAトランザクションを終了することで対処できます。

#### コマンドラインを使用したセッション管理

<main id="notice" type='explain'>
    <h4>説明</h4>
    <p>以下のコード例は、特に指定がない限り、デフォルトでsysテナントを使用します。</p>
  </main>

1. データベース内に長時間トランザクションが存在するかどうか確認します。

   ```sql
   SELECT * FROM OCEANBASE.__all_virtual_trans_stat WHERE part_trans_action <= 2 AND ctx_create_time < date_sub(now(), INTERVAL 600 SECOND) AND is_exiting != 1
   ```

2. トランザクションがXAトランザクションかどうかを確認します。ここで、トランザクションIDは上記のSQLで取得した`svr_ip`です。SQLの実行結果が空の場合、長時間トランザクションは非XAトランザクションです。実行結果がある場合、その結果が対応するXAトランザクションです。

   ```sql
   SELECT * FROM OCEANBASE.__all_virtual_global_transaction WHERE trans_id LIKE '%トランザクションID%';
   ```

3. 長時間トランザクションを処理するには、以下のコマンドを実行してください。

   1. 通常の長時間トランザクションをロールバックします。注意：killセッションは対応するOBServerノードに直接接続する必要があり、プロキシ経由でデータベースに接続する必要はありません。

      ```sql
      SELECT svr_ip FROM OCEANBASE.__all_virtual_processlist WHERE id=セッションID;
      kill セッションID;
      ```

   2. XAトランザクションを終了するには、以下のコマンドを実行してください。

      1. システムテナントに移動し、XAトランザクションのXIDを検索します。

         ```sql
         SELECT hex(gtrid),hex(bqual),format_id FROM OCEANBASE.__all_virtual_global_transaction WHERE tenant_id = テナントID AND format_id <> -2 AND state = 3 AND gmt_modified < date_sub(now(), INTERVAL 1800 SECOND);
         ```

      2. Oracleテナントの場合は、一般テナントに移動してXAトランザクションのXIDを確認できます。

         ```sql
         SELECT rawtohex(gtrid),rawtohex(bqual),format_id FROM sys.all_virtual_tenant_global_transaction_agent WHERE format_id <> -2 AND state = 3 AND ROUND((sysdate - cast(GMT_MODIFIED as date)) * 86400) > 1800;
         ```

         一般テナントに移動し、XAトランザクションを終了します。

         ```sql
         set
           serveroutput on;
         declare
           l_xid DBMS_XA_XID;
           l_ret PLS_INTEGER;
         BEGIN
           l_xid.formatid := format_id;
           l_xid.gtrid := hextoraw('hex(gtrid)');
           l_xid.bqual := hextoraw('hex(bqual)');
           l_ret := DBMS_XA.XA_ROLLBACK(xid = > l_xid);
         dbms_output.put_line(l_ret);
         END;
         /
         ```

### 一時停止されたトランザクション

一時停止されたトランザクションとは、コミット後も長時間終了しないトランザクションを指します。一般的なシナリオは以下の2つです：

1. トランザクションが関連するパーティションにリーダーが存在せず、トランザクションの状態機械が進められない場合。

2. トランザクションはリーダー上で完了しているものの、スタンバイマシンのメモリ、ネットワーク帯域幅などのリソース制限により、ログの同期や再生が遅く、トランザクションの状態が終了するのが遅い場合。

上記の2つのシナリオでは、対処方法が異なります。以下にそれぞれ説明します。

**パーティションにリーダーが存在しない場合**

OceanBaseデータベースのアーキテクチャでは、パーティションは複数のレプリカを持ち、そのうち1つだけがリーダー（プライマリ）、他はすべてフォロワー（セカンダリ）となります。リーダーが配置されているOBServerがダウンした場合、リーダーが存在しなくなります。少数派のレプリカに異常が発生した場合、他のレプリカはPAXOSプロトコルに基づいて新たなリーダーを選出します。このプロセス中に実行中のトランザクションが長時間トランザクションとなる可能性があります。

このようなシナリオでは、以下の方法で対処します：

1. 現在のトランザクションが関連するすべてのテーブル情報を照会します。SQLは以下のとおりです。ここで、`participants` の各 `tid` は1つのテーブルを表します。

   ```sql
   SELECT svr_ip, trans_id, participants FROM OCEANBASE.__all_virtual_trans_stat WHERE part_trans_action> 2 AND ctx_create_time < date_sub(now(), INTERVAL 600 SECOND) AND is_exiting != 1;
   ```

2. 上記のパーティションリストにリーダーが存在するかどうかを個別に確認します。SQLは以下のとおりです。`role` 列がすべて follower の場合、すべてがフォロワーレプリカであり、リーダーが存在しないことを意味します。

   ```sql
   SELECT svr_ip, svr_port,table_id, partition_idx, role, status, replica_type FROM OCEANBASE.__all_virtual_clog_stat WHERE table_id=テーブルID;
   ```

   パーティションにリーダーが存在しない場合、現在のトランザクションは長時間トランザクションとなります。長時間トランザクションの処理手順に従って対処できます。

**レプリカのアプリケーションログ適用が遅い場合**

レプリカのアプリケーションログ適用が遅い原因は多岐にわたります。例えば、あるOBServerノードサーバーが突然リソース異常を起こし、OS上で実行されているタスクが大量のI/Oやネットワークなどのリソースを消費し、そのサーバー上のOBServerの応答が遅くなる場合。または、プライマリレプリカの分布が均等でなく、特定のサーバー上にリーダーが特に多く、リーダーがアプリケーション要求に応答する際に大量のリソースを消費し、フォロワーの利用可能なリソースが相対的に少なくなり、そのフォロワーが対応するリーダーに追いつけない場合。さらに、あるOBServerノードサーバーのハードウェアに異常が発生した場合、例えばNIC異常により、PAXOSプロトコルがフォロワーに伝わるのが非常に遅く、待機状態や追従中の状態が続く場合。または、そのOBServerがマージやバックアップなどを行っている場合などです。

このようなシナリオでは、以下の方法で対処します：

1. 現在のトランザクションが関連するすべてのテーブル情報を照会します。SQLは以下のとおりです。ここで、`partition` の各 `tid` は1つのテーブルを表します。

   ```sql
   SELECT svr_ip, svr_port,trans_id, 'partition' FROM OCEANBASE.__all_virtual_trans_stat WHERE part_trans_action > 2 AND ctx_create_time < date_sub(now(), INTERVAL 600 SECOND) AND is_exiting != 1;
   ```

2.  第1ステップで取得した`partition`に記録されている`table_id`情報に基づき、現在の`pkey`に対応する`leader`の位置を確認します。

   ```sql
   SELECT svr_ip,svr_port FROM OCEANBASE.__all_virtual_clog_stat WHERE role='LEADER' AND table_id = テーブルID;
   ```

   もし第1ステップと第2ステップで対応する`svr_ip`が異なる場合、異常トランザクションはフォロワー上に存在します。

3.  上記トランザクションに対応するパーティション、および現在のクラスタ内のレコード数を照会します。

   ```sql
   SELECT count(1) FROM OCEANBASE.__all_virtual_trans_stat WHERE trans_id LIKE '%{第1ステップのtrans_idからhashフィールドを抽出したもの}%'AND`partition` LIKE '%xxx%';
   ```

   上記のクエリ結果が1件のみの場合、異常トランザクションはスタンバイ機上にのみ存在します。この場合は、OceanBaseサポートチームにお問い合わせください。
