# バックアップ・リストアの概要

このセクションでは、OCPがOceanBaseに提供するバックアップ・リストア機能とセカンダリバックアップ機能について説明します。

## バックアップ・リストア

バックアップ・リストアは、OceanBaseデータベースの高可用性機能の中核をなすコンポーネントであり、主にデータの安全性を確保するために使用されます。これには、ストレージメディアの損傷やユーザーの誤操作などによるデータ損失の防止が含まれます。ストレージメディアの損傷やユーザーの誤操作によってデータが失われた場合、リストア機能を使用してユーザーデータを復元できます。

   <main id="notice" type='explain'>
   <h4>説明</h4>
   <p>OceanBase 4.x系では、sysテナントはバックアップをサポートしていません。
   </p>
   </main>

現在、OceanBaseデータベースはFile（NFS）、OSS、OBS、S3の4種類のストレージメディアをサポートしており、バックアップ、リストア、管理の3つの機能を提供しています。

物理バックアップは、ベースラインデータとログアーカイブデータの2種類のデータで構成されており、したがって物理バックアップはログアーカイブとデータバックアップの2つの機能が組み合わさっています。

* ログアーカイブとは、ログデータの自動アーカイブ機能を指します。OBServerノードは定期的にログデータを指定されたバックアップパスにアーカイブします。この動作は完全に自動的であり、外部からの定期的なトリガーは不要です。

* データバックアップとは、ベースラインデータをバックアップする機能を指します。この機能は、フルバックアップと増分バックアップの2種類に分かれています。

  * フルバックアップとは、ベースラインが必要なすべてのマクロブロックをバックアップすることを指します。

  * 増分バックアップとは、前回のバックアップ以降に追加または変更されたマクロブロックをバックアップすることを指します。

OceanBaseデータベースはテナントレベルでのリストアをサポートしており、リストアは既存のデータのバックアップに基づいて新しいテナントを再構築するプロセスです。リストアプロセスには、テナントのシステムテーブルとユーザーテーブルのRestoreおよびRecoverプロセスが含まれます。Restoreは、リストアに必要なベースラインデータをターゲットテナントのOBServerノードに復元することです。Recoverは、ベースラインに対応するログを対応するOBServerノードに復元して再生することです。

### 物理バックアップのアーキテクチャ

OceanBaseデータベースの物理バックアップのアーキテクチャは以下の図のとおりです。

![image.tiff](https://help-static-aliyun-doc.aliyuncs.com/assets/img/zh-CN/0082988061/p200031.tiff "image.tiff")

ユーザーがシステムテナントでバックアップ対象のクラスタにログインした後、まずSQLを使用してログアーカイブを開始する必要があります。ログアーカイブの開始段階が完了した後に、ベースラインバックアップを開始できます。

ログアーカイブは定期的にバックアップ先に送信されます。ユーザーが一度`alter system archivelog`を実行するだけで、ログバックアップはバックグラウンドで継続的に実行されます。ログアーカイブは、各PG（PartitionGroup）のleaderが定期的にそのPGのログをバックアップメディアの指定されたパスにアーカイブする責任を負います。RS（RootService）は定期的にログアーカイブの進捗状況を統計し、内部テーブルに更新します。

データバックアップはユーザーによってトリガーする必要があります。一般的なシナリオとしては、土曜日に1回のフルバックアップ、火曜日と木曜日に1回の増分バックアップを実行する方法があります。ユーザーがデータバックアップリクエストを送信すると、そのリクエストはまずRSが配置されているノードに転送されます。RSは、現在のテナントとそのテナントが含むPGに基づいてバックアップデータのタスクを生成し、その後バックアップタスクをOBServerノードに配布して並列実行します。OBServerノードは、PGのメタ情報とマクロブロックを指定されたバックアップディレクトリにバックアップする責任を負います。マクロブロックはPG単位で管理されます。

OceanBaseデータベースは現在、File（NFS）、OSS、OBS、S3の4種類のストレージメディアをバックアップ先として使用することをサポートしています。以下の2つの図は、バックアップ機能がバックアップ先に作成するディレクトリ構造と、各ディレクトリに保存されるファイルタイプを示しています。図1はV4.x系のOceanBaseクラスタに適用され、図2はV3.x系のOceanBaseクラスタに適用されます。

  └── 1 # cluster_id
      └── tenant_incarnation_1 #分身ID（OceanBaseクラスタ4.x系に適用）
          ├── 1001 # テナントID

          │   │   ├── 1 # clogバックアップのラウンドID
          │   │   │   ├── data # ログのデータディレクトリ

          │   │   └── tenant_clog_backup_info # ログバックアップのメタ情報、ラウンドIDごとに分割して記録
          │   └── data # データのルートディレクトリ

### 物理復元アーキテクチャ

OceanBaseデータベースの物理復元アーキテクチャは以下の図のとおりです。

![復元アーキテクチャ.png](https://help-static-aliyun-doc.aliyuncs.com/assets/img/zh-CN/0082988061/p200032.png "復元アーキテクチャ.png")

ユーザーが確認できるプロセスは主に2つあります：

1. 目的クラスタで `CREATE RESOURCE POOL` コマンドを使用して、復元テナントに必要なresource poolを作成します。

2. `ALTER SYSTEM RESTORE TENANT` コマンドを使用して、テナント復元タスクをスケジュールします。

バックアップと復元において、restore tenantコマンド内部のプロセスは以下のとおりです：

1. 復元用テナントの作成

2. 復元テナントのシステムテーブルデータの復元

3. 復元テナントのシステムテーブルログの復元

4. 復元テナントのメタ情報の調整

5. 復元テナントのユーザーテーブルデータの復元

6. テナントのユーザーテーブルログの復元

7. 復元後の処理

単一のPGについて言えば、復元プロセスはまずPGのメタ情報とマクロブロックデータを指定されたOBServerノードにコピーし、ベースラインデータのみを持つPGを構築します。この時点ではデータバックアップの時点までしか復元されません。その後、PGのログを指定されたOBServerノードにコピーし、そのPGのMemTableに戻します。これにより、災害発生時刻またはユーザーが復元したい時刻まで復元されます。このプロセスでログの量が多すぎる場合、ダンプ操作がトリガーされる可能性があります。

## 二次バックアップ

<main id="notice" type='explain'>
   <h4>説明</h4>
   <p>OceanBase 4.x系では二次バックアップはサポートされていません。
   </p>
   </main>

OceanBaseクラスタのバックアップ・リストアにおいて、通常のバックアップを一次バックアップと呼ぶならば、二次バックアップとは、OceanBaseクラスタで一次バックアップが正常に完了した上で、その一次バックアップのフルバックアップデータを再度バックアップし、通常のバックアップとは異なる保存先にアーカイブすることです。フルバックアップデータには、ベースラインデータとログアーカイブデータが含まれます。

二次バックアップの目的は、一次バックアップのストレージ負荷を軽減することです。通常のバックアップが保存されているサーバー上のバックアップデータを定期的に二次バックアップの保存ディレクトリにアーカイブすることで、一次バックアップのバックアップファイルの保持日数を短縮し、一部のストレージ容量を解放できます。

同時に、二次バックアップはOceanBaseクラスタの復元可能性も保証します。通常のバックアップが保存されているサーバーに障害が発生し、バックアップファイルが取得できなくなった場合でも、二次バックアップによりOceanBaseクラスタの復元可能性を確保できます。

二次バックアップの有効化と設定については、[テナントレベルのバックアップポリシーの作成](500.regular-backup/200.manage-tenant-backup-strategy/100.creat-a-tenant-backup-stategy.md)および[クラスタレベルのバックアップポリシーの作成](500.regular-backup/100.manage-cluster-backup-strategy/100.create-a-cluster-backup-strategy.md)を参照してください。二次バックアップタスクについては、[バックアップの概要](../1100.backup-and-restoration-functions/300.backup-and-recovery-overview.md)を参照してください。
